# Ревью: задача 3 плана 6 — состояние приложения. Измерение: настоящие поломки поведения

Дата: 01.08.2026. HEAD до слайса — `0acfe93`, слайс не закоммичен.

Объём: `client/state/filters.js`, `client/state/sorting.js`, `client/state/session.js`
и три тестовых файла в `tests/web/`. Прогон трёх файлов слайса: 32 теста зелёные
(`cd client && npm test`).

Проверка шла значениями, а не чтением замысла: перебор `cycled` прогнан по всем
достижимым сочетаниям, `passes` сверена с боевым SQL в
`backend/storage/repository/sections.py`, имена полей `chosen` — с
`bridge/feed.py:FILTER_FIELDS`, ключи сортировки — с `backend.model.query.Sort`.

## Сильные стороны

- **Круг из трёх состояний замкнут и не имеет ловушек.** Прогон `cycled` четыре
  раза подряд по одной строке даёт ровно `пусто → включено → исключено → пусто →
  включено`; невозможное состояние «включён и исключён разом» недостижимо, потому
  что каждая ветвь пишет обе половины сразу, а не одну. Ветка «строка уже
  исключена» отдельная и правильная: `on` она не трогает, `ex` чистит.
- **`passes` совпадает с базой посимвольно по смыслу.** Внутри признака «или»
  (`_carrying` → `IN`), между признаками «и» (отдельный `where` на каждый),
  исключённое сильнее включённого и проверяется до включённого. Отдельно верно
  главное расхождение, на котором легко ошибиться: карточка **без** оценки
  исключением по оценке не задевается — в SQL это `_COLUMN.is_(None) |
  not_in(...)`, здесь `has = []` и `some(...)` даёт `false`. Округление вниз тоже
  сходится: `Math.floor` против `CAST(score AS INTEGER)`, оценки положительные.
- **Контракт с мостом не разъехался.** Шесть имён `chosen` — это ровно
  `FILTER_FIELDS` из `bridge/feed.py`; `{ key, descending }` из `orderFor` — ровно
  то, что читает `_feed`; пять ключей сортировки — ровно `Sort`; три типа
  содержимого — ровно `Kind`.
- **`marked` действительно другой автомат, а не сокращение `cycled`.** Включает из
  любого состояния (в том числе из исключённого), выключает в пустоту, через
  исключение не проводит — то есть клик по метке на карточке не может спрятать ту
  карточку, с которой нажали.
- **Возврат того же объекта из `withKind`/`withSection` при равном значении
  проверен и безопасен.** Оба результата уходят в `onsession(...)`, а там
  `let session = $state(...)`; присваивание той же ссылки — не событие, и это
  верно, потому что ничего и не изменилось. Единственный побочный эффект по
  дороге — `--primary` в `chooseKind` — выставляется до вызова и от короткого
  замыкания не зависит.
- **`EMPTY` за прогон не портится.** После четырёх `cycled`, `marked` и `cleared`
  подряд `EMPTY` остаётся `{on:{[],[],[]},ex:{[],[],[]}}`: все ветви строят новые
  массивы через `spread` и `filter`, ни одной записи на месте нет.
- **Ноль не притворяется законной оценкой.** Проверено по коду, а не по догадке:
  гистограмма строится по `range(1, 11)`
  (`backend/storage/repository/sections.py:126,133`), модалка фильтра предлагает
  `TEN = [10..1]`, шкалы у `average_score` — целые ≥ 1. Столбца «0» в проекте нет.

## Находки

### Critical (обязательно исправить)

**1. `client/state/sorting.js:20-21` — сортировка по алфавиту идёт в сторону,
обратную своей подписи.**

```js
{ key: 'title', down: true,  icon: 'sort_by_alpha', dir: 'arrow_downward', label: 'По алфавиту, А → Я' },
{ key: 'title', down: false, icon: 'sort_by_alpha', dir: 'arrow_upward',   label: 'По алфавиту, Я → А' },
```

`orderOf` переводит `down` прямо в `descending` (`sorting.js:50`), а база
применяет его так: `key.desc() if feed.order.descending else key.asc()`
(`backend/storage/repository/sections.py:96`). Значит состояние с подписью
**«По алфавиту, А → Я» уезжает как `descending: true` и возвращает Я → А**, а
состояние «Я → А» возвращает А → Я. Ровно наоборот.

Входные значения, при которых наступает: раздел «Оценённые», позиция 6
(`orderFor('rated', 6)` → `{key: 'title', descending: true}`) — это шестое нажатие
кнопки сортировки от открытия раздела. В «Хочу посмотреть» это позиция 2
(`CYCLES.wishlist = [8, 9, 6, 7]`), то есть **третье нажатие**, и там алфавит —
один из двух критериев вообще.

Причина ошибки видна в самой таблице: `down` служит сразу двум вещам — стороне
сортировки и направлению стрелки на кнопке (`dir` меняется с ним синхронно во всех
десяти строках). У оценки, дат и даты добавления «стрелка вниз» и «по убыванию» —
одно и то же, у алфавита нет: «А → Я» рисуется стрелкой вниз, но это `asc`.
Комментарий над таблицей («Направление показано стрелкой в углу кнопки») подтвердил
подмену смысла, а не поймал её.

Почему важно: это единственный в слайсе случай, когда элемент интерфейса делает
обратное тому, что о себе написал, и заметить это можно только на непустой
библиотеке. Оба состояния достижимы обычным перебором, никаких особых условий.

**Беда в самом плане, а не в исполнении:** таблица в
`docs/plans/2026-07-31-page-shell.md:1210-1211` содержит ту же перестановку, и код
её перенёс дословно. В макете (`docs/design/index.html:1840-1841`) колонок `key` и
`down` нет вовсе — там только глиф и подпись, — то есть ошибка появилась при
дописывании плана. **Править нужно и план, и код**, иначе следующее чтение плана
вернёт её обратно.

Как чинить — поменять местами `down` у двух строк алфавита, ничего больше не
трогая:

```js
{ key: 'title', down: false, icon: 'sort_by_alpha', dir: 'arrow_downward', label: 'По алфавиту, А → Я' },
{ key: 'title', down: true,  icon: 'sort_by_alpha', dir: 'arrow_upward',   label: 'По алфавиту, Я → А' },
```

и приписать рядом коротко, что у алфавита стрелка и `descending` расходятся
намеренно. Порядок строк и подписи остаются на месте, поэтому «первое состояние
алфавита» по-прежнему А → Я, а тест «соседи — две стороны одного критерия»
(`tests/web/sorting.test.js:26-39`) остаётся зелёным: он сверяет `second.descending
=== !first.descending`, а не подпись со стороной. Ни один тест слайса подпись со
стороной не связывает — поэтому ошибка и прошла молча.

### Important (следует исправить)

**2. `client/state/sorting.js:39-44` — `nextSort` и `stateAt` не переживают `null`,
а `null` — это начальное значение `session.sort`.**

`orderFor` про нетронутый переключатель знает (`position ?? 0`, строка 57), два
других экспортируемых метода того же модуля — нет:

- `stateAt('rated', null)` → `cycleOf('rated')[null]` → `undefined` →
  `SORT_STATES[undefined]` → **`undefined`** (проверено запуском). Читатель
  результата возьмёт `.icon` и уронит шапку целиком.
- `nextSort('rated', null)` → `(null + 1) % 8` → **`1`**. Ответ случайно верный:
  `null` приводится к нулю, а нетронутый переключатель и стоит на нуле. Но держится
  это на приведении типов, а не на решении, и `nextSort('rated', undefined)` уже
  даёт `NaN` — то есть `sort: NaN`, из которого выхода нет: `NaN + 1` снова `NaN`,
  и кнопка сортировки перестаёт переключаться до смены раздела.

Сегодня не ломается: оба зовутся из шапки плана 6 через `session.sort ?? 0`
(`docs/plans/2026-07-31-page-shell.md:2080,2152`). То есть модуль из трёх функций
над одним и тем же `position` обрабатывает `null` в одной из трёх, а двум другим
вменяет это вызывающему — и вызывающий про уговор нигде не предупреждён.

Почему важно: `null` здесь не экзотика, а состояние при каждом открытии раздела;
цена ошибки — не «не то значение», а пустой экран (`undefined.icon`). Уговор,
который надо помнить в каждой точке вызова, рано или поздно забудут — плану 8 и 9
эти же функции ещё звать.

Как чинить: свести все три к одному месту — `const at = (section, position) =>
cycleOf(section)[position ?? 0]`, и через него пустить `stateAt` и `orderFor`, а
`nextSort` записать как `((position ?? 0) + 1) % cycleOf(section).length`. Вызовы
`?? 0` в шапке после этого убираются.

### Minor (можно потом)

**3. `client/state/sorting.js:37` — неизвестный раздел молча получает набор
«Оценённых».**

`CYCLES[section] ?? CYCLES.rated`. Это не мёртвая ветвь: `requestOf` из плана 8
зовёт `orderFor(session.section, session.sort)` и на разделе `stats`
(`docs/plans/2026-07-31-filters-and-stats.md:1419`), где своего набора нет.
Проверено: `orderFor('stats', null)` возвращает `{key: 'score', descending: true}`,
и `StatsScreen` это поле просто выбрасывает, беря только `kind` и `filters`. То
есть падения нет, и умолчание тут нужное.

Плохо другое: у этого умолчания нет ни строчки объяснения, и опечатка в имени
раздела («raited») даст не отказ, а тихую сортировку по оценке. Чинить —
комментарием на месте: «разделы без своего перебора спрашивают порядок всё равно
(гистограмма), и им отдаётся набор „Оценённых“; поле они не используют».

**4. `client/state/filters.js:98-99` — оценка отбирается по истинности, а не по
наличию.**

```js
const score = view.rating?.score
return score ? [Math.floor(score)] : []
```

`score === 0` даёт `[]`, то есть карточка с нулём не совпала бы с фильтром «0» и
не отсеялась бы исключением «0». Проверено запуском: `passes({rating:{score:0}},
фильтр 0)` → `false`; исключение нуля такую карточку пропускает. **Поломкой это
сегодня не является**: ноль в проекте не законная оценка — гистограмма
`range(1, 11)`, модалка предлагает `[10..1]`, шкалы целые ≥ 1. Случай
`rating: {score: null}` (закладка без оценки) обработан правильно и совпадает с
базой.

Чинить по желанию: `score == null ? [] : [Math.floor(score)]` — тогда условие
говорит про наличие, а не про истинность, и правило «столбцов десять» остаётся
единственным местом, где живёт диапазон.

**5. `client/state/filters.js:6-7` — `EMPTY` один на всё приложение и не заморожен.**

`newSession()` кладёт в поле `filters` саму эту ссылку, `withKind` возвращает её же
при сбросе, а `let session = $state(newSession())` объявлен в двух корнях
(`docs/plans/2026-07-31-page-shell.md:2182,2395`). Svelte 5 оборачивает вложенное в
прокси и пишет в исходный объект: одна случайная запись вида
`session.filters.on.tags.push(id)` испортила бы `EMPTY` **навсегда и во всех
корнях**, а сброс фильтров при смене типа с этого дня возвращал бы не пустоту.

Из написанного сегодня этого не делает никто — проверено: все три модуля чисты, а
компоненты планов 7–9 меняют фильтры только через `onfilters(cycled(...))`. Поэтому
Minor.

Чинить дёшево: `Object.freeze` на `EMPTY` и на три его вложенных объекта с
массивами — тогда случайная запись станет громкой ошибкой вместо тихой порчи.
Заморозку надо прогнать тестами: в `svelte/src/internal/client/proxy.js` версии
5.56 проверки `Object.isFrozen` нет, прокси навешивается всё равно, но трогает
исходный объект только на запись, которой сейчас не бывает.

  `docs/plans/2026-07-31-page-shell.md:1210-1211`, иначе план вернёт ошибку при

  два `?? 0` из шапки плана 6 — дешевле сделать до того, как эти функции позовут

- Что проверено и оказалось в порядке, чтобы это не разбирали заново: круг
  `cycled` по всем достижимым сочетаниям, совпадение `passes` с боевым SQL по всем
  трём признакам и по неоценённому, совпадение шести имён `chosen` с
  `FILTER_FIELDS`, совпадение ключей сортировки с `Sort`, отсутствие достижимой
  позиции вне набора раздела (`nextSort` замыкает по модулю, `withSection` при
  смене раздела ставит `null` — других путей сменить раздел в планах нет),
  недостижимость нулевой оценки.
