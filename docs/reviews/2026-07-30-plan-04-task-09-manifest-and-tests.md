## Правило 8 — ничего на всякий случай

**`SeriesCounts` как отдельный тип.** Обоснован. `Item` требует шесть
обязательных полей (`id`, `kind`, `source`, `source_id`, `title`, `synced_at`),
которых у ответа `/tv/{id}` в дешёвом виде нет и не нужно добывать. Заворачивать
два числа в `Item` означало бы городить фиктивные значения ради остальных
шести полей. `SeriesCounts(seasons, episodes)` — минимальный носитель для
`Found[T]` из `Outcome`, потребители есть уже сегодня: `parse_series_counts`,
`TmdbClient.series_counts`, `Loader.refresh`. Не нарушение.

**Две ветви в `Loader.refresh`:**

```python
if item is None or item.kind is not Kind.SERIES:
    return
if item.source is not Source.TMDB:
    return
```

Вторая ветвь **не мёртвая и не лишняя**. Проверено по `Sources.client_for`
(`backend/sources/registry.py:43`):

```python
def client_for(self, source: Source):
    return {
        Source.TMDB: self.tmdb,
        Source.STEAM: self.steam,
        Source.GOG: self.gog,
    }.get(source)
```

`None` он отдаёт только для `Source.MANUAL` (и любого источника вне словаря).
Для `Source.STEAM`/`Source.GOG` он возвращает **настоящий** клиент — а у
`SteamClient`/`GogClient` метода `series_counts` нет вовсе. Если бы вторую
ветвь убрали (понадеявшись на `client_for`, возвращающий `None`), карточка
ручного сериала (`Kind.SERIES`, `Source.MANUAL`) прошла бы первую проверку,
`client_for` отдал бы `None`, и `client.series_counts(...)` упал бы
`AttributeError` — на выражении-аргументе `answered()`, то есть **до** входа в
`try/except` самого `answered`, значит необработанным.

По коду источников (`backend/sources/steam/parse.py:32,66`,
`backend/sources/gog/parse.py:34`) Steam и GOG заводят карточки только с
`Kind.GAME`; `Kind.SERIES` у них взяться неоткуда. Значит на практике до
`client_for` доходит только пара `(SERIES, TMDB)` и `(SERIES, MANUAL)` — и
вторая ветвь ловит ровно `MANUAL`, которую и покрывает
`test_a_manual_card_is_never_re_asked`. Останься гипотетическая карточка
`(SERIES, STEAM)` (битые данные, чужой баг) — с нынешней проверкой `refresh`
тихо выходит; без неё — упал бы `AttributeError` на `SteamClient`, у которого
нет `series_counts`. Ветвь оставлена верно и в верном порядке (до
`client_for`).

## Правило 2 и 6 — место кода, одна ответственность

`backend/service/loading.py` — докстринг модуля: «Кандидат превращается в
карточку.» Докстринг `Loader`: «Три круга загрузки. Первый — выдача поиска, она
уже позади: на входе кандидат. Здесь второй, детальный ответ и обложка разом, и
запись.» Ни один не упоминает `refresh` — а `refresh` работает не с
кандидатом, а с уже лежащей в базе карточкой, это не «второй круг».

Место выбрано по плану намеренно: `docs/plans/2026-07-27-reading.md:86`
описывает файл как «loading.py водит три круга, перезапрос по сроку, путь по
ссылке» — то есть архитектурно `loading.py`/`Loader` заранее назначен домом и
для перезапроса, и задача 9 явно значится «Изменить: backend/service/loading.py».
Само размещение не считаю нарушением места (правило 2) — оно проектное, а не
случайное.

Но докстринги за размещением не поспевают: сейчас читатель `Loader` по
докстрингу не узнает о третьей обязанности класса. Тест на «опиши модуль/класс
одной фразой без и» не проходит буквально — фраза есть, но она неполная, а не
избыточная (лишнего «и» нет, но и нет упоминания второго дела). Это разошлось
с картой (`docs/module-map.md` корректно показывает `refresh` как метод), но
не с прозой докстринга.

**Находка (Important):** `backend/service/loading.py:23-25` — докстринг
`Loader` не упоминает `refresh`. Починка: дописать фразу про третью обязанность
(например: «...Здесь же перезапрос по сроку — обновление того немногого, что у
карточки меняется само.») либо явно решить, что `refresh` — не часть «трёх
кругов» и заслуживает отдельного упоминания в докстринге. Не блокирует коммит:
размещение оправдано планом, страдает только точность описания.

## Правило 11 — комментарии и докстринги

Прочитан каждый комментарий/докстринг в диффе:

- `SeriesCounts`: «Единственное, что у карточки перезапрашивается: сезоны и
  серии растут.» — объясняет, почему тип узкий, не пересказывает поля. ОК.
- `REFRESH_TTL` над константой: «Срок тот же, что у оценок со значением.
  Перезапрашиваем только видимые карточки: невидимых может быть тысяча.» —
  небанальное решение (почему 30 дней, почему не «все карточки»). ОК.
- `Loader.refresh` докстринг и внутренние комментарии («Ручной карточке
  перезапрашивать нечего...», «Отказ — состояние данных: повторим при
  следующем показе.») — каждый объясняет решение, а не код рядом. ОК.
- `TmdbClient.series_counts` докстринг: «Перезапрос по сроку. Без
  `append_to_response`: `aggregate_credits` тянет 167 КБ, а нужны два числа.» —
  конкретная причина отдельного метода, число обосновывает решение. ОК.
- `parse_series_counts` докстринг: «Оба числа лежат в ответе /tv/{id} без
  единого довеска. Считать сезоны по длине seasons[] нельзя: нулевой сезон —
  спецматериалы, и у «Andor» вышло бы три вместо двух.» — прямое перенесение
  проверенной вживую ловушки из `CLAUDE.md`, не декоративно. ОК.
- Докстринги тестов (`167 КБ довеска...`, `SourceHttp.get отдаёт отказ...`,
  `Перезапрос идёт по видимым карточкам...`, `Ответ 200 с телом не тем...`,
  `Иначе следующий показ пойдёт за теми же числами опять.`, `У фильма меняться
  нечему...`, `Перезапрашивать нечего: она ниоткуда не приезжала.`,
  `Сорвавшийся клиент — тот же отказ...`, `Карточка твоя: из TMDB пропала — у
  тебя осталась.`, докстринг про границу срока и закрепление `REFRESH_TTL`) —
  все объясняют, зачем нужен именно этот тест / что он ловит, ни один не
  пересказывает ассерт. ОК.

Нарушений не найдено.

задания ловятся ровно этими тестами.

**Про `assert REFRESH_TTL == timedelta(days=30)`
(`test_the_edge_of_the_term_is_not_stale_yet`).** Это оправданное закрепление,
не чтение объявления вхолостую — по той же схеме, что `SEARCH_SIZE`/`PAGE_SIZE`
в проекте: рядом, в том же тесте и в соседнем `test_a_day_past_the_term_is_stale`,
стоит проверка, что величина **применяется** — `MOMENT - REFRESH_TTL` и
`MOMENT - REFRESH_TTL - timedelta(days=1)` гоняются через реальный `refresh()`,
и поведение (`tmdb.asked`) меняется на границе. Без строки-якоря `REFRESH_TTL`
можно было бы урезать вдвое, а оба теста остались бы зелёными, потому что оба
мерили расстояние от самой константы, а не от литерала — это и есть та мутация
из списка задания, которая «сперва прошла молча». Закрепление её закрывает.
Докстринг теста прямо это объясняет.

## Чего не хватает

Правдоподобная поломка, которую ни один из 41 теста не поймает:

**`parse_series_counts` при частично пустом ответе TMDB.** Если у сериала
`number_of_seasons` есть, а `number_of_episodes` отсутствует (снят с публикации
эпизодов, спецвыпуск без объявленного числа серий и т. п.), `payload.get(...)`
тихо отдаёт `None`, и `Loader.refresh` без раздумий пишет это `None` поверх уже
хранимого корректного `episodes_count` через `refresh_series_counts`. Ни
фикстура `tv_detail.json`, ни один из моков в `test_tmdb_card.py` не оставляют
ни одно из двух полей отсутствующим — везде оба ключа на месте. Тест,
целенаправленно ломающий это (замена `payload.get("number_of_episodes")` на
константу/удаление обработки отсутствия), прошёл бы зелёным.

Также проверено по подсказке задания и не оказалось дырой:
- **Сериал из Steam/GOG** — комбинация `(Kind.SERIES, Source.STEAM/GOG)`
  недостижима через код источников (см. правило 8 выше); ветвь `item.source is
  not Source.TMDB` в любом случае выходит без падения. Не гэп, а недостижимое
  состояние — тестировать нечего.
- **Карточка, удалённая в момент перезапроса** — `refresh_series_counts` это
  `UPDATE ... WHERE id = item_id`, на несуществующей строке — не операция, не
  падение. Гонка теоретически возможна, но не тестируется и не роняет ничего:
  не критично, можно оставить без теста.
- **`Missing` из `answered`** — да, достижимо: `TmdbClient.series_counts`
  возвращает `Missing()` напрямую (по классификации 404 с известным кодом), не
  через исключение, значит `answered()` просто транслирует его — и это
  покрыто `test_a_vanished_series_is_logged_and_kept`.

## Вердикт по измерению

Критических нарушений манифеста не найдено. Одна важная находка (докстринг
`Loader` не отражает третью обязанность — правило 6, косметика, не блокирует),
