# Ревью 23.08.2026 — ошибки поведения в мосте и фронте

Диапазон: `0650ea8..84b25c9`, только `bridge/` и `client/`.
Измерение: настоящие поломки поведения. Тесты, повторы, манифест, полнота и
мутации — чужие измерения, здесь их нет.

Читалось: весь дифф по обеим папкам, плюс код вокруг — `client/api/bridge.js`,
`client/components/Feed.svelte`, `client/components/Picker.svelte`,
`client/components/Synopsis.svelte`, `client/app/CardModal.svelte`,
`bridge/answer.py`, `bridge/thread.py`, `bridge/kept.py`,
`backend/model/results.py`, `backend/model/suggestion.py`,
`backend/storage/repository/credits.py`.

## Сильные стороны

- **Смещение догрузки помнит мост, а двигает его приехавший ответ.**
  `bridge/search.py:96-110` — сорвавшийся запрос до сдвига не доходит вовсе, и
  порция остаётся неспрошенной, а не пропадает молча. Это ровно та дыра, которую
  ревью слайса 2 называло по имени; здесь она закрыта строением, а не заплатой.
- **Приращение против накопленного разведено правильно.**
  `bridge/search.py:121` отдаёт `merged[len(shown):]`, а в `Kept` кладёт всё
  целиком. Срез верен именно потому, что `merge_results`
  (`backend/model/results.py:55-63`) строит `list(local)` плюс новые в конец и
  порядок половин не трогает: хвост среза — ровно новые строки. Память при этом
  остаётся полной, и `ensure` заводит кандидата из первой порции после приезда
  второй.
- **`ready`/`done` гасятся до запроса, а не по ответу**
  (`client/app/SearchScreen.svelte:165-167`). Это закрывает гонку «дописанная
  строка пускает догрузку тем же номером операции» — ту самую, что описана в
  шапке `look()`.
- **`withoutText`** (`client/app/reread.js:36`) — точный инструмент: перечитанная
  строка не стирает показанный текст пустым полем. Применён в обеих дверях
  (`reread.refreshed`, `SearchScreen.adopt`).
- **`refreshed` спрашивает синопсис своим каналом и глушит его отказ**
  (`client/app/reread.js:52-53`): не приехал текст — метка `cover` всё равно
  доезжает, и перезалитая обложка не остаётся в суточном кеше из-за пустяка.
- **`_text` в мосте терпит удалённую строку** (`bridge/feed.py:53-58`): карточку
  могли снести ровно между показом и вопросом, и показ от этого не падает.
- **Виток догрузки будится пересозданием узла, а не эффектом**
  (`client/components/Feed.svelte:108-111`). Довод про петлю эффекта записан
  рядом и проверен живьём; решение честнее сторожевого флага.
- **Остановка витка на порции, не добавившей ни строки**
  (`client/components/Feed.svelte:65-68`) — настоящая защита от выкачивания
  источника через фильтр, который работает на странице.
- **`refused()` делит плашку и журнал по тому, кто спрашивал**
  (`client/app/SearchScreen.svelte:215-219`): лента молчит, человек узнаёт.
- **Тип обложки уезжает ручкой и переводится внутри заявки**
  (`bridge/serve.py:85-95`, `bridge/covers.py:14-25`): неизвестное значение не
  уходит исключением через границу потоков.

## Находки

Всего 7: Critical — 2, Important — 1, Minor — 4.

### Critical (Must Fix)

#### 1. `client/app/CardModal.svelte:93-99` — чтение синопсиса затирает то, что человек печатает

    $effect(() => {
      if (!view?.item_id || view.synopsis) return
      const untouched = form.synopsis          // <- читается внутри эффекта
      numbered('feed.synopsis', view.item_id, { channel: 'card:text' })
        .then((text) => { if (form.synopsis === untouched) form.synopsis = text })

`form` — это `$state` (строка 28), то есть глубокий прокси, а
`<Field bind:value={form.synopsis}>` (строка 292) пишет в него на **каждое
нажатие клавиши**. Значит `const untouched = form.synopsis` регистрирует
зависимость, и эффект перезапускается на каждую букву.

Что из этого выходит:

1. На каждое нажатие уходит свой вызов `feed.synopsis` через границу потоков.
   Предыдущие устаревают по каналу `card:text` и молчат, доезжает последний.
2. Последний захватил `untouched` = **то, что человек уже набрал**. Пока ответ
   летит, человек больше ничего не нажал — значит `form.synopsis === untouched`
   истинно, и строка `form.synopsis = text` **кладёт поверх набранного текст из
   базы**.

Комментарий над эффектом обещает ровно обратное: «затирать сделанное руками
нельзя ничем». Сторож не работает потому, что снимок `untouched` берётся заново
на каждый перезапуск, а перезапуск устраивает сам набор текста.

Хуже всего на карточке, у которой синопсиса в базе нет вовсе (у игр GOG — обычное
дело, см. докстринг `client/components/Synopsis.svelte:79`): туда приезжает `""`,
и набранный вручную синопсис **стирается в пустоту**.

Пути в окно правки с пустым `view.synopsis` штатные: только что заведённый из
поиска кандидат (`SearchScreen.adopt` читает `feed.views_of`, а `view_from_item`
синопсис не копирует — `backend/model/view.py:79`), карточка, у которой второй
круг не доехал или был отменён уходом с раздела, и любая карточка без синопсиса
в базе.

**Почему важно:** молчаливая потеря введённого пользователем текста в форме
правки — ни плашки, ни следа.

**Как чинить:** снимок брать вне отслеживания, чтобы эффект зависел от карточки,
а не от поля:

    import { untrack } from 'svelte'
    ...
    $effect(() => {
      const id = view?.item_id
      if (!id || view.synopsis) return
      untrack(() => {
        const untouched = form.synopsis
        numbered('feed.synopsis', id, { channel: 'card:text' })
          .then((text) => { if (form.synopsis === untouched) form.synopsis = text })
          .catch((error) => lost(error, 'Не удалось прочитать синопсис'))
      })
    })

Заодно исчезает вызов на каждую букву.

#### 2. `client/app/CardModal.svelte:110-111` — `hint_kind` до подсказки не доезжает, и квадратный всплывающий постер не работает вовсе

    const hinted = (row) => ({ id: row.entity_id, name: row.name,
                               hint: row.hint, hint_item_id: row.hint_item_id })

`Suggestion` несёт четвёртое поле — `hint_kind` (`backend/model/suggestion.py:23`),
и заполняет его репозиторий (`backend/storage/repository/credits.py:334`:
`return row.title, row.id, Kind(row.kind)`). Но `hinted()` — единственный
переводчик строки подсказки для `Picker` (обе двери: `suggest()` на строке 127 и
`more()` на строке 148) — это поле выбрасывает.

Значит в `client/components/Picker.svelte:60` и `:255` `hovered?.hint_kind`
всегда `undefined`, `squareOf(undefined)` всегда `false`, и:

- `shape` всегда `POSTER` (120×180) — место у края окна считается по афишной
  ширине;
- класс `is-square` не вешается никогда, и правило
  `client/styles/picker.css:60` — мёртвое;
- обложка альбома показывается в рамке 2:3 с `object-fit: cover`, то есть с
  обрезанными боками — ровно то, ради устранения чего делался слайс 4.

**Почему важно:** объявленная функция слайса не работает ни в одном случае, при
том что поле проведено через базу, модель и мост. Путь, где данные не приезжают
вовсе.

**Как чинить:** дописать поле в `hinted`:

    const hinted = (row) => ({ id: row.entity_id, name: row.name,
                               hint: row.hint, hint_item_id: row.hint_item_id,
                               hint_kind: row.hint_kind })

### Important (Should Fix)

#### 3. `client/app/SearchScreen.svelte:176-184` — сорвавшаяся первая порция выключает догрузку до конца запроса

    try {
      await portion()
      ready = true
    } catch (error) {
      lost(error, 'Внешняя база недоступна')
    }

`ready` остаётся `false` навсегда для этой строки поиска: `more()` (строка 135) на
нём и стоит. Смещение у моста при этом не сдвинулось — повторить ту же порцию
можно и нужно, но некому: прокрутка вернёт `false`, а другого входа нет. Чтобы
догрузка ожила, человеку надо править строку поиска.

Цена названа в самом коде на строках 141-144: у Google Books `503` — обычная
икота, замерено 23.08.2026, **восемь запросов выдачи из десяти**. Путь не редкий.

**Как чинить:** ставить `ready = true` и в ветке отказа — смещение не сдвинуто,
повтор попросит ту же порцию:

    try { await portion() }
    catch (error) { lost(error, 'Внешняя база недоступна') }
    finally { ready = true }

Бесконечного витка отсюда не выйдет: `more()` ловит отказ и возвращает `false`, а
цикл в `Feed.svelte` встаёт до следующего события метки дна.

### Minor (Nice to Have)

#### 4. `client/app/SearchScreen.svelte:215-219` — смысл условия «ни одной строки» тихо сменился

`refused()` решает по `answer.views.length`, а `answer.views` после правки — это
**приращение**, а не весь ответ. Если внешняя половина привезла двадцать строк,
но все двадцать уже есть в своей половине (книга в библиотеке), приращение
пустое, и при отказе второго источника человек получит плашку «Внешняя база
недоступна» при полном экране строк. Докстринг говорит «ответ не принёс ни одной
строки» — теперь это значит «не принёс ни одной **новой**».

Отказ при этом настоящий, так что вреда немного; но либо докстринг переписать,
либо считать по сумме приращения и уже показанного.

#### 5. `client/components/Feed.svelte:108` вместе с `SearchScreen.portion` — порция без приращения глушит догрузку насовсем

Виток будит только смена `views.length`. Если порция приехала, но приращение
пустое (всё чужое совпало со своим), длина не меняется: узел метки дна не
пересоздаётся, события видимости не будет, а цикл в `more()` сам себя обрывает по
`views.length === shown`. При `more === true` у источника вторая страница не
спросится уже никогда, пока человек не тронет строку.

Случай узкий — нужно, чтобы вся первая порция источника оказалась дублем своей
половины, — и лечится тем же ключом, если считать его не по длине, а по счётчику
приехавших порций.

#### 6. `client/app/visible.js:71-73` против `client/app/reread.js:52` — два синопсиса на разных каналах не упорядочены между собой

`feed.synopsis` второго круга идёт каналом `card:<id>:text`, а перечитывание
правленой карточки — каналом `views:text`. Каналы разные, значит ни один не гасит
другой: ответ круга, отправленный до правки, вправе лечь **поверх** свежего
текста от `refreshed`. Окно крошечное — чтение одной колонки по номеру, — но
защита, которую докстринг `onCardShown` описывает для оценок («человек правит
синопсис, `refreshed` кладёт новый текст, а вернувшийся круг кладёт прежний»), на
сам синопсис не распространяется.

#### 7. `client/components/Feed.svelte:21` — `atEnd` переживает пересоздание метки

`eye.disconnect()` обратных вызовов не шлёт, так что при смене `views.length`
признак остаётся от прежнего узла, пока новый наблюдатель не доложит своё первое
состояние. Между этими двумя мигами цикл `while (atEnd && await onmore())` может
попросить одну лишнюю порцию. Один запрос, не поломка.

## Что проверено и оказалось верным

Чтобы следующий проход не разбирал это заново:

- **Гонки двух порций в мосте нет.** `_outer` читает `shown` до `await`, а кладёт
  после, — но одновременных вызовов не бывает: `Feed.more()` сторожит `asking`, а
  `SearchScreen.more()` не пускает ничего до `ready`, который ставится только
  после приезда первой порции.
- **Устаревший ответ порции не ложится поверх свежего.** `numbered` сверяет номер
  канала в момент доставки (`client/api/bridge.js:67`), а `look()` бьёт канал
  новым номером через `search.local`; отказ `stale` молчит по
  `client/app/trouble.js:12`.
- **Смещение не уезжает на брошенной операции.** `local()` переписывает `_asked`
  целиком вместе с номером, и сторож `self._asked[0] == op` в `_outer` не даёт
  старому ответу двинуть чужое смещение.
- **Номера `feed.synopsis` не копятся в мосте.** `BackendThread._end` снимает
  запись из `_numbered` на каждое завершение (`bridge/thread.py:150-155`).
- **Повторный `put({synopsis})` на каждое появление карточки не заставляет
  `Synopsis.svelte` мерить заново.** Его эффект зависит от примитивного `text`, а
  `patch` кладёт ту же строку — сигнал пропса не срабатывает.
- **Короткий первый экран действительно будится.** `ready = true` выставляется в
  той же синхронной цепочке, что и `arrived()`, то есть раньше, чем Svelte
  пересоздаст метку дна и наблюдатель доложит видимость.
- **Клик по имени догрузку не пускает**: `about()` ставит `done = true` до
  запроса, а `external()` на чужой номер отвечает `stale()`.

## Рекомендации

1. Находки 1 и 2 — до коммита: первая теряет введённый текст, вторая делает
   слайс 4 неработающим в подсказке.
2. Правило, которое стоит записать после находки 1: **снимок «что было до
   запроса» нельзя брать внутри отслеживаемой части эффекта.** Прочитанный там,
   он делает эффект зависимым от того самого поля, которое сторожит, и сторож
   переписывает сам себя на каждое изменение.
3. Находка 2 — второй за проект случай «поле есть в модели, есть в мосте, а
   переводчик на странице его роняет». Проводки такого рода проверяются от
   конечного потребителя вверх, а не от объявления вниз.
