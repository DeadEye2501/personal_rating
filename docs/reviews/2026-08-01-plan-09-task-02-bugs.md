## Strengths

- **`getBoundingClientRect` в `follow` безопасен.** `anchor` привязан к
  `div.picker`, который в разметке безусловен и живёт весь срок компонента, а
  `follow` зовётся только из `onmousemove` строки, лежащей внутри него. Пустым
  `anchor` там оказаться не может, и `position: relative` на том же элементе
  делает перевод координат верным: рамки и отступов у него нет, границы боксов
  совпадают.
- **`bind:value` вместе с `oninput` набранного не теряет и двух источников правды
  не заводит.** Проверено по исходникам Svelte: `bind_value` вешает свой
  слушатель прямо на элемент, а `oninput` идёт делегированным — то есть
  пользовательский обработчик срабатывает **после** записи в `text`. Плюс сам
  `typing` читает `event.currentTarget.value`, а не `text`, поэтому порядок ему
  вообще безразличен; `currentTarget` в делегированном обработчике Svelte
  подменяет намеренно (`events.js:231`), так что это не совпадение.
- **Ключи `{#each}` дублей не дают ни с одной стороны.** У совпадений `hit.id`
  — это `Genre.id` либо `Suggestion.entity_id`, оба первичные ключи; у выбранных
  `one.name + index` различает и двух полных тёзок в одном поле («Иван Иванов0»
  и «Иван Иванов1»), и двух заведённых руками с `id: null`.
- **Заведение с `id: null` отбор по `id` не ломает.** `Suggestion.entity_id`
  объявлен `int`, `Genre.id` тоже, пустого номера в совпадениях не бывает —
  значит `chosen.some((one) => one.id === hit.id)` на `null` ни с чем не
  слипается. Тёзку, заведённого руками, справочник не предложит: его в базе ещё
  нет.
- **Выбор на `mousedown` действительно опережает `blur`.** Обработчик отрабатывает
  внутри диспетчеризации, до действия по умолчанию, — выбор не теряется (но см.
  Important 4 про то, что теряется вместо него).
- **`FiltersModal` переезд таблицы пережил без потерь:** единственный её
  потребитель — `asked` (строка 43), импорт добавлен, а `test_page_contract.py`
  теперь читает `state/genres.js`; `body_of` считает скобки, поэтому однострочный
  словарь ему по зубам.
- **Имена ролей сходятся с базой поимённо:** `director`, `actor`, `showrunner` —
  весь `PersonRole`, `developer`, `publisher` — весь `CompanyRole`.
- **Гонки между полями нет:** `suggested = { ...suggested, [role]: ... }` читает
  текущее значение в момент разрешения промиса, и два поля друг друга не
  затирают.
- **Сессия на запрос** (`Repository._row`/`_rows`) — параллельные `refs.suggest`
  не сталкиваются в SQLAlchemy.

## Issues

### Critical (Must Fix)

**1. Подсказка складывается по порядку приезда, а не по порядку вопроса —
поздний ответ на старую строку затирает свежий.**

`client/app/CardModal.svelte:56-59`:

```js
async function suggest(role, domain, text) {
  const found = await call('refs.suggest', domain, text)
  suggested = { ...suggested, [role]: found.map(hinted) }
}
```

`call` — вызов без номера, и ни отбрасывания устаревшего, ни привязки ответа к
строке, на которую он приехал, здесь нет вовсе. Что это не теория:

- pywebview зовёт **каждый** метод в своём потоке —
  `webview/util.py::js_bridge_call` делает `Thread(target=_call); thread.start()`
  на каждый вызов;
- `BackendThread.run` кладёт каждую заявку отдельной задачей в один цикл, и
  выполняются они вперемешку;
- `CreditsRepository.suggest` делает `1 + N` запросов: строка плюс `_hint` на
  каждого найденного. Короткий префикс даёт до десяти строк, длинный — одну.
  То есть **поздний запрос систематически быстрее раннего**, и «не тот порядок»
  тут не редкий случай, а обычный ход быстрого набора: «и» → «ив» → «иван»
  сначала показывает Ивана, а через мгновение его затирает выдача на «и».

Почему важно: в списке оказываются имена, не отвечающие набранному, — и это
видно не мгновение, а до следующей буквы. Дальше по этому списку человек и
выбирает: щелчок мышью или Enter по подсвеченному кладёт в карточку **другого
человека**, чем тот, кого искали. Проект этот класс уже ловил на себе — «Гонка в
поиске: `_outer` писал сложенную выдачу в память, не проверив, что ячейка ещё
его» (план 5), — и правило оттуда здесь не применено.

Как чинить: пометить ответ тем, на что спрашивали, и отбросить чужой. Дешевле
всего своим счётчиком на роль:

```js
const asked = {}          // роль → номер последнего вопроса

async function suggest(role, domain, text) {
  const mine = (asked[role] = (asked[role] ?? 0) + 1)
  const found = await call('refs.suggest', domain, text)
  if (asked[role] !== mine) return
  suggested = { ...suggested, [role]: found.map(hinted) }
}
```

`numbered` здесь не подходит: он подставляет `op` первым доводом, а
`Refs.suggest(domain, name)` его не принимает.

### Important (Should Fix)

**2. Стрелки и Enter работают по закрытому списку — можно выбрать то, чего не
видно.**

`client/components/Picker.svelte:60-71`. `keydown` не смотрит на `open` вовсе.
Путь без всякой асинхронности: выбрали кого-то с клавиатуры → `clear()` ставит
`open = false`, а фокус из поля никуда не делся → нажали стрелку вниз → `marked`
стал `0` при спрятанном `<ul hidden>` → Enter кладёт в карточку `offered[0]`,
которого человек в этот момент не видел. Тем же путём вместо заведения нового
(Enter без подсветки — это весь жест различения тёзок) молча берётся существующий.

Комментарий у `clear()` («следующий щелчок по полю и так спросит») этот случай и
пропускает: после Enter щелчка нет, поле фокуса не теряло.

Чинить: в начале `keydown` — `if (!open) { if (event.key === 'ArrowDown') open = true; return }`,
либо просто не двигать `marked` и не брать по Enter, пока список закрыт.

**3. `offered[marked]` не проверяется: Enter по строке, которой уже нет, либо
берёт соседа, либо падает.**

`client/components/Picker.svelte:63-69`. `marked` — номер в `offered`, а `offered`
пересчитывается сам по себе, когда приезжает ответ подсказки. `marked`
сбрасывается только в `typing` и в `clear`, но не тогда, когда список сменился
под подсветкой. Отсюда два исхода:

- список стал короче — `offered[marked]` это `undefined`, и `take` падает
  `TypeError: Cannot read properties of undefined (reading 'id')` прямо в
  обработчике клавиши. Наружу это выглядит как «Enter не делает ничего»: и
  выбора нет, и нового не завели, хотя имя набрано;
- список сменился, а длины хватило — Enter берёт **другого человека**, стоящего
  на том же месте.

Основной поставщик обоих — находка 1, но чинить их надо порознь: проверка стоит
одной строки и держит любой будущий источник пересчёта.

```js
} else if (event.key === 'Enter') {
  event.preventDefault()
  const hit = marked >= 0 ? offered[marked] : null
  hit ? take(hit) : create()
}
```

**4. Выбор мышью уводит фокус в никуда: следующее имя набирать некуда.**

`client/components/Picker.svelte:131-134` — `onmousedown={() => take(hit)}` без
`preventDefault`. Порядок в Chromium: обработчик отработал → действие по
умолчанию переносит фокус на саму `<button class="picker__hit">` → микрозадача
Svelte прячет `<ul hidden>` → фокусированный элемент стал `display: none`, и
браузер отдаёт фокус `<body>`.

Итог: после каждого выбора мышью поле мертво — набранное уходит в пустоту, пока
человек не щёлкнет по полю снова. Больнее всего это в «Актёрах», где имён
подряд вводят несколько; на глаз выглядит как «поле перестало печатать».

Чинить одной правкой, и она же обычная для такого списка:

```svelte
onmousedown={(event) => { event.preventDefault(); take(hit) }}
```

Фокус остаётся в поле, `blur` не срабатывает вовсе, список гасит сам `clear()`.

**5. Подсветку стрелкой не прокручивает никто, а в список она не помещается.**

`client/styles/picker.css:33` — `max-height: 216px`, `padding: 4px`; строка
`.picker__hit` это `padding: 7px 10px` при `--body-m: 400 14px/20px`, то есть
34 px. Видно **шесть** строк из десяти (`refs.suggest` отдаёт `limit=10`).
`scrollIntoView` для `is-marked` нигде нет, автопрокрутки у `<ul>` тоже.

Седьмым нажатием стрелки подсветка уезжает за нижний край, и дальше человек
жмёт Enter вслепую. План на этом держит весь жест различения тёзок дословно:
«однозначность держится ровно на том, что подсветку видно». Сейчас она видна
только у первых шести.

Чинить: в `keydown` после сдвига `marked` — `queueMicrotask` с
`element.scrollIntoView({ block: 'nearest' })` по ссылке на подсвеченную строку
(`bind:this` в `{#each}`), либо ограничить выдачу тем, что помещается.

**6. Всплывающий постер не переживает отсутствие обложки.**

`client/components/Picker.svelte:146-150` — голый `<img>` без `onerror`.
`bridge/serve.py::_poster` на карточку без обложки отвечает `404` и прямо в
комментарии называет договор проекта: «на месте обложки заглушка, и делает её
`onerror` у картинки»; `client/components/Poster.svelte:24` его и соблюдает.

Условие показа — `hovered?.hint_item_id`, то есть «связанная карточка есть», а
не «обложка есть»: у карточки, заведённой руками без постера, номер будет, а
байтов нет. Тогда за курсором таскается рамка 120×180 с битой картинкой внутри —
при том, что план требует обратного: «не приехал — строка живёт дальше, ничего
не двигая».

Чинить: `onerror={() => { hovered = null }}` (или свой признак), либо показывать
`Poster.svelte`, у которого это уже написано.

**7. Переименование `entity_id` → `id` разойдётся с задачей 4 молча.**

`client/components/Picker.svelte:73,82` кладут в выбранное `{ id, name }`, а
план задачи 4 (`docs/plans/2026-07-31-card-window.md:1210`) пишет состав так:

```js
const entity_id = one.entity_id
  ?? await call('refs.create_person', domain, one.name)
```

`one.entity_id` теперь `undefined` **у всех** — и у выбранных из подсказки тоже,
— то есть `??` уйдёт вправо и заведёт нового человека на каждое сохранение.
Ошибка тихая: связи проставятся, карточка сохранится, а в справочнике заведётся
второй Дени Вильнёв, потом третий. Само переименование верное и объяснено
(`hinted`, строки 47-51) — поправить надо план, пока задача 4 не начата.

### Minor (Nice to Have)

**8. Отбор жанров и отбор имён ищут по-разному.**
`CardModal.svelte:43-45` берёт `name.toLowerCase().includes(...)`, а
`CreditsRepository._name_starts_with` — префикс по свёрнутому имени. Одно и то же
поле на «ов» покажет все жанры со слогом внутри, но ни одного Иванова. Само по
себе не поломка, но поведение поля зависит от того, кто его наполняет, а
компонент об этом различии не знает.

**9. `typedGenre` не сбрасывается после выбора.**
`CardModal.svelte:107` — `ontype` только пишет, а `clear()` внутри `Picker`
чистит своё `text`, до `typedGenre` не дотягиваясь. Поле пустое, а `matching`
всё ещё сужен последним набранным. Сегодня это не видно только потому, что
`open` уже `false`, — то есть держится на находке 2, которая как раз и позволяет
в этот список залезть стрелками.

**10. `follow` меряет вёрстку на каждый `mousemove`.**
`Picker.svelte:108-114`: `getBoundingClientRect()` плюс запись нового объекта в
`at` сто с лишним раз в секунду. Коробка `.picker` за время наведения не
двигается — хватило бы `onmouseenter` с одним замером и слежения только за
точкой.

**11. `Field` роняет обработчики у абзаца молча.**
`Field.svelte:20-28`: `oninput`, `onkeydown`, `onfocus`, `onblur` подставлены
только в ветку `<input>`; у `area` их не примет никто и не скажет об этом. Пока
потребитель один, но следующий `Field area` с обработчиком отладится не сразу.

**12. Ответ `refs.genres` может приехать в закрытое окно.**
`CardModal.svelte:35-39`: закрыли окно на неотвеченном запросе, запрос сорвался —
`lost` покажет плашку «Не удалось прочитать список жанров» поверх приложения, из
которого это окно уже ушло.
