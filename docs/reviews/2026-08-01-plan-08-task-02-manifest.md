## Strengths

**Перенос значений точен.** Все три файла оформления совпадают с макетом
объявление в объявление. Единственные подмены — литерал на токен той же
величины, и все восемь проверены по `palette.css`:

| Макет | Проект | Значение |
|---|---|---|
| `#fff` (`.tagrow__name`, `.taggrip i`) | `--text-bright` | `#ffffff` |
| `#0a0a0a` (`.tagbox[data-state]`) | `--bg` | `#0a0a0a` |
| `rgba(255,255,255,.25)` | `--tint-25` | то же |
| `rgba(255,255,255,.55)` | `--tint-55` | то же |
| `rgba(255,255,255,.3)` | `--tint-30` | то же |
| `rgba(255,255,255,.14)` | `--tint-14` | то же |
| `#ef4444` | `--exclude` | `#ef4444` |
| `color-mix(in srgb, var(--primary) 14%, transparent)` | `--fill-primary-14` | то же |

Расхождений по величине нет ни одного. Цвета по месту нет ни одного.
`<style>` внутри компонента нет ни одного. Двух красных — `--error` `#ff4a45`
у беды и `#ef4444` у исключения — макет и правда держит порознь
(`docs/design/styles/tokens.css:27` против `index.html:1401`), комментарий в
палитре не врёт.

**Шесть раз исполнитель предпочёл макет плану, и все шесть раз был прав.** План
задачи 2 разошёлся с макетом, реализация пошла за макетом:

1. Порядок узлов строки. План (`plan:739-757`) ставил `TagBox` последним, после
   имени и крестика; макет (`makeRow`, `index.html:2146-2160`) — вторым, сразу
   за ручкой. `TagRow.svelte:10-29` — как в макете.
2. Глиф удаления. План — `close`, макет — `delete` (`index.html:2158`).
3. Подпись удаления. План — «Удалить», макет — «Удалить тег»
   (`index.html:2157`).
4. Признак пустой звезды. План вешал `is-empty` на обёртку
   (`plan:777`), макет — прямо на глиф (`index.html:2897-2898`); с обёртки
   правило `.scorerow__stars .material-symbols-outlined { 'FILL' 1 }` не
   перебилось бы, и комментарий в `ScoreRow.svelte:17-19` это записывает.
5. Носитель `--score`. План ставил его на `<li>` (`plan:773`), макет — на
   `.scorerow` (`index.html:2901`).
6. Строка ввода. План брал `color: var(--text)` и одно правило
   `::placeholder` (`plan:659-664`); макет (`index.html:1059-1080`) —
   `--text-bright` плюс `:hover::placeholder` и `:focus::placeholder`. В
   `newtag.css:21-37` перенесено всё пять правил.

Плюс `field.focus()` после отправки (`NewTag.svelte:21`) — есть в макете
(`index.html:2951`), в плане не было.

**Скрытие системной полосы прокрутки не потерялось.** В макете `overflow-y`,
`scrollbar-width` и `::-webkit-scrollbar` висят на `.taglist`
(`index.html:1258-1261`); в проекте они уехали на `.scrollarea__box`
(`scrollarea.css:14-18`) ещё задачей 1, а потолок высоты остался в `taglist.css`
с комментарием, объясняющим почему. Разъехаться тут было легко — не разъехалось.

**Слои и знание одностороннее (правила 2, 6, 10).** Оформление — в `styles/`,
компоненты — в `components/`, ни один из четырёх не ходит ни в мост, ни в общее
состояние: всё приходит `$props()`. `ScoreRow` берёт `LABELS`/`colorOf` из
`$state/scores.js` — это прямо разрешено решением «компонентам открыт слой
`state/`». Локальное `$state` в `NewTag` — своё значение поля, не общее.

**Правило 7 чисто.** `TagBox` вынесен не «на будущее»: у него сегодня два
потребителя, `TagRow` и `ScoreRow`. Звёзды строки не сведены со `Stars.svelte` —
довод записан в плане и он верный: там десять кнопок с дробной звездой, здесь
неподвижные глифы.

## Issues

### Critical (Must Fix)

#### C1. `.newtag__ok` — третья дословная копия уже вынесенного `.icon-btn`

`client/styles/newtag.css:40-63`.

**Что нарушено:** правило 3 («во фронте не ждут») и правило 8. В проекте есть
`client/styles/iconbutton.css` — круглая кнопка с одним глифом, заведённая ровно
под этот приём, с комментарием «Размер ставит тот, кто применяет: у карточки он
28, у поля поиска 26». У неё три потребителя: `Acts.svelte`, `Film.svelte`,
`SearchField.svelte`. В макете класса `.icon-btn` нет вовсе (`grep` по
`index.html` — ноль вхождений), то есть это собственное решение проекта, а не
перенос, и точность переноса его не отменяет.

`.newtag__ok` совпадает не только с `.icon-btn`, но и с конкретным его
потребителем — `.search__clear` (`search.css:54-63`): тот же размер 26,
`flex: 0 0 auto`, `color: var(--primary)`, `transition: background .15s`,
`font-size: 18px` у глифа, `:hover { background: var(--fill-primary-14) }`.
Повторено восемь объявлений плюс всё правило для вложенного глифа
(`newtag.css:56-62` против `iconbutton.css:15-20`).

**Почему важно:** сейчас в проекте три места, где меняется одно и то же — круг,
размер и центрирование глифа. Правка `iconbutton.css` (например, замена
центрирования межстрочным интервалом на что-то другое) обойдёт две новые кнопки
молча, и разъедутся они не отказом, а видом.

**Как чинить:** в `NewTag.svelte:29` — `class="icon-btn newtag__ok"`. В
`newtag.css` оставить своё:

```css
.newtag__ok {
  --icon-btn: 26px;

  flex: 0 0 auto;
  color: var(--primary);
  opacity: 0;
  transform: scale(.7);
  pointer-events: none;
  transition: opacity .16s, transform .16s, background .15s;
}
.newtag__ok .material-symbols-outlined { font-size: 18px }
.newtag__ok:hover { background: var(--fill-primary-14) }
```

Вид не меняется: `.icon-btn` даёт те же `display: block`, `width`/`height` из
`--icon-btn`, `border-radius: var(--r-full)` и то же правило для глифа.

#### C2. `.tagrow__del` — вторая дословная копия `.icon-btn`

`client/styles/taglist.css:95-115`.

То же самое, что C1, и в том же слайсе: `display: block`, `width: 28px`,
`height: 28px`, `border-radius: var(--r-full)`, а у вложенного глифа
`display: block; width: 28px; line-height: 28px; text-align: center` — это
`.icon-btn` целиком, причём 28 у него значение по умолчанию, объявлять даже
`--icon-btn` не нужно.

**Как чинить:** в `TagRow.svelte:24` — `class="icon-btn tagrow__del"`. В
`taglist.css` оставить:

```css
.tagrow__del {
  flex: 0 0 auto;
  color: var(--tint-30);
  transition: color .16s;
}
.tagrow__del .material-symbols-outlined { font-size: 18px }
.tagrow__del:hover { color: var(--error) }
```

Комментарий «Подложки нет, но скругление держим: по нему идёт рамка фокуса»
переезжает не в `taglist.css`, а исчезает: скругление приходит из
`iconbutton.css`, и там оно уже объяснено. Образец такой правки в проекте есть —
`acts.css:16-17`: «Круг, размер и центрирование глифа приходят из
`iconbutton.css`, подложку с рамкой снимает `base.css`; здесь остаётся своё».

### Important (Should Fix)

#### I1. Сброс кнопки переобъявлен трижды

`taglist.css:66,69,71` (`.tagbox`), `taglist.css:100,101,104,106`
(`.tagrow__del`), `newtag.css:45,46,48,50` (`.newtag__ok`) — одиннадцать
объявлений `padding: 0`, `border: none`, `background: transparent`,
`cursor: pointer`.

**Что нарушено:** правило 3 и правило 8. Всё это уже стоит в `base.css:33-40`
для любого `button`, и комментарий там написан именно про этот повтор:
«Сбрасывалось это порознь семью местами — от капсулы переключателя до имени в
титрах, — и восьмой раз отвести повтор было нечем». Восьмое, девятое и десятое
место заведены этим слайсом.

**Почему важно:** дело не в трёх строках, а в том, что вынос перестаёт
действовать. Комментарий в `base.css` после этого слайса утверждает неправду.

**Как чинить:** снять `padding`, `border`, `background`, `cursor` во всех трёх
блоках. У `.tagbox` остаётся собственная рамка `border: 2px solid var(--tint-25)`
— она не сброс, а вид, её держим.

#### I2. `.newtag__input` дословно повторяет `.search__input`

`newtag.css:21-31` против `search.css:35-45`: совпадают восемь объявлений из
десяти — `flex`, `min-width`, `border`, `outline`, `background`, `font`,
`caret-color`, `user-select`. Различий два: `color` (`--text-bright` против
`--text`) и цвет подсказки.

**Что нарушено:** правило 3. Комментарий `newtag.css:17-20` эту заявку уже
частично признаёт, но адресует её плану 9 («когда план 9 заведёт общее поле,
эти пять правил обязаны уехать туда») — а второе объявление того же блока стоит
в проекте **сегодня**, и не с полем окна карточки, которого нет, а с полем
поиска, которое есть.

**Это заявка, а не решение.** Макет держит их порознь намеренно:
`.field__input, .newtag__input` — один блок (`index.html:1059-1080`),
`.search__input` — другой (у него своя подсказка `--tint-28` и своя
`::-webkit-search-cancel-button`). Свести их значило бы отойти от макета в
структуре, и такое решение принимает пользователь, а не рецензент.

**Как чинить:** один из двух путей, и выбирает его пользователь —
(а) оставить как есть и снять из комментария обещание про план 9, заменив его
записью в `docs/deferred.md`; (б) вынести общее прямо сейчас — например,
`styles/field.css` с общей строкой ввода, откуда и `.search__input`, и
`.newtag__input` берут восемь одинаковых объявлений, а своё оставляют себе.

### Minor (Nice to Have)

#### M1. Комментарий ссылается на одноразовые документы

`newtag.css:17-20`. Три вещи разом: ссылка на макет как на источник
заимствования («В макете эти пять правил объявлены вместе с полями окна
карточки»), ссылка на номер плана («план 9 заводит общее поле») и разметка
`**…**` внутри CSS-комментария.

Правило 11 и решение проекта «не тащить ссылки на источники заимствований». И
`docs/design/`, и `docs/plans/` — папки одноразовые: удалят их, и комментарий
станет указателем в никуда. Полезная часть здесь одна — «поле ввода не должно
оказаться объявлено дважды», и она формулируется без единой ссылки. Замечание
не касается коротких «из макета» в `NewTag.svelte:5,13` — такая формулировка в
проекте уже принята (`state/scores.js:3,10`, `palette.css:68`).

#### M2. Три места без сегодняшнего потребителя

`TagRow.svelte:6` — `ondelete` и `ongrab`; `taglist.css:56-57` —
`.tagrow.is-dragging` и `.taggrip` под ним. Ручку и крестик зажигает задача 4
(«Теги карточки и правка набора»), сегодня их не передаёт никто: `TagRow` вообще
пока не импортирован ни одной сборкой.

Правило 8 формально нарушено, но нарушение санкционировано планом: интерфейс
`TagRow` с `ondelete` и `ongrab` объявлен в задаче 2 прямым текстом
(`plan:472-474`). Записано, чтобы задача 4 действительно их подключила, а не
чтобы они остались висеть: если к концу плана 8 `ongrab` так и не получит
обработчика, ветку и стиль надо снимать.

#### M3. `.tagbox` живёт в файле чужого блока

`TagBox.svelte` — самостоятельный переиспользуемый компонент с двумя
потребителями, а его оформление лежит в `taglist.css` вместе с `.taglist`,
`.tagrow` и `.taggrip`. Прецедент обратного в проекте есть: `.icon-btn` вынесен
в собственный `iconbutton.css` ровно потому, что его применяют разные блоки.

Довод против выноса тоже есть и он неслабый: оба потребителя — строки одного и
того же списка, `ScoreRow` даже рисует `<li class="tagrow">`, то есть `.tagbox`
пока не выходит за пределы блока. Оставлять как есть допустимо; если задача 4
или план 9 поставят переключатель вне списка — выносить.

#### M4. Подпись строки оценки разошлась с макетом

`ScoreRow.svelte:13` передаёт `label={LABELS[score]}`, и вслух строка называется
«Шедевр: включён». В макете `aria-label` собирается из элемента списка, а
элементы у оценок — `['10','9',…]` (`index.html:2165` и `2912`), то есть «10:
включён».

Видимого расхождения нет, расходится только доступное имя. Вариант проекта
осмысленнее, но это уже не перенос, а решение — назвать его стоит.

#### M5. Интерфейс `TagBox` шире объявленного планом

План обещал `TagBox` с входными `state` и `onclick` (`plan:472-473`);
реализация принимает ещё `label` и собирает из него `aria-label`
(`TagBox.svelte:7,16`). Это опять победа макета над планом — там подпись именно
такая, `name + ': ' + BOX_STATES[value].label` (`index.html:2165`), — и она
правильная: без имени «включён» сказано ни о чём.

Записано затем, что задача 3 будет писать сборки по тексту плана, а он про
`label` молчит: не передав его, она получит `aria-label` вида «undefined:
включён».
