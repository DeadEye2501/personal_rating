- **`ops` перестал быть `$state`** — список номеров операций ничего не

### Critical

#### 1. `client/app/LibraryScreen.svelte:21-23` — комментарий утверждает свойство, которого у кода нет (правило 11)

```js
  // Запрос отдельной величиной: прочитанный в эффекте `session` метил бы его
  // грязным на любую пересборку сеанса, а перезапрашивать раздел надо только
  // на смену того, что в запрос входит.
  const asked = $derived(requestOf(session))
```

Вторая половина фразы неверна. `requestOf` возвращает **новый объект** на каждый
пересчёт, а Svelte сравнивает значение производной строгим равенством —
`client/node_modules/svelte/src/internal/client/reactivity/equality.js`:

```js
export function equals(value) {
	return value === this.v;
}
```

Новый объект никогда не равен прежнему, значит производная уведомляет эффект на
**каждую** пересборку сеанса, ровно как и чтение `session` в эффекте. Приём
работает только у соседа: `kind` — примитив, и там сравнение действительно
гасит лишнее.

Наблюдаемое следствие: `withCollapsed` (кнопка «Свернуть всё» в шапке,
`client/app/Topbar.svelte:133`) отдаёт новый `session` → `asked` пересчитан →
эффект `feed.page` перезапрошен с нулевого смещения → `views` заменены первой
полусотней. Человек, прокрутивший ленту на триста карточек и нажавший «Свернуть
всё», получает прыжок к пятидесяти и лишний поход через границу.

Отдельно про то, почему это не поймает шаг 3 плана: в базе разработчика карточек
меньше пятидесяти, и перезапрос возвращает тот же список — глазами не видно
ничего. Свойство наблюдается только на второй странице.

Чинить одним из двух:

- сравнивать содержимое, а не ссылку: держать производной **строку**
  (`JSON.stringify` от запроса или явный ключ из раздела, типа, фильтров и
  позиции сортировки) и собирать сам запрос уже внутри эффекта;
- либо признать перезапрос на любую пересборку сеанса ценой, убрать
  производную вовсе и **переписать комментарий на правду** — сегодня он
  защищает решение, которого в коде нет.

Второе честнее только вместе с записью в `docs/deferred.md`: сегодня
пересборок сеанса шесть, и «Свернуть всё» среди них.

### Important

#### 2. Повтор: запрос ожидаемых источников списан дословно

`client/app/LibraryScreen.svelte:28-32` против
`client/app/SearchScreen.svelte:28-32` — пять строк совпадают посимвольно,
включая имя канала:

```js
  $effect(() => {
    numbered('world.expected', kind, { channel: 'expected', ops })
      .then((sources) => { expected = sources })
      .catch(lost)
  })
```

Плюс `let expected = $state([])` и производная `kind` с комментарием о том же
самом, написанным дважды разными словами. Машинная проверка дублей `.svelte` не
разбирает вовсе, так что второго сторожа тут нет.

На HEAD совпадения не было: у библиотеки стоял черновик с литералом `'movie'`,
без `ops` и без обработчика. Слайс довёл его до копии соседа — то есть повтор
завёл именно он, и правило 3 требует выноса сейчас.

**Какое объявление должно остаться:** ни одного из двух. `expected` зависит
только от `session.kind`, а `session` принадлежит `client/app/App.svelte` —
туда и просится: одна производная, один эффект, `expected` уезжает разделам
входным параметром рядом с `session` и `query`. Побочно уходит лишний поход
через границу на каждую смену раздела: `{#key session.section}` сегодня
пересоздаёт экран и спрашивает `world.expected` заново, хотя тип не менялся.

#### 3. Повтор: обработчик отказа — и он же врёт про записи

`client/app/LibraryScreen.svelte:44-48` против
`client/app/SearchScreen.svelte:42-46`:

```js
  function lost(error) {
    if (error.silent) return
    console.warn('раздел библиотеки', error)
    ontrouble('Не удалось прочитать библиотеку')
  }
```

Различаются двумя литералами. Третье, неполное появление идиомы — `quietly` в
`client/app/visible.js:51-60` (там без плашки).

К повтору прицеплена вторая беда, и она серьёзнее самого повтора. Один
обработчик обслуживает и чтения, и **записи** — `score`, `aspect`, `wish`
уходят в него через `.catch(lost)` в разметке (`LibraryScreen.svelte:106-108`).
А комментарий над записями (`LibraryScreen.svelte:67-68`) обещает обратное:

> Отказ у них показывается плашкой, а не гасится — человек должен знать, что
> оценка не сохранилась.

Человек узнает, что «Не удалось **прочитать** библиотеку». Плашка называет не то
действие, и снова правило 11: комментарий описывает намерение, а не код.

**Какое объявление должно остаться:** одно, с местом и текстом параметрами —
`app/trouble.js` с `reporting(tag, text, ontrouble)`, отдающим готовый
обработчик. Прецедент в проекте есть: `parsed()` в бэкенде вынесен ровно так,
с `logger` доводом, «чтобы запись осталась на месте вызова». У записей при этом
обязан быть свой текст («Не удалось сохранить оценку»), иначе вынос закрепит
неправду.

#### 4. Повтор: «своё сильнее общего» объявлено дважды

`client/app/LibraryScreen.svelte:92`:

```js
  const collapsedOf = (view) => view.collapsed ?? session.collapsed
```

`client/components/Feed.svelte:72`:

```svelte
      <Film {view} collapsed={view.collapsed ?? collapsed} {expected}
```

Одно правило, две записи, и над каждой свой комментарий о том, что тумблер шапки
— состояние приложения, а шеврон — свойство карточки (`LibraryScreen:88-89` и
`Feed:69-71`). Два комментария об одном и том же — обычный признак того, что
решение списано, а не вынесено.

Цена расхождения наглядна: пока слайс не написал `collapsedOf`, эти две записи
уже разошлись — в плане стояло `!view.collapsed`, и щелчок шеврона при
включённом «Свернуть всё» не делал ничего. Один раз разойтись уже успели.

**Какое объявление должно остаться:** одно, в `state/` — правило чистое, над
обычными данными, и по решению проекта проверяется именно этот слой
(`clean.json` открывает `state` и компонентам, и сборке). Сегодня у правила нет
ни одного теста ни с одной стороны.

#### 5. Повтор: «та же строка списка» объявлена трижды, и по двум разным ключам

- `client/app/LibraryScreen.svelte:96-99` — `patch`, ключ `item_id`;
- `client/app/SearchScreen.svelte:97-101` — `replace`, ключ `source` +
  `source_id`;
- `client/components/Feed.svelte:65` — ключ `{#each}`, снова `source` +
  `source_id`.

Тела `patch` и `replace` — один `views.map` с одним тернарником; `shown`
(`LibraryScreen:62-65`) и `shownCard` (`SearchScreen:105-108`) вокруг них
совпадают построчно, отличаясь ровно вызовом замены.

Разные ключи здесь не выдумка: у кандидата поиска нет `item_id`. Но из этого
следует не «пусть будет три записи», а «идентичность строки ленты — одно
понятие, и жить ему в одном месте»: `keyOf(view)` в `state/`, отдающая
`item_id`, когда он есть, и пару «источник плюс идентификатор», когда нет.
Тогда `patch` остаётся один на оба экрана, `Feed` берёт ту же функцию ключом
`{#each}`, а `shown`/`shownCard` схлопываются в одно тело.

Проверено, что сегодня ключи не спорят: ручная карточка получает `source_id`
из `uuid4` (`backend/model/item.py:37-41`), так что столкновения ключей
`{#each}` в библиотеке не бывает. То есть это повтор понятия, а не поломка.

## Что повтором не является

Разобрано и отведено, чтобы следующий проход не начинал сначала:

- **`const ops = []` и `$effect(() => () => { cancel(ops.splice(0)) })`** в двух
  экранах. Одна строка, и она — владение: каждый экран гасит то, что начал сам.
  Вынос потребовал бы помощника, который прячет владение, а короче строки не
  станет.
- **`let views = $state([])`** в двух экранах. Совпало объявление пустого
  списка, предметы разные: у библиотеки это страница базы, у поиска — склейка
  двух выдач, которую фильтрует `passes`.
- **Два экрана как таковые.** Слить `LibraryScreen` и `SearchScreen` в один с
  переданным способом загрузки нельзя тем же доводом, каким проект уже отвёл
  `CardWriter ≠ Linker`: разница — не флаг, а половина тела. Правильный ответ
  — вынести совпавшие куски (находки 2–5), а экраны оставить два.

Записать это в `docs/not-duplicates.md` не получится: `places()` считает
стороной только `путь.py:Объявление` — см. `docs/deferred.md:648-656`. Значит
место записи — `docs/deferred.md`, разделом про задачу 6.
