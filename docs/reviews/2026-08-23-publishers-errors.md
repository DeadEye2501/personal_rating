# Ревью: регистр, издательства, отсев синглов — ошибки поведения, тесты, манифест

Измерение — ошибки поведения на живых данных, качество новых сторожей,
манифест. Пишется по ходу.

Проверяемое: незакоммиченная правка, три работы —
1) правило регистра (`backend/naming.py` + семь дверей записи),
2) правило издательств (`backend/publishers.py`, `storage/entity.py`,
   `credits.py:_written_alike`, `google_books/parse.py:named`),
3) отсев синглов (`deezer/parse.py:parse_albums`).

Всё, что ниже помечено «проверено пробой», подтверждено запуском: временный
файл `tests/backend/test_zzprobe.py`, снесён после проверки.

## Critical

### C1. Отсев синглов гасит догрузку музыки: вторая порция не приедет никогда

**Место:** `backend/sources/deezer/parse.py:parse_albums` против
`backend/service/search.py:_has_more`.

`_has_more` считает «есть ещё» по длине **сырой выдачи источника**, и его
докстринг это прямо оговаривает: «Считается по сырой выдаче, до всякой чистки:
из двадцати строк отсев нерелевантного, снятие убранного и склейка изданий
оставляют меньше, и короткая порция после них означает „почистили“, а не
„кончилось“».

Отсев синглов встал **внутрь разборщика**, то есть выше этой границы: до
`_has_more` доезжает уже почищенная порция.

**Проверено пробой.** Двадцать строк, из них семь `record_type: "single"` —
ровно то соотношение, что замерено автором по «дельфин»:

```
PARSED: 13 of 20
HAS MORE: False
```

**Когда проявится:** на любом поиске музыки, где Deezer вернул хоть один сингл
в первой двадцатке. По собственному замеру автора это 7 из 20 — то есть почти
всегда. Лента показывает 13 строк и больше ничего не грузит; альбом, лежащий на
второй странице, недостижим **ничем**.

Это тот же дефект, ради которого слайс 2 заводил `startIndex`/`page`: единственная
строка, ради которой делалась догрузка, снова не наблюдается ничем. Ни один тест
не гоняет `parse_albums` на полной двадцатке — все три фикстуры Deezer обрезаны
до 4–5 строк (`search_album_kino` 4, `search_album_page2` 5,
`artist_albums_kino` 5), так что связка «отсев → полнота порции» не сторожится.

Страница на это же и рассчитывает — `client/app/SearchScreen.svelte:portion`:
«Конец называет источник, а не длина списка: из двадцати строк отсев
нерелевантного и снятие убранного оставляют меньше, и считать по показанному
значило бы вставать на первой же убранной строке». Отсев синглов ровно это и
делает, только на шаг раньше, где обмануть нечего.

**Где чинить (заявка, не решение):** отсев вне разборщика — там же, где стоят
остальные чистки (`_narrowed`), либо признак «есть ещё» считать до отсева.

### C2. Издательство с пустым ключом заводит новую строку на каждую книгу

**Место:** `backend/storage/repository/credits.py:_written_alike` +
`backend/publishers.py:alike`.

`ensure` для студий больше **не ищет точного совпадения имени вовсе**: ветка
`find_anonymous_by_name` заменена на `_written_alike`, а `alike` первым делом
отвечает `False`, если приведение любой из сторон пусто.

Приведение пусто у всего, что `flattened` вычищает целиком, — то есть у любого
имени вне латиницы и кириллицы, — и у имени, целиком состоящего из служебных
слов.

**Проверено пробой** (одна и та же строка, дважды подряд):

```
studios.ensure(Credit(name="講談社", ...))  -> 1
studios.ensure(Credit(name="講談社", ...))  -> 2   # две строки на одно имя
```

**Когда проявится:**

- японские, китайские, корейские, греческие, ивритские, арабские издательства
  Google Books («講談社», «岩波書店», «Εκδόσεις Πατάκη» — все дают пустой ключ,
  проверено);
- **студии игр из магазинов**: `sources/convert.py:companies` отдаёт их голыми
  строками без идентичности, то есть они идут этой же дверью — и любое их имя
  вне латиницы и кириллицы получит тот же пустой ключ. Названий из магазинов я
  не мерил, в отличие от книжных;
- издательство, названное одним служебным словом: `Media`, `Press`, «Дом»,
  `Books` — ключ пустой, проверено.

Каждая карточка заводит свою строку студии. Клик по студии показывает одну книгу
из десяти, а список студий растёт линейно по карточкам.

Регрессия: до правки эти имена склеивались точным сравнением
(`find_anonymous_by_name`, регистронезависимым). Комментарий
`sources/convert.py:companies` — «таких склеивают по имени» — с этой правки
неправда.

### C3. `Vintage Books` и `Vantage Press` — одна строка в базе

**Место:** `backend/publishers.py:_same_bones`.

Костяк согласных при равном числе гласных склеивает два **разных настоящих
издательства**: `vintage` (Penguin Random House) и `vantage` (Vantage Press).
Костяк `vntg` совпадает, гласных по три, длина 7 ≥ `LEAST_BONES`.

**Проверено пробой** — через боевой `ensure`, а не только через `alike`:

```
Vintage Books -> 1
Vantage Press -> 1     # вторая книга уехала к чужому издателю
```

**Когда проявится:** на любой книге Vantage Press, если в базе уже есть книга
Vintage Books (или наоборот). Правило `_same_bones` заменяет **любую** гласную
на любую другую, поэтому пара «одна гласная различает два имени» склеивается
всегда, начиная с шести букв. Замер, на который ссылается модуль, шёл по 111
написаниям одной выдачи и такой пары в нём не было — цена правила не в том, что
оно ошиблось на замере, а в том, что замер её не покрывает.

Отдельно: `test_the_list_of_exceptions_does_not_touch_the_rest` прямо
утверждает `alike("Vintage", "Vintage Books")` — то есть `Vintage` в тестах уже
есть, а его двойник — нет.

## Important

### I1. Правило издательств применяется ко **всем** безымянным студиям, а замерено на книжных

**Место:** `backend/storage/entity.py` — `COMPANIES = Entity(..., alike=alike)`.

Идентичности нет ни у одной студии магазинов: `sources/convert.py:companies`
отдаёт их голыми строками, `oldgames/parse.py:_companies` тоже. Значит через
`_written_alike` с книжным правилом проходят **разработчики и издатели игр**, а
у TMDB студий не бывает вовсе — то есть безымянная половина таблицы это игры
плюс книги, и правило, замеренное на 111 книжных написаниях, решает и про игры.

Проверено перебором 107 правдоподобных имён (издательства русские и английские,
студии и издатели игр, 5671 пара): ложная склейка ровно одна — та самая
`Vintage`/`Vantage` из C3. То есть **правило в целом консервативно**, и находка
не в частоте, а в том, что область его действия шире области замера, и это
нигде не оговорено: докстринг `Entity.alike` говорит только про издательства.

### I2. Цена поиска: 205 мс на одну студию при двух тысячах строк

**Место:** `credits.py:_written_alike`.

Докстринг утверждает: «Строки читаются все, и это дёшево: студий у карточки
одна-две, а всего их в базе сотни».

**Проверено пробой.** 2000 безымянных студий в базе, 20 вызовов `ensure`:

```
20 ensure over 2000 rows = 4.093s (204.6 ms each)
```

То есть цена линейна по числу студий и платится **на каждую студию каждой
карточки**. Сотни строк — это ~50 мс на студию; библиотека из тысячи игр даёт
до двух тысяч безымянных студий (разработчик + издатель на игру), и там уже
0.4 с на сохранение игры только за поиск студий.

Умножается это дважды на пустом месте:

- `alike(row.name, name)` пересчитывает `publisher_key(name)` — **ключ
  спрошенного** — заново на каждой строке таблицы;
- `_steps` — динамика O(n·m) с выделением таблицы на пару, и зовётся она до
  дешёвой проверки костяка.

Разложено замером: из 204.6 мс на вызов **203.5 мс — это питон, а не SQL**.
Внутри питона ключи стоят 24.7 мс на 2000 строк, остальные ~180 мс — динамика
`_steps`, то есть 102 мкс на строку таблицы. Дешёвая проверка костяка при этом
стоит после дорогой.

Оценка «студий сотни» верна для книг и неверна для игр; это тот же случай, что
«клик по исполнителю привозил четверть работ» — цена посчитана по тому
сценарию, на котором проверяли живьём.

### I3. `alike` — не отношение эквивалентности, а `_written_alike` берёт первого по номеру

**Место:** `credits.py:_written_alike`, докстринг: «Первый по номеру, а не
ближайший: если написание близко к двум разным записям, значит эти две записи
близки и между собой, то есть уже слились бы при заведении второй».

Утверждение неверно: порог `min(len(left), len(right)) // PER_EDIT` зависит от
**длины пары**, поэтому близость нетранзитивна.

**Проверено пробой:**

```
A = "abcdefghijklmnop"   B = "abcdefghijklmnzz"   C = "abcdefghijklzzzz"
A~B True   B~C True   A~C False
```

Следствие: если в базе уже лежат A и C (правильно раздельные), то B прилипнет к
тому из них, кто заведён раньше, — а не к тому, чьим написанием является. Тот же
класс, что транзитивность в склейке игр, которую проект уже ловил 03.08.2026 на
`Worms 2`.

Дешёвая правка замысла, если решать: брать **ближайшего**, а не первого.

### I4. Шесть слов в `FORMS`/`WORDS` не срабатывают никогда, и латинские имена коверкаются

**Место:** `backend/publishers.py:_as_russian` + `FORMS`/`WORDS`.

Комментарий над `FORMS` объявляет порядок «сперва письменность, потом шелуха»
решением и называет только его пользу. Обратная сторона не названа: `_as_russian`
переводит в кириллицу **любое** слово, целиком набранное буквами-двойниками, а
шесть из двенадцати таких букв обратной транслитерацией дают **другую** букву:
`c→s`, `h→n`, `p→r`, `x→h`, `b→v`, `y→u`.

**Проверено пробой.** Записи, которых приведение не встретит никогда:

```
ab -> av      book -> vook    co -> so
oy -> ou      pao -> rao      pty -> rtu
```

и настоящие имена, которые от этого коверкаются:

```
Hachette               -> nasnette
Jonathan Cape          -> jonathan sare
Focus Home Interactive -> focus nome interactive
Bay Books              -> vau
Thomas Cook            -> thomas sook
```

Само по себе коверканье устойчиво (одно имя коверкается одинаково), но мёртвые
слова дают **настоящие расхождения одного издательства**, проверено:

```
alike("Doubleday & Co", "Doubleday")            -> False
alike("Allen & Unwin Pty Ltd", "Allen & Unwin") -> False
alike("Peter Book", "Peter Books")              -> False
```

**Когда проявится:** у любого издательства, где форма собственности или слово
`Book` записаны латиницей и стоят отдельным словом из одних двойников. `Pty Ltd`
у австралийских, `& Co` у старых американских — обычные написания Google Books.

### I5. Комментарии обещают склейку по имени там, где её больше нет

**Место:** `backend/sources/convert.py:companies` — «Магазины отдают студии
голыми строками: идентичности у них нет… **таких склеивают по имени**»;
`backend/sources/google_books/parse.py:parse_card` — «Таких склеивают по имени,
как студии магазинов».

С этой правкой студий по имени не склеивает никто: `ensure` для `COMPANIES`
ходит только через `_written_alike`. Оба комментария описывают снятое поведение
— и второй ещё и ссылается на первое как на образец. Правило 11.

## Качество новых сторожей

### T1. Сторож «правило издательств людей не касается» не может упасть

**Место:** `tests/backend/test_publishers.py:test_two_people_with_alike_names_are_not_merged`.

Тест берёт «Пресс» и «Пресс Медиа» и требует разных строк. Но у обоих имён
приведение **пусто** (`пресс` → `press` → служебное слово), и `alike` отвечает
`False` на пустой ключ раньше всякого сравнения:

```
'Пресс'       -> ''
'Пресс Медиа' -> ''
alike -> False
```

То есть впиши кто-нибудь `PEOPLE = Entity(..., alike=alike)` — тест останется
зелёным, а тёзки-транслитерации начнут склеиваться. Свойство, названное его
собственным докстрингом, не наблюдается ничем.

**Пара, которая падала бы** (проверено): `alike("Иванов", "Ivanov") is True`,
`alike("Иванов, ООО", "Иванов") is True` — ровно те два случая, которые докстринг
теста и называет.

### T2. Сторож «разные издательства не встречаются» читает ключ, а не поведение

**Место:** `tests/backend/test_publishers.py:test_different_publishers_do_not_meet`.

Он сравнивает `publisher_key(a) != publisher_key(b)`, а решает про склейку
`alike`, и равенства ключей она не требует — в том и смысл `_steps` и
`_same_bones`. Тело теста `alike` не зовёт вовсе, поэтому **никакая** правка
порога, костяка или `PER_EDIT` его не уронит. Правило 13: наблюдается
промежуточное объявление, а не следствие.

Тот же разрыв у `test_one_publisher_in_two_spellings` — но он безвреден:
равенство ключей склейку влечёт.

### T3. Два теста — один и тот же

`test_a_short_name_one_letter_apart_is_another_publisher` целиком повторяет
объединение двух соседей:

- `test_an_added_vowel_makes_another_name` → `not alike("The Planet", "Planeta Publishing")`
- `test_a_short_name_is_not_recognised_by_its_bones` → `not alike("АСТ", "АСТА")`

и не добавляет ни одной новой проверки. Правило 3.

### T4. Восемь тестов из четырнадцати импортируют внутри тела

`from backend.publishers import alike` повторён в теле десяти тестов при том,
что `named` и `publisher_key` импортированы сверху. Тот же приём в
`test_naming.py`. Косметика, но повтор десятикратный.

## Minor

### M1. Строка, целиком состоящая из служебных слов, всё-таки заводит студию

`named` отбрасывает часть с пустым приведением — но только когда частей
несколько. Если пустая часть одна, срабатывает запасной выход
`tuple(kept) or (raw.strip(),)`, и наружу уезжает ровно то, что правило
объявило не издательством. Проверено:

```
named("ООО")          -> ('ООО',)
named("Издательство")  -> ('Издательство',)
named(",,,")           -> (',,,',)
named("  ,  ;  ")      -> (',  ;',)
```

Докстринг `named` при этом говорит: «Отдельно стоящая форма собственности
отбрасывается». Отдельно стоящая **среди других** — да; отдельно стоящая
**сама по себе** — нет. Плюс к C2: у всех четырёх ключ пуст, значит каждая
такая книга заводит свою строку.

### M2. `"the"` в `WORDS` не срабатывает никогда

`flattened` снимает артикли (`ARTICLES = {"the", "a", "an"}`) до того, как
приведение доходит до `WORDS`. Запись мёртвая — правило 8.

### M3. Союз склеивает и настоящий перечень

`_JOINED` смотрит на всю строку, поэтому один союз где угодно отменяет разбор
целиком. Проверено:

```
named("ЛитРес, АСТ и Эксмо")          -> ('ЛитРес, АСТ и Эксмо',)
named("Simon and Schuster, Penguin")   -> ('Simon and Schuster, Penguin',)
```

Три издательства (или два) становятся одной студией с запятой в имени.
Докстринг называет цену только для «Манн, Иванов и Фербер».

### M4. Косая черта режет имя издательства

`_SEPARATORS` включает `/`, и `named("Simon & Schuster/Paula Wiseman Books")`
даёт два издательства. Это правильный разбор для импринта и неправильный для
имени с чертой внутри. Стоит рядом с уже названной ценой двоеточия.

Хорошая новость на том же месте: `named("Bilingua/Билингва")` даёт две строки,
но `alike` сводит их в одну запись, а повторную связь гасит
`on_conflict_do_nothing` — двойной привязки не выходит.

### M5. Имя студии в базе — то, что прислал **первый** источник

При склейке побеждает строка, заведённая раньше. Книга, у которой Google
прислал `Izdatel'stvo ACT`, навсегда закрепит это написание за издательством, и
десять следующих книг с честным «АСТ» покажут человеку транслитерацию. Правилом
это не разбирается нигде, и поправить видимое имя нечем.

### M6. Порядок импортов

`from backend.naming import capitalized` стоит **до** `from backend.model import …`
в `backend/service/hits.py` и после `backend.storage.entity` в
`backend/storage/repository/library.py`. Ruff по умолчанию `I001` не считает, так
что это не отказ хука — но в обоих файлах остальные импорты отсортированы.

### M7. Докстринг обещает пять дверей, проверяет четыре

`tests/backend/test_naming.py:test_a_person_a_studio_a_track_and_a_tag_are_stored_the_same_way`
— «Пять дверей записи», а в теле их четыре (человек, студия, тег, трек).
Карточка проверяется отдельным тестом; рецензия (`ratings.set_review`) и запись
убранного (`removed.remember`) не проверяются нигде — см. таблицу мутаций ниже.

## Манифест

**Правило 2 (место) — держится.** `naming.py` и `publishers.py` в корне пакета
по тому же доводу, что `titles.py`, `unique.py`, `language.py`: приём нужен и
источникам, и хранилищу, а источники в хранилище не ходят. Проверено по
потребителям: `publishers` зовут `sources/google_books/parse.py` и
`storage/entity.py` — то есть обе стороны границы, и общего места кроме корня у
них нет.

**Но докстринг `naming.py` называет потребителя, которого нет.** «Приём нужен и
хранилищу, **и мосту**» — в `bridge/` нет ни одного упоминания `backend.naming`.
Потребители: пять репозиториев и `service/hits.py`. Правило 11.

**Правило 6 (одна ответственность) — на грани, и «и» стоит прямо в докстринге:**
«Издательство книги: как его пишут **и** как его узнавать». Внутри два разных

названия живёт в `titles.py`, а решение «кто с кем одна игра» — в
`service/merging.py`.

издательством, тем же `publisher_key` — «Проверяется тем же приведением, а не
своим списком, иначе два места знали бы одно и то же». Отвожу как заявку, а не
как находку: решать должен тот, кто писал.

### I6 (Important). Список исключений отменяется любым лишним словом

**Место:** `backend/publishers.py:publisher_key` — `if latin in KEPT_WHOLE`.

Проверка идёт на **точное равенство** приведённой строки, поэтому исключение
работает ровно на трёх написаниях и рассыпается от любого добавленного слова.
Проверено:

```
'Penguin Group'      -> 'penguin group'   (исключение сработало)
'Penguin Group LLC'  -> 'penguin'         (исключение мимо)
'Signal Books'       -> 'signal books'
'Signal Books Ltd'   -> 'signal'
'Ardis Publishers'   -> 'ardis publishers'

alike("Penguin", "Penguin Group")     -> False   (как задумано)
alike("Penguin", "Penguin Group LLC") -> True    (то, что задумано не допускать)
alike("Signal",  "Signal Books Ltd")  -> True
```

Форма собственности снимается **после** сверки со списком, а сверяется вся
строка целиком — значит `Penguin Group LLC` в список не попадает и обрезается
как обычное имя. По замеру `Penguin` и `Penguin Group` — разные издательства,
то есть склейка ложная, и заводит её ровно то написание, которое чаще всего
приезжает от Google.

`Ardis Publishers, Inc.` этой беды избегает случайно: `named` режет строку по
запятой раньше, и до `publisher_key` доезжает `Ardis Publishers`. У
`Penguin Group LLC` запятой нет.

### M9. `capitalized` иногда меняет **длину** строки, а иногда не срабатывает вовсе

`text[0].upper()` у части символов даёт не одну букву, а две. Проверено:

```
'ßeta'      -> 'SSeta'      (длина изменилась)
'ﬁnal cut'  -> 'FInal cut'  (лигатура ﬁ развернулась в FI)
```

Лигатуры `ﬁ`/`ﬂ` в названиях Google Books встречаются — это набор, а не
опечатка, — и «ﬁnal cut» превращается в «FInal cut» с заглавной `I` посреди
слова. Правило при этом объявлено как «поднимается ровно первая буква».

Обратная сторона: если первый символ не буква, правило молча не применяется
вовсе:

```
'«тихий дон»' -> '«тихий дон»'
'"quoted"'    -> '"quoted"'
' пробел'     -> ' пробел'
```

Строку никто не обрезает при записи (`create` не зовёт `strip`, в отличие от
`find_anonymous_by_name`, который обрезает искомое), так что имя с ведущим
пробелом ложится в базу как есть и заглавной не получает. Последнее старше этой
правки.

Скорее всего так и задумано — вставил ссылку, значит хотел именно её, — но

### T5. Порог костяка `LEAST_BONES` не наблюдается ничем, а его тест смотрит не туда

`LEAST_BONES = 6` → `3` оставляет все 35 проверок зелёными.
`test_a_short_name_is_not_recognised_by_its_bones` объясняет число так: «„Дом“ и
„Дым“ — тот же костяк и то же число гласных, а издательства разные. Правило
включается с шести букв».

До костяка эта пара не доходит вовсе. Проверено:

```
publisher_key("Дом") -> ''     (dom — служебное слово, оно в WORDS)
publisher_key("Дым") -> 'dym'
```

`alike` отвечает `False` на пустом ключе за две проверки до костяка. Вторая
половина теста (`АСТ` / `АСТА`) держится на **разном числе гласных**, а не на
длине. Значит порог, подобранный замером, не сторожит ни один тест, и пример,
которым он объяснён, работает по другой причине.

Заодно это ещё один случай C2: настоящее издательство «Дом» ключа не имеет вовсе.

### T6. Первое правило замера — имя в кавычках — не наблюдается ничем

проверок зелёными, включая `test_a_name_in_quotes_is_the_whole_name`. Причина
та же: оба его примера разбираются и без кавычек, служебными словами.

```
без выделения кавычек:
  'Издательский дом "Питер"' -> 'piter'
  'Izd-Vo "Mik"'             -> 'mik'
  alike("Питер", 'Издательский дом "Питер"') -> True
  alike("Mik", 'Izd-Vo "Mik"')               -> True
```

Пара, которая падала бы, — имя в кавычках, вокруг которого стоит **не**
служебное слово: у замера такие были («имя в кавычках берётся целиком: кавычки
для того и стоят»), в тесте — нет.
