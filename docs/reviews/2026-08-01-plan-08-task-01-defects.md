Проверялось против макета (`docs/design/index.html:1244-2016`) и против плана
(`docs/plans/2026-07-31-filters-and-stats.md`, задача 1; `2026-07-31-card-window.md`
для будущих потребителей). Две находки подтверждены чтением исходников Svelte
5.56.8 в `client/node_modules/svelte` и компиляцией `Modal.svelte` компилятором
проекта (вывод не сохранялся, дерево не менялось).

**Ни `Modal`, ни `Scrollarea` пока никем не смонтированы** — потребителей нет ни

и план 9). Серьёзность проставлена по природе дефекта, а не по тому, что он
сейчас спит.

## Strengths

- **Отрицательный исход у `thumbOf` явный.** `null` вместо «нулевого ползунка»
  снимает целый класс ошибок: `class:is-shown={thumb !== null}` и
  `pointer-events: none` у скрытой полосы вместе гарантируют, что перетаскивание
  не начнётся там, где прокручивать нечего.
- **Деление на ноль в `thumbOf` невозможно по построению**: ранний выход
  `total <= visible` закрывает и `total - visible === 0`, и `visible === 0`
  (непроложенная область даёт `0 <= 0`).
- **Отказ от `mine` в эффекте обоснован верно.** Компиляция подтверждает:
  `$.event('keydown', $.window, escaped)` ставится синхронно в теле компонента, а
  `$.user_effect` — только на сбросе. Между созданием и первым сбросом окно
  действительно уже ловит Escape, и комментарий на строке 17-18 не врёт.
- **Наблюдение за детьми — правка сверх плана и в нужную сторону.** План смотрел
  только на `box`, а он упёрт в свой потолок и на смену содержимого не отзывается
  вовсе.
- **`overlay` закрывается по цели, а не по всплытию**, и это защищает от того,
  чтобы `stopPropagation` внутри окна ломал делегирование Svelte.

## Issues

### Critical (Must Fix)

#### 1. `scaleOf` неверен ровно там, ради чего заведён `MIN_THUMB`: конец списка перетаскиванием недостижим

`client/state/scroll.js:17`, используется в `client/components/Scrollarea.svelte:34`.

Обратная арифметика ползунка обязана быть обратной к прямой. Прямая
(`scroll.js:12-13`): `offset = (visible - height) * passed / (total - visible)`,
значит `d(passed)/d(offset) = (total - visible) / (visible - height)`. Сокращается
до `total / visible` **только при незажатой высоте** `height = visible²/total`.
Как только сработал `Math.max(MIN_THUMB, …)`, знаменатель больше не равен
`visible - visible²/total`, и `scaleOf` занижает шаг.

Макет считает правильно и прямо этой формулой —
`docs/design/index.html:2005-2008`:

```js
const travel = list.clientHeight - thumb.offsetHeight;
const range  = list.scrollHeight - list.clientHeight;
list.scrollTop = startTop + (moveEvent.clientY - startY) * range / travel;
```

`range / travel` — это `(total - visible) / (visible - height)`, то есть с учётом
зажатия. `total / visible` — без.

Что сломается: пока курсор тянет ползунок, содержимое отстаёт; ползунок,
доведённый до низа дорожки, не доводит список до конца, и остаток добирается
только колесом. Ошибка растёт с длиной списка.

Когда видно: как только `visible / total < MIN_THUMB / visible`. Синопсис карточки
(план 9 кладёт `Field` в `Scrollarea`) при области 120 px и тексте 800 px:
доля дала бы 18 px, зажатие ставит 28 — правильный масштаб 7.39, `scaleOf` даёт
6.67, промах 11 % на каждом перетаскивании. Список тегов в области 640 px
начинает промахиваться после ~14600 px содержимого.

Порядок действий: открыть область, где содержимое длиннее видимого более чем в
`visible / MIN_THUMB` раз, схватить ползунок, довести до низа дорожки — список
до конца не доехал, ползунок уполз выше курсора.

Как чинить: считать масштаб от высоты ползунка, а не от доли видимого, — то есть
отдавать наружу то же, что макет:

```js
export const scaleOf = (visible, total, height) => (total - visible) / (visible - height)
```

Высота у вызывающего уже есть — `thumb.height` в компоненте. Тест
`tests/web/scroll.test.js:31-34` при этом сторожит именно неверную формулу
(«пиксель курсора стоит больше пикселя содержимого») и должен уехать на пару
«зажатый ползунок доводит список до конца»: `offset = visible - height`
обязан давать `passed = total - visible`.

### Important (Should Fix)

#### 2. Счётчик стопки ломается, если верхнее окно создано раньше, чем разрушено нижнее: Escape умирает навсегда

`client/components/Modal.svelte:19-25`.

`mine` берётся при создании (`++opened`), а возвращается на сбросе эффекта. Эти
два момента не парны: Svelte создаёт новую ветку **до** того, как разрушит
старую. Подтверждено исходником —
`client/node_modules/svelte/src/internal/client/dom/blocks/branches.js:187-206`
(`ensure` вызывает `branch(() => fn(this.anchor))`) и `:73-163` (`#commit`,
который только после этого гасит `#onscreen`).

Что сломается: у окна, оставшегося на экране, `mine > opened`, и условие
`mine === opened` не выполнится больше никогда. Escape перестаёт закрывать окно
совсем — не «до следующего раза», а до перезагрузки страницы.

При каком порядке действий видно (оба реальны для этого приложения):

1. **Одно наложение сменяется другим в одном обновлении** — `{#if overlay === 'a'}`
   / `{:else if overlay === 'b'}`, `{#key}`, а также два соседних `{#if}`, если
   открываемое стоит в разметке раньше закрываемого. Новое окно получает
   `mine = 2`, старое возвращает счётчик к 1.
2. **Из двух окон стопки первым уходит нижнее.** Верхнее остаётся с `mine = 2`
   при `opened = 1`.

Как чинить: заменить счётчик стопкой по личности, оставив взятие места при
создании (обоснование в комментарии верно, см. Strengths):

```js
<script module>
  const stack = []
</script>

const mine = {}
stack.push(mine)
$effect(() => () => { stack.splice(stack.indexOf(mine), 1) })

const escaped = (event) => {
  if (event.key === 'Escape' && stack.at(-1) === mine) onclose()
}
```

`splice` по `indexOf` снимает своё место при любом порядке разрушения, а
сравнение с вершиной остаётся тем же по смыслу.

#### 3. Отпущенная над затемнением кнопка закрывает окно — в том числе после перетаскивания ползунка

`client/components/Modal.svelte:12` и `:34`.

`click` приходит на ближайшего общего предка узлов нажатия и отпускания. Нажали
внутри окна, отпустили над `.overlay` — общий предок и есть `.overlay`, то есть
`event.target === event.currentTarget`, и окно закрывается. `event.preventDefault()`
в `Scrollarea.svelte:31` не спасает: по спецификации Pointer Events отмена
`pointerdown` гасит совместимостные `mousedown`/`mouseup`, но `click` не гасит.

Что сломается: окно закрывается посреди жеста. Два пути, и оба штатные для этой
же задачи — ползунок живёт внутри модалки:
- схватить ползунок у правого края окна, увести курсор чуть вбок за границу
  окна и отпустить — окно закрылось, прокрутка потеряна;
- выделить текст (синопсис в плане 9) и отпустить за краем окна — то же самое.

Как чинить: закрывать только тогда, когда на затемнении случилось **и** нажатие,
и отпускание:

```js
let pressed = false
const press = (event) => { pressed = event.target === event.currentTarget }
const outside = (event) => { if (pressed && event.target === event.currentTarget) onclose() }
```

`onpointerdown={press}` на том же `.overlay`.

#### 4. Перетаскивание не отпускается, если кнопку отпустили вне окна приложения

`client/components/Scrollarea.svelte:39-44`.

Обработчики висят на `window` без захвата указателя. Отпускание за пределами окна
браузера `pointerup` в окно не доставит, и `move` останется подписанным.

Что сломается: вернув курсор в окно **без нажатой кнопки**, пользователь видит,
что список продолжает ездить за мышью; отпустить его можно только новым нажатием
и отпусканием внутри окна.

Порядок действий: схватить ползунок, вывести курсор за край окна приложения,
отпустить кнопку, вернуть курсор внутрь.

Как чинить: как в макете (`docs/design/index.html:1997`) — `setPointerCapture` на
самом ползунке и слушатели на нём же; захват сам доставляет `pointerup` и
`pointercancel` независимо от того, где курсор. Если слушатели остаются на
`window`, то как минимум добавить `pointercancel` к снятию — сейчас его нет
вовсе, и системная отмена жеста оставляет тот же зависший `move`.

#### 5. `ResizeObserver` не видит детей, появившихся после первого сброса

`client/components/Scrollarea.svelte:21-28`, комментарий `:18-20`.

`box.children` перебирается один раз, при создании наблюдателя. Эффект зависит
только от `box`, поэтому повторно он не выполнится никогда, и узлы, добавленные
позже, под наблюдение не попадают.

Что сломается: высота и смещение ползунка остаются от прежнего содержимого, пока
пользователь не прокрутит (`onscroll` — единственный оставшийся пересчёт).
Ползунок либо короче, либо длиннее правды, и его положение врёт.

При каком порядке действий видно: область уже упёрта в свой потолок (собственный
размер `box` больше не меняется), а строки — прямые дети `box`, как в
`{#each tags}<TagRow/>{/each}` из задачи 3 этого плана. Завести новый тег или
снять фильтр в поле поиска списка: строк стало больше, ни один наблюдаемый узел
не изменился, `measure` не позвался.

Комментарий на `:18-20` утверждает, что наблюдение за детьми закрывает именно
фильтрацию списка, — оно закрывает только её сужающую половину.

Как чинить: пересоздавать наблюдение при смене состава либо, короче, добавить
`MutationObserver` на `childList` того же `box`, зовущий и `measure`, и
переподписку. Второй вариант — потребовать от потребителей единственного
элемента-обёртки внутри области, но тогда это условие надо записать рядом с
`children`, иначе оно нарушится молча.

### Minor (Nice to Have)

#### 6. Своя полоса работает только там, где прокручивается сам `.scrollarea__box`

`client/styles/scrollarea.css:14-18`, `client/components/Scrollarea.svelte:15`.

Замер идёт по `box`. Из четырёх областей, названных в комментарии, две
прокручиваются не им, а вложенным элементом: синопсис — это `textarea`
(`docs/design/index.html:1096-1102`, своя высота и свой `overflow`), список
совпадений — `ul.picker__hits` со своим `max-height: 216px` и `overflow-y: auto`
(план 9, `docs/plans/2026-07-31-card-window.md:580-596`). Обёртка над таким
элементом не прокручивается вовсе, `thumbOf` вернёт `null`, и полоса не покажется
никогда, а системная у них скрыта — прокрутка останется без всякого указателя.

Плюс порядок импортов: `scrollarea.css` подключён последним
(`client/main.js:26`), поэтому при равной специфичности его потолок 640 px
перебьёт потолки, объявленные в файлах выше.

Чинить сейчас необязательно — потребители появятся в задачах 3 и в плане 9, — но
условие «прокручивается сама область» стоит записать рядом с компонентом, иначе
оно нарушится молча.

#### 7. `thumbOf` даёт отрицательное смещение на области ниже `MIN_THUMB`

`client/state/scroll.js:11-13`.

При `visible < 28` зажатие даёт `height > visible`, `room` отрицателен, и ползунок
уезжает вверх за край дорожки, будучи выше её самой. Область меньше 28 px в макете
не встречается, поэтому Minor; закрывается одним `Math.min(visible, …)` при
вычислении высоты.

#### 8. Полоса теперь видна всегда, а в макете она проявлялась под курсором

`client/components/Scrollarea.svelte:52`, `client/styles/scrollarea.css:21-34`.

Макет (`docs/design/index.html:1983-1995`) вешает `is-shown` на `mouseenter`
области и снимает через 700 мс после прокрутки, если курсор ушёл. Здесь класс
стоит всё время, пока есть что прокручивать, и `transition: opacity .25s` из
макета больше ничего не переключает — он мёртв.

Так написано в плане, поэтому это не отступление исполнителя. Записано как
наблюдение: макет — источник истины, и расхождение стоит либо подтвердить
решением, либо вернуть проявление.

#### 9. Входные `ask` и `danger` объявлены планом, но не приняты компонентом

`client/components/Modal.svelte:8`; интерфейс задачи —
`docs/plans/2026-07-31-filters-and-stats.md:97-100`; потребитель —
`docs/plans/2026-07-31-card-window.md:1043-1051`
(`.modal--ask`, `.modal--danger { --neon: var(--error) }`).

Svelte 5 неизвестный вход молча игнорирует. Когда план 9 передаст `danger`,
подтверждение удаления получит акцентную кромку вместо красной и ничего не упадёт
— ровно тот класс тихой поломки, который проект уже ловил на именах источников.
`--neon` на `.modal` (`modal.css:17`) заведён под это правильно, не хватает
только двух классов и двух входных.
