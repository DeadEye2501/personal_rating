# Ревью среза 02: качество тестов

Предмет — 4 теста из `tests/backend/test_session.py` и код, который они
охраняют: `backend/storage/session.py` (36 строк). Линза одна: **может ли тест
упасть, если сломается ровно то, ради чего он написан.**

Метод — мутационная проверка. 23 поломки внесены в `session.py` по одной,
после каждой прогон `pytest -q` по файлу теста, после прогона откат из
эталонной копии с проверкой контрольной суммы. Ни одна правка не осталась:
`md5` файла в конце тот же, что в начале (`2ebc5df…`), полный прогон —
`36 passed`.

Исходное состояние: `36 passed in 0.41s`, из них 4 в срезе.

## Счёт

| | |
|---|---|
| Поломок внесено | 23 |
| Поймано | 15 |
| **Прошло молча** | **8** |

Находок: **3 блокирующих, 3 важных, 2 мелких.**

Отличие от среза 01: там непойманное было незаконченным покрытием однотипных
мест — «не посмотрели в соседнее поле». Здесь другое. Файл маленький и почти
весь простреливается, но **три из четырёх заявленных свойств кода не проверены
ни одним тестом**, а один тест назван по свойству, которого не касается.

## Блокирующие

### 1. `test_sessions_keep_objects_usable_after_commit` не проверяет то, чем назван

`tests/backend/test_session.py:25-35`, охраняет `backend/storage/session.py:35`.

Имя теста и его докстрока говорят про `expire_on_commit=False`. Тело выполняет
`text("SELECT 1")`, коммитит и читает `result.scalar()`.

`expire_on_commit` управляет **только** просрочкой ORM-объектов в карте
идентичности сессии. Результат сырого `text()` — буферизованный `CursorResult`,
к карте идентичности отношения не имеющий. Тест не может упасть по своей
причине.

Мутации и результат:

| Поломка | Результат |
|---|---|
| `expire_on_commit=False` → `True` | **4 passed** |
| убрать аргумент вовсе (умолчание `True`) | **4 passed** |

Что происходит на самом деле, замерено отдельно на настоящем ORM-объекте:

```
raw text(), expire_on_commit=False: scalar=1
raw text(), expire_on_commit=True:  scalar=1        <- разницы нет
ORM attr,   expire_on_commit=False: title='Ведьмак'
ORM attr,   expire_on_commit=True:  RAISES MissingGreenlet:
            greenlet_spawn has not been called; can't call await_only() here
```

То есть поломка не безобидная: в проекте, где `backend` живёт в отдельном
потоке со своим циклом asyncio, обращение к полю после коммита при
`expire_on_commit=True` роняет не тест, а рабочий поток — ровно тем `MissingGreenlet`,
про который докстрока и предупреждает («не должно лезть в базу за обновлением
из другого потока»). Тест написан против настоящей опасности и не смотрит на неё.

Чинится только заменой тела: нужен ORM-объект, `add` + `commit`, затем чтение
поля. Пока в `backend/model/*` лежат замороженные датаклассы, а не декларативные
модели, честного объекта нет — значит, этот тест либо ждёт слайса с таблицами,
либо заводит свою модель в тестах. Оставлять в нынешнем виде нельзя: он
показывает зелёный за настройку, которой не касается.

### 2. Ни один тест не отличает настройку «на каждое соединение» от «на первое»

`backend/storage/session.py:23`, комментарий на `:25`.

Комментарий прямо называет опасность: «SQLite выключает внешние ключи на каждом
подключении заново». Слушатель повешен на `connect` — правильно. Но все четыре
теста открывают ровно одно соединение, поэтому `connect` и `first_connect`
для них неразличимы.

| Поломка | Результат |
|---|---|
| `"connect"` → `"first_connect"` | **4 passed** |

Замер на двух одновременно открытых соединениях одного движка:

```
event=connect        conn1 fk=1  conn2 fk=1
event=first_connect  conn1 fk=1  conn2 fk=0
```

Это и есть рабочая конфигурация: пул `AsyncAdaptedQueuePool`, несколько
соединений. При `first_connect` внешние ключи выключены везде, кроме первого
соединения, каскадное удаление молча перестаёт работать — а срез остаётся
зелёным. Та же дыра закрывает и `py_lower`: со второго соединения функции
просто нет.

Закрывается одним тестом: открыть два соединения одновременно (второе — не
закрыв первое, иначе пул вернёт то же самое) и проверить `PRAGMA foreign_keys`
и `py_lower` на обоих.

### 3. `deterministic=True` не проверен ничем

`backend/storage/session.py:29`.

| Поломка | Результат |
|---|---|
| убрать `deterministic=True` | **4 passed** |

Флаг не украшение. Замер:

```
deterministic=True:  index CREATED ok
deterministic=False: FAILS -> non-deterministic functions prohibited
                              in index expressions
```

`py_lower` заведён ради регистронезависимого сравнения названий, а такое
сравнение рано или поздно уезжает в индекс по выражению (равно как в
генерируемый столбец, `CHECK` или частичный индекс — SQLite запрещает
недетерминированные функции во всех четырёх). Флаг несущий, и его потеря
проявится не здесь, а в миграции, которая не накатится.

## Важные

### 4. `fold(None)` не проверен

`backend/storage/session.py:16`, сигнатура `str | None -> str | None`.

| Поломка | Результат |
|---|---|
| `return value.lower()` без обработки `None` | **4 passed** |

Ветка обещана типом и не исполняется ни разу. Замер мутанта:

```
py_lower(NULL) -> OperationalError: user-defined function raised exception
fold(None)     -> AttributeError
```

NULL в текстовом столбце достижим в обычном запросе, и `py_lower` по такому
столбцу уронит весь запрос. `fold` — чистая функция, проверка стоит одной
строки.

### 5. Не проверено, что `session_factory` привязан к переданному движку

`backend/storage/session.py:34-35`.

| Поломка | Результат |
|---|---|
| фабрика привязывается к своему `:memory:`-движку | **4 passed** |

Единственный тест, который вообще зовёт `session_factory`, выполняет `SELECT 1`
— он выполнится на любом движке. Поэтому подмена базы целиком проходит молча:
сессии ходили бы в память вместо файла на диске, и срез бы этого не заметил.
Непривязанную фабрику тест ловит (`S2`), а подменённую — нет.

Закрывается тем же тестом, что и находка 1, если тот будет писать объект и
читать его обратно из файла.

### 6. `parents=True` не проверен: «глубокий» путь в тесте глубиной в один уровень

`tests/backend/test_session.py:17` против `backend/storage/session.py:20`.

| Поломка | Результат |
|---|---|
| `mkdir(exist_ok=True)` без `parents=True` | **4 passed** |

Тест берёт `tmp_path / "deep" / "library.db"` — `tmp_path` уже существует,
недостающий уровень ровно один, и обычный `mkdir` с ним справляется. Замер при
существующем корне:

```
1 недостающий уровень: mkdir(exist_ok=True) OK      <- то, что берёт тест
2 недостающих уровня:  FileNotFoundError
3 недостающих уровня:  FileNotFoundError
```

Правится одним символом в самом тесте: путь на два уровня вместо одного. Это не
придирка — рабочий путь к базе лежит в каталоге приложения, которого при первом
запуске нет целиком, вместе с родителем.

## Мелкие

### 7. `cursor.close()` не проверяется

`backend/storage/session.py:28`. Удаление проходит молча (`4 passed`).
Тестом не закрывается разумно: курсор освобождается сборщиком, наблюдаемого
эффекта нет. Записано для полноты счёта, действий не требует.

### 8. Четыре копии подготовки и уборки

`tests/backend/test_session.py:9/13, 18/21, 29/35, 41/47`.

`engine = create_engine(tmp_path / "library.db")` и `await engine.dispose()`
повторены по четыре раза. По манифесту (правило 3) дубль выносится на втором
появлении. Фикстура убрала бы повтор и заодно починила бы то, что сейчас
`dispose()` стоит последней строкой без `try/finally`: упавший `assert` его
пропускает, и под Windows остаётся открытый handle на файл в `tmp_path`.
Серьёзность низкая — упавший тест и так останавливает работу.

## `test_case_folding_works_for_cyrillic`: утверждение про SQLite, а не про нас

`tests/backend/test_session.py:46`:

```python
assert builtin.scalar() == "Ведьмак"
```

Проверено на текущей сборке — утверждение верно:

```
sqlite_version = 3.45.3
ENABLE_ICU в compile_options: False
lower('Ведьмак') == 'Ведьмак': True
lower('ABC') == 'abc':         True
```

Но это свойство **сборки SQLite**, а не нашего кода. Расширение ICU в SQLite
переопределяет `upper()`, `lower()` и `like` юникодными версиями; на сборке с
ICU строка вернёт `ведьмак`, и тест станет красным при полностью исправном
`session.py`. Красный будет показывать не на ту причину и не на тот файл.

Первая половина теста (`:45`, `py_lower('Ведьмак') == 'ведьмак'`) — настоящая
проверка нашего кода, и она хороша: её ловят пять разных мутаций `fold` и
регистрации.

Вторая половина — обоснование замысла, записанное как assert. Обоснованию место
в комментарии и в докстроке `fold` (`session.py:13-15`), где оно уже есть слово
в слово. Предложение: убрать `builtin`-ветку из этого теста. Если проверять
предпосылку всё же хочется — она заслуживает отдельного теста с честным именем
(«встроенный lower не годится для кириллицы»), чтобы падение читалось как
«сборка SQLite сменилась, замысел пора пересмотреть», а не как «наш код сломан».

## `dispose()` и утечки соединений

Проверено отдельно, потому что вопрос задавался прямо.

`await engine.dispose()` есть **во всех четырёх** тестах. Замер:

```
до dispose:  pool checkedin=1, size=5
после:       pool checkedin=0
файл базы удаляется сразу после dispose: да (открытых handle не осталось)
```

`pytest -W error::ResourceWarning` по срезу — чисто. Прогон файла дважды в одном
процессе — чисто. **Утечки между тестами нет.** Единственная оговорка — про
`try/finally`, записана выше как находка 8.

## Итог

Три теста из четырёх держат своё уверенно. Четвёртый
(`test_sessions_keep_objects_usable_after_commit`) не может упасть по своей
причине и потому не считается. Сверх этого не охраняются три свойства кода:
применение настроек на каждое соединение, `deterministic=True` и обработка
`None` в `fold`.

Блокирующих — три: находки 1, 2 и 3.
