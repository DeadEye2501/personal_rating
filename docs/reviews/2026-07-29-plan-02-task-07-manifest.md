# Ревью: план 2, задача 7 (Steam) — соответствие манифесту

Дата: 2026-07-29. Измерение: манифест чистого кода, правила 2, 6, 7, 10, 11, 13.
Работа не закоммичена.

## Сильные стороны

- **Место для кода (правило 2).** `backend/sources/steam/{client,parse}.py`
  дословно повторяет расстановку `backend/sources/tmdb/`: сеть отдельно от
  разбора, никакого нового паттерна ради одного источника. Правки вне новой
  папки — только `backend/model/card.py` (поле `companies`, ожидалось ещё
  задачей 5) и `tests/backend/sources/conftest.py` (`replay` на несколько
  файлов) — обе оправданы и не трогают соседние источники.
- **Одна ответственность (правило 6).** `parse.py` — «перевод ответов Steam в
  наши типы», `client.py` — «разговор со Steam по сети». Каждый описывается
  фразой без «и»; разбор (`parse_card`, `parse_tags`, `_companies`,
  `_metascore`, `_year`) не содержит сетевого кода, `client.py` не собирает
  домен из JSON сам — только маршрутизирует (`Found`/`Missing`/`Refusal`) и
  зовёт `parse_*`.
- **Абстракция со второй реализацией (правило 7).** Новых интерфейсов,
  реестров или базовых классов не заведено — `SteamClient` просто вторая
  реализация уже существующего негласного контракта `search/card/aclose` от
  `TmdbClient`, без промежуточного `Protocol`/ABC. Параметр `kind`, нигде не
  используемый внутри Steam-методов, — сознательное продолжение решения,
  принятого ещё в задаче 4 ради будущего реестра, а не забытый мусор.
- **Логика не в интерфейсе (правило 10).** `client.py` не превращает JSON в
  `Credit`/`Item` сам — этим занимается только `parse.py`; структурные проверки
  в клиенте (`block is None`, `block.get("success")`) — маршрутизация исхода, а
  не разбор полей.
- **Комментарии (правило 11).** Все объясняют неочевидное: почему `_year`
  ищет год регэкспом, а не берёт хвост строки; почему метраж Metacritic, а не
  Steam; почему сверка appid и код у тегов важны, хотя не различают исход;
  почему теги достаются вне общего `try`. Пересказа кода и ссылок на чужие
  проекты нет.
- **Тесты проверяют поведение (правило 13).** Все 23 теста наблюдают
  наблюдаемое: значения полей после разбора реальных фикстур, тип `Outcome`,
  содержимое `detail`/`caplog` там, где два разных отказа иначе неразличимы
  (`test_a_reply_about_another_game_is_refused` смотрит `"appid" in
  result.detail`, `test_tags_that_did_not_arrive_do_not_break_the_card` —
  `"400" in caplog.text`). Проверено вручную: без явной проверки кода на
  запросе тегов `response.json()` упал бы на HTML-теле `store_items_broken.txt`
  с другим текстом ошибки — тест на `"400"` в логе реально ловит удаление этой
  проверки, то есть обе спорные проверки из отклонения №4 оправданы, а не
  избыточны.
