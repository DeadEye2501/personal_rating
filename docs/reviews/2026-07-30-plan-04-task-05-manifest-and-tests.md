## Правило 6 — одна ответственность на модуль

Формальная проверка манифеста («опиши без „и“») **не проходит буквально**:
модульный докстринг — «Страницы разделов **и** гистограмма для показа.» —
использует «и» напрямую. Это не автоматически нарушение (у `SectionsRepository`
в задаче 4 было то же самое и признано одной ответственностью — «два вопроса
об одном и том же наборе»), но там основанием служил общий `_narrow`,
реально разделяемый обоими методами. Здесь такого нет: `page` зовёт
`self._sections.ids` + `self._views.views_for`, `histogram` зовёт только
`self._sections.histogram` — общей реализации между двумя методами
`LibraryService` нет вовсе, это две независимые однострочные переадресации.
Единственное настоящее основание для одной ответственности — не код, а экран:
раздел «Оценённые» в клиенте показывает ленту карточек и гистограмму
одновременно, по одному и тому же отфильтрованному набору, и по границе
слоёв (`CLAUDE.md`: «через границу ходят только простые данные», клиент не
знает про SQLAlchemy) кто-то обязан быть точкой входа для обоих. Это
рассуждение нигде не записано — ни в докстринге модуля, ни класса. См. находку
Important ниже.

## Правило 7+8 вместе — оправдан ли `LibraryService` сегодня

**`page`** — не пустая обёртка: восстанавливает порядок (`found[item_id] for
item_id in item_ids`, а не `found.values()`) поверх словаря, который
`ViewsRepository.views_for` намеренно не сортирует (её докстринг: «Порядок
принадлежит запросу раздела»). Это настоящая логика сборки, оправдана
безусловно.

**`histogram`** — буквально одна строка, `return await
self._sections.histogram(kind, filters)`, без единого добавленного действия.
Сегодняшнего потребителя, кроме теста, нет: `main.py` не существует, клиент
(планы 5–6) не начаты, `SearchService` (задача 6) тоже. Формально это
«потребителя без сегодняшнего кода» — but I checked whether it's premature all
the same:

- Задача 4 (`docs/reviews/2026-07-30-plan-04-task-04-manifest.md:158-163`)
  уже называла этот сервис заранее как единственное правильное место для
  `histogram`, вызванного вместе с `ids`: «выносить его в сервис
  (`backend/service/library.py` из задачи 5)... сервису тогда пришлось бы либо
  звать `histogram` со специальным флагом... либо дублировать». То есть решение
  принято не в этом слайсе задним числом, а предсказано за слайс до него.
- По спеке структуры клиент не имеет права дойти до `SectionsRepository`
  напрямую (она принимает `sessions`/использует `Select` — детали хранилища).
  Значит `histogram` в любом случае должен получить публичную точку входа
  где-то в `service/`; вопрос не «нужен ли метод», а «в каком классе».
- Отдельного класса на один метод (`HistogramService`) правило 7 запрещает
  ровно так же: одна реализация, второй нет. Совмещение с `page` в одном
  классе — не premature abstraction, а единственный не premature вариант.

**Вывод: `LibraryService` оправдан сегодня, но не потому, что у него есть
работающий вызывающий код — такого пока действительно нет ни у одного
сервиса в `backend/service/` (`main.py` не существует), — а потому, что (1)
это уже предсказанная задачей 4 точка соединения `ids`+`histogram`
одного экрана и (2) архитектурная граница слоёв не оставляет `histogram`
других мест без нарушения правила 7 в другую сторону.** Проговорить это в
докстринге классу стоит — сейчас там объяснено только `page` (см. правило 6/11).

## Правило 13 и 14 — каждый из 8 тестов `test_feed.py`

1. **`test_a_page_keeps_the_order_of_the_section`** (19-26) — наблюдает: порядок
   возвращённых `CardView` — по убыванию оценки (10, 7, 3), не по порядку
   вставки в базу и не по словарному порядку `views_for`. Ломает: замена
   `[found[item_id] for item_id in item_ids if item_id in found]` на
   `list(found.values())` — тест получит порядок, в котором `ViewsRepository`
   вернула строки БД (обычно по id вставки), а не по оценке.

2. **`test_a_page_carries_the_whole_card`** (29-38) — наблюдает: элемент
   страницы — полноценный `CardView` с `rating.score` и списком тегов, а не

3. **`test_an_empty_section_is_an_empty_page`** (41-42) — наблюдает: на пустой
   базе `page()` реально возвращает `[]`, не падает и не выдаёт мусор. Ломает:
   любая ветка, которая обращается к элементу без проверки длины (например,
   гипотетическое `found[item_ids[0]]` вместо list comprehension). **Слабое
   место**: при нынешней реализации не нашёл ни одной правдоподобной поломки
   одной строкой в `library.py`, которую поймал бы только этот тест и не
   ловил бы никто из остальных семи — `views_for([])` уже возвращает `{}` по
   собственному короткому пути (задача 2), и никакой код в `page()` не
   ветвится по пустоте отдельно. Тест не вреден, но по факту дублирует
   гарантию, уже данную `ViewsRepository.views_for` (`test_nothing_is_asked_for_an_empty_list`
   в `test_views.py`) на уровень выше.

4. **`test_a_portion_is_fifty_and_it_is_applied`** (45-56) — наблюдает:
   `PAGE_SIZE == 50` **и** при 51 карточке страница реально возвращает ровно

5. **`test_the_next_portion_continues_the_previous`** (59-67) — наблюдает:

   Ломает: `offset` не передаваемый в запрос (например, захардкоженный

6. **`test_a_page_asks_with_the_filters_it_was_given`** (70-80) — наблюдает:

7. **`test_the_histogram_asks_with_the_filters_it_was_given`** (83-95) —
   наблюдает: `feed.histogram(kind, Filters(tag_ids=(tag_id,)))` реально

## Непокрытые поломки

**Главная: снятие `if item_id in found` в `page()`.** Строка
```python
return [found[item_id] for item_id in item_ids if item_id in found]
```
если заменить на
```python
return [found[item_id] for item_id in item_ids]
```
— все восемь тестов проходят без изменений. Ни в одном тесте не встречается
`item_id`, который вернул бы `sections.ids`, но для которого `views_for`
не нашла бы строку (в тестах карточки создаются и тут же читаются в одной
транзакции, удаления между двумя запросами нет). Молчаливая поломка меняет
поведение с «пропущенная карточка тихо выпадает из страницы» на «пропущенная
карточка роняет всю страницу `KeyError`» — ровно тот случай, которым описан
защитный комментарий `library.py:26`, но который сам комментарий не
проверяет ничем. Стоит отдельного теста: создать карточку, узнать её id через
`sections.ids` напрямую (или пойти окольным путём — что технически means
мокать `ViewsRepository`, либо удалить строку `item` между двумя запросами
внутри теста), убедиться, что `page()` не падает и просто возвращает страницу
короче.

**Раздел «Хочу посмотреть» не встречается в `test_feed.py` вовсе** — только
`RATED`. Смягчающее обстоятельство: `page()`/`histogram()` не содержат
никакой ветки по `Section` внутри `library.py` — весь выбор раздела уходит
целиком через `feed.section`/`kind` в `SectionsRepository`, который уже
проверен на `WISHLIST` в `test_sections.py` (задача 3). Правдоподобной
поломки, специфичной для `WISHLIST` и живущей именно в `library.py`, не
нашёл — но если такая ветка появится в будущем слайсе (например, служебная
проверка раздела внутри сервиса), тест на неё не отреагирует, потому что
такого теста тут нет ни одного.

**`limit=0`** — не тестируется ни здесь, ни (насколько видно из диффа) в
`test_sections.py`. Поведение (пустая страница или ошибка) сегодня нигде не
зафиксировано контрактом; не блокирует, но реальный клиентский код (например,
экран статистики, которому карточки не нужны, только гистограмма) может
рано или поздно вызвать `page(feed, limit=0)` буквально, и тогда обнаружится,
что там на самом деле происходит.
