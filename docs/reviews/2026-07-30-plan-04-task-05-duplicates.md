## Кандидаты рассмотрены

1. **`LibraryService.histogram` против `SectionsRepository.histogram`.**
   Подтверждено чтением `backend/service/library.py:29-30` и
   `backend/storage/repository/sections.py:103-136`: метод сервиса — один
   вызов без всякой логики, репозитория — тридцать с лишним строк с двумя
   запросами и сборкой `Histogram`. Прямого повтора кода здесь нет: сервис не
   переписывает логику репозитория, а вызывает её ровно один раз.
   Рассмотрено как архитектурный вопрос (главный вопрос слайса, а не повтор
   строк). Вывод: **прослойка оправдана и не снимается**. План 4, задача 5,
   прямо объявляет `histogram(kind, filters) -> Histogram` частью поверхности
   `LibraryService` — это согласованный интерфейс, а не случайный побочный
   метод. `page()` на этой же поверхности несёт настоящую логику (сохранение
   порядка раздела при сборке карточек), и `histogram` держится рядом с ним
   по той же причине: `LibraryService` — единая точка входа в раздел для
   будущей сборки бэкенда (задача 14), и она прячет за собой сразу два
   репозитория. Убери `histogram` — вызывающему из клиентского каркаса
   пришлось бы держать ссылки на `SectionsRepository` отдельно от
   `LibraryService`, то есть свойство единой точки входа сломалось бы. Не
   считаю повтором.

2. **`LibraryService.page` против `SectionsRepository.ids` и
   `ViewsRepository.views_for`.** Прочитан `backend/service/library.py:22-27`.
   Ответственность не размазана, а честно распределена: `ids` отвечает про
   номера отфильтрованного и отсортированного набора, `views_for` — про сбор
   карточек по номерам без порядка (возвращает словарь), а `page` — про
   восстановление порядка раздела при сборке (`[found[i] for i in item_ids if
   i in found]`). Это ровно то, что описано в докстроке модуля и в плане
   («Порядок восстанавливает сервис»). Не повтор — логика существует только в
   одном месте.

3. **`PAGE_SIZE` (50) против `limit` в `list_by_kind`, `list_ids`,
   `SectionsRepository.ids`, `suggest` (умолчание 10).** Прочитаны сигнатуры
   через `grep`. Совпадений значений нет: `PAGE_SIZE = 50` — единственная
   объявленная константа порции, у `suggest` умолчание `10` захардкожено
   локально и не совпадает по величине с `PAGE_SIZE`, у остальных `limit` —
   параметр без умолчания, значение приходит от вызывающего. Двух источников
   истины для одного и того же числа нет. Не повтор, кандидат отклонён.

4. **`backend/service/library.py` против остальных модулей `backend/service/`
   (`cards.py`, `linking.py`, `card_parts.py`, `posters.py`, `genres.py`,
   `images.py`).** Прочитаны докстроки и структуры всех шести через
   `module-map.md`, вдобавок открыт `genres.py` и начало `posters.py`.
   Ответственности не пересекаются: запись карточки, привязка, общая основа
   записи, обложки, разрешение жанров, обрезка картинки — ни один не читает
   разделы и не строит гистограмму. `library.py` — единственный модуль про
   чтение ленты. Не повтор, кандидат отклонён.

5. **`rated` в `tests/conftest.py` против `an_item`, фикстуры `card` там же и
   `make_item` в `test_library.py`.** Прочитаны все четыре. `rated` не
   переписывает их логику, а компонует: строит `Item` через `an_item`,
   записывает через `LibraryRepository.create` (как и `card.make` внутри
   себя), опционально ставит оценку через `RatingsRepository.set_score`. Общее
   с `card.make` — идиома в одну инструкцию
   (`await LibraryRepository(sessions).create(Item(...))`), короче порога в
   пять инструкций, который уже describан в манифесте как не подлежащий
   вынесению. Отличаются по существу: `card.make` — три параметра, фиксированный
   `synced_at`, без оценки; `rated` — полный проброс полей, умолчание года,
   опциональная запись оценки. С `make_item` пересечения ещё меньше:
   `make_item` строит **незаписанный** `Item` с богатым набором полей для
   проверки круглого пути через базу, `rated` всегда пишет и возвращает номер.
   Не повтор.

6. **Константа `RATED` в `tests/backend/test_feed.py` против `RATED`/`WANTED`
   в `tests/backend/test_sections.py`.** Прочитаны оба места:
   - `tests/backend/test_feed.py:11`: `RATED = Feed(Section.RATED, Kind.MOVIE, Filters(), Order(Sort.SCORE))`
   - `tests/backend/test_sections.py:26`: `RATED = Feed(Section.RATED, Kind.MOVIE, Filters(), Order(Sort.SCORE))`

   Выражения совпадают дословно, вплоть до порядка позиционных аргументов.
   Обоснования для расхождения нет — оба представляют один и тот же базовый
   `Feed` для «Оценённых» по разделу, сортированный по оценке, и служат одной
   и той же цели: отправная точка, которую тесты правят через `replace(...)`.
   **Подтверждённый повтор.**

7. **Фикстура `feed` в `test_feed.py` против фикстуры `sections` в
   `tests/conftest.py`.** Прочитаны обе. `sections` строит
   `SectionsRepository(sessions)` и ничего больше. `feed` зависит от `sections`
   и добавляет `ViewsRepository`, собирая из них `LibraryService`. Одна
   переиспользует другую, а не повторяет её тело. Не повтор.

## Подтверждённые повторы

Один: константа `RATED` в `tests/backend/test_feed.py:11` дословно совпадает с
`RATED` в `tests/backend/test_sections.py:26` — тот же `Feed`, то же
назначение (база для `replace()` в проверках раздела «Оценённые»), нет ни
одной причины различаться. Оставить одно объявление в `tests/conftest.py` (там
уже лежат общие для тестов константы `MOMENT`, `LATER`, `TABLES`, `MINIMAL`) и
импортировать его из обоих файлов; `WANTED` в `test_sections.py` — не дубль,
уникален для раздела «Хочу посмотреть», трогать не нужно.
