### 15. `test_a_page_costs_the_same_no_matter_how_many_cards`
Следствие: число настоящих обращений к курсору ровно 9 и не растёт при 20
карточках вместо одной — считает событие SQLAlchemy `before_cursor_execute`,
то есть реальные запросы к драйверу, а не вызовы `_fetch_all`.

**Поймал бы он цикл по карточкам внутри?** Да. Если бы `views_for` вызывал
`_fetch_all` (или любой из девяти хелперов) по разу на каждую карточку вместо
пачки, `for_many` было бы 9×20=180, а `for_one` осталось 9 — `for_many ==
for_one` упадёт. Дополнительно `for_one == 9` — тоже жёсткая проверка, а не
только сравнение «один против многих».

**Сломается ли он от постороннего запроса вроде `PRAGMA`?** Нет. `PRAGMA
foreign_keys=ON` и регистрация `py_lower` выполняются в `prepare_connection`
(`backend/storage/session.py:27-35`) через `dbapi_connection.cursor()` —
**сырой курсор драйвера, полученный напрямую с открытого DBAPI-соединения**, в
обход `Connection`/диалекта SQLAlchemy. Событие `before_cursor_execute`
инструментирует курсоры, которые SQLAlchemy создаёт сама при выполнении
`Connection.execute`/`session.execute`; курсор, заведённый в обход этого пути,
под инструментацию не попадает. Эмпирическое подтверждение — тест уже зелёный
с жёстким числом 9: будь `PRAGMA` в счёте, число расходилось бы с девятью
признаками, которые перечислены в докстринге. Отдельный риск (не про этот
тест, а про хрупкость самого решения): при смене пула соединений (например, на
`NullPool`, где новое соединение — и, значит, `PRAGMA` — заводится на каждую
сессию) поведение осталось бы прежним лишь потому, что `PRAGMA` идёт мимо
инструментации; риска ложного красного из-за этого нет.

**Пройдёт ли он молча, если один из девяти признаков перестанут читать
вовсе?** Нет. `for_one == 9, counted` — жёсткое число, а не только равенство
`for_one`/`for_many`. Выброшенный вызов (скажем, `_wishlist`) даст `for_one ==
8`, и assert упадёт по абсолютному значению, а не только по паритету.

## Проверка доводов о ненаблюдаемости

### Довод 1 — снятие `.where(...item_id.in_(item_ids))` в `_genres` (и соседних)

Согласен. Финальная сборка (`views.py:95-107`) читает вспомогательные словари
только по ключам `known = list(views)` (`views.py:85`), которые уже
ограничены первым запросом к `item`. Это структурное свойство, а не
случайность тестовых данных: даже если `_genres`/`_tags`/`_credits`/
`_external`/`_identifiers` соберут `defaultdict` по **всей** таблице (без
фильтра по `item_ids`), лишние ключи для карточек, которых не просили,
никогда не читаются — `genres[item_id]` берётся только для `item_id in
views`. Никакой тест, включая двухкарточечный, не может это поймать в
принципе через возвращаемый тип: чтобы утечка стала видна, `views_for` должен
был бы возвращать данные и по незапрошенным карточкам, а он этого не делает
по конструкции. Единственная цена снятия фильтра — запрос дорожает
(сканирует всю таблицу вместо `item_ids`), что не измеряется числом запросов
в тесте 15 (там считаются штуки, а не объём). Согласен, что фильтр можно
снять без вреда корректности; из соображений производительности (не
тестового покрытия) я бы всё же не советовал его убирать — это отдельный
довод, не про наблюдаемость.

### Довод 2 — снятие `.order_by(external_rating.c.source)` в `_external`/`_identifiers`

Согласен, с уточнением. Обе таблицы объявлены с составным первичным ключом
`PrimaryKeyConstraint("item_id", "source")` (`backend/storage/tables/catalog.py:114,
126`), и SQLite строит по нему автоиндекс `sqlite_autoindex_*_1` на
`(item_id, source)`. При `WHERE item_id IN (...)` для **одного** значения
`item_id` (все тесты файла used именно так — списки из одного элемента)
SQLite делает точечный seek по индексу и обходит совпадающий диапазон в
порядке второй колонки индекса — то есть строго по `source` — не как
случайное совпадение движка, а как гарантированное следствие структуры
B-дерева при равенстве по первому столбцу составного индекса. Тест
`test_external_ratings_come_with_the_card` пишет строки в обратном алфавиту
порядке нарочно, чтобы не спутать это с порядком вставки, — и именно поэтому
он **не отличит** наличие `order_by(external_rating.c.source)` от его
отсутствия: обе версии дают IMDB перед METACRITIC. Тот же довод переносится
на `_identifiers` (`external_id` — тот же тип ключа), хотя в файле нет теста,
который вставлял бы две записи `external_id` для проверки их порядка вовсе.

Оговорка: это поведение SQLite (выбор плана через индекс) не задокументировано
как контракт и не гарантировано на будущее — при списке из нескольких
`item_id` или при иных настройках планировщика он мог бы выбрать другой план
(например, OR-разворачивание `IN` с объединением через временное дерево,
теряющее порядок). Для целей вопроса «нужно ли `ORDER BY` тестам» — нет,
сохранённые ассерты его не заметят. Для целей «нужно ли `ORDER BY` в коде» —
решение оставить его вопрос вкуса/устойчивости к будущим версиям SQLite, а не
вопрос покрытия тестами.

## Непокрытое

Правдоподобная одна поломка, которую не поймает ни один из 15 тестов:

**Смешивание жанров, состава (людей/студий), внешних оценок или внешних
идентификаторов между двумя карточками при пачечном чтении.** Например,
`views.py:159` в `_credits`: `found[row.item_id].append(...)` заменить на
`found[item_ids[0]].append(...)` — то есть все привязки уходят под ключ первой
запрошенной карточки. Та же форма поломки применима к `_genres` (`views.py:120`),
`_external` (`views.py:180`), `_identifiers` (`views.py:196`).

Почему пройдёт молча: все тесты, которые проверяют содержимое этих четырёх
признаков (4, 6, 7, 8, 9, 10, 11), запрашивают **ровно одну** карточку — для
неё `item_ids[0]` и есть её собственный `item_id`, так что подмена ключа
неотличима. Единственный тест с двумя карточками —
`test_two_cards_do_not_mix_their_belongings` — вообще не трогает жанры,
состав и внешние данные, только теги/оценку/закладку. Значит, ту же самую
форму бага, которая для тегов/оценки/закладки уже поймана явно (три мутации в
присланном списке), для жанров/людей/студий/внешних оценок/идентификаторов не
поймает никто. Это прямой аналог уже закрытых дыр, только для другой четвёрки
признаков.

## Вердикт

Прогон: `57 passed in 6.27s`. Тесты 1, 4–12, 14 наблюдают настоящее поведение
и каждый ловит минимум одну мутацию из присланного списка (либо явно
названную, либо структурно эквивалентную). Тесты 2 и 3 не вредны, но не имеют
однострочной ронки — они проверяют форму результата, которая гарантирована
раньше кода репозитория (несуществующая строка / `.in_([])`). Оба довода о
ненаблюдаемости подтверждены: снятие `.where` в `_genres`-подобных методах не
наблюдаемо в принципе через возвращаемый тип, снятие `.order_by` в
`_external`/`_identifiers` не наблюдаемо конкретно этим набором тестов из-за
устройства составного первичного ключа в SQLite.

Найден один реальный пробел: смешивание жанров/состава/внешних оценок и
идентификаторов между двумя карточками не проверяется нигде, хотя ровно та же
форма бага для тегов/оценки/закладки уже закрыта. Стоит расширить
`test_two_cards_do_not_mix_their_belongings` (или добавить рядом) хотя бы одной
проверкой на одном из этих четырёх признаков — так же, как уже сделано для
тегов.

**Готово к коммиту: С правками** — долить в двухкарточечный тест проверку
хотя бы одного из непокрытых признаков (жанры/состав/внешние оценки/
идентификаторы), прежде чем закрывать слайс. Тесты 2 и 3 — не блокер, но
достойны короткого замечания при полном ревью: они не проверяют то, что
заявлено в имени, только по другой причине, чем правило 13 обычно ловит
(результат детерминирован раньше, чем успевает сработать проверяемая строка).
