## Разбор по правилам манифеста

### Правило 8 — «ничего на всякий случай»

- **`SearchService` как класс с одним методом.** Оправдан: повторяет уже
  устоявшийся в проекте паттерн «сервис = состояние из репозиториев +
  методы» (второй пример после `LibraryService`, который тоже начинался с
  одного значимого метода до появления `histogram`). У задачи 7 того же плана
  уже расписано добавление `sources`/`genres` и вторых методов — класс не
  придуман про запас, а обрезан по сегодняшней части того же интерфейса,
  который план фиксирует целиком. Не нарушение.
- **`SEARCH_SIZE` публичной константой.** Есть сегодняшний потребитель — тест
  импортирует её напрямую и использует в вычислении границы (аналогично
  `PAGE_SIZE`). Не нарушение.
- **`if not needle: return []` в `LibraryRepository.search`.** Не декоративная
  ветка: без неё `contains("")` в SQL вернул бы «истина» для всех строк
  (любая строка содержит пустую подстроку), и пустой/пробельный запрос
  показывал бы всю библиотеку — ровно то поведение, которое запрещено
  спекой. Ветку сторожит `test_an_empty_query_finds_nothing` (запрос
  `"   "`, `strip()` превращает его в `""`). Не нарушение.

### Правило 2 / 6 — место `in_order`, одна ответственность

Перенос образования `in_order` из `LibraryService.page` в
`ViewsRepository.in_order` — обоснован. По букве задача 5 фиксирует «порядок
восстанавливает сервис», но по существу причина решения была другая:
«сортировка принадлежит запросу раздела, а не сборке карточек» — то есть
`views_for` не должен *хранить* порядок в словаре. Это условие не нарушено:
`in_order` по-прежнему получает словарь без порядка и восстанавливает его по
уже готовому списку id, который приносит вызывающий (раздел либо поиск).
Второе появление тех же трёх строк — ровно тот случай, когда правило 3
требует выноса, а `ViewsRepository` — тот модуль, который уже отвечает за
«собрать карточки для показа»: упорядочить то, что сам же собрал, не
разрывает эту ответственность на «и». Альтернатива (отдельная свободная
функция вне обоих классов) не выигрывает ничего, кроме формального сохранения
буквы прежнего решения.

Единственное следствие переноса, заслуживающее внимания: тестовый дублёр
`Forgetful` в `tests/backend/test_feed.py` пришлось превратить из
композиции (`Forgetful(views, lost)`) в наследника `ViewsRepository`, чтобы
переопределённый `views_for` подхватился внутри унаследованного `in_order`
(вызов `self.views_for` — полиморфизм через `self`). Это работает, но
привязывает тестовый дублёр к внутренней реализации `in_order` (что он
вызовет `self.views_for`, а не проведёт SQL сам). Пока это единственный
наследник, и правило 7 тут ни при чём (наследование — не абстракция,
заведённая заранее, а приём для теста над уже существующим конкретным
классом) — но если `in_order` когда-нибудь перестанет обращаться к
`views_for` через `self`, `Forgetful` перестанет ловить сценарий тихо, без
ошибки импорта. Не блокирует, но стоит держать в уме при следующей правке
`in_order`.

### Правило 7 — абстракция со второй реализацией

`docs/module-map.md` добавил `ViewsRepository` в раздел «Абстракции с одной
реализацией» (наследник — `Forgetful`). Это не нарушение: `ViewsRepository` —
не абстракция, заведённая в ожидании второй реализации, а рабочий класс,
у которого впервые появился наследник (тестовый дублёр). Раздел и раньше
фиксировал такие случаи (`Base` — `Note`), это учётная запись карты, а не
сигнал о преждевременной абстракции.

### Правило 10 — логика не в интерфейсе

Не применимо к этому слайсу: интерфейса (обработчиков Qt) в диффе нет.

### Правило 11 — комментарий объясняет неочевидное

`ViewsRepository.in_order`, docstring:

```python
async def in_order(self, item_ids: list[int]) -> list[CardView]:
    """Карточки в порядке спрошенных номеров: порядок принадлежит тому
    запросу, который их выбрал, а словарь его не хранит.

    Пропавшая между двумя запросами карточка тихо выпадает: удалить её
    человек мог ровно в этот промежуток, и ронять из-за неё всю выдачу
    незачем."""
```

Оба абзаца объясняют неочевидное: почему порядок не хранится в словаре (первый)
и почему пропажа карточки не роняет вызов (второй) — оба решения не читаются
из кода построчно, оба стоило записать. Комментарий унаследован дословно от
прежнего места (`LibraryService.page`), пересказом кода не стал.

`LibraryRepository.search` — комментарий объясняет отличие от `find_by_title`
и назначение `autoescape` — тоже по делу, не пересказ.

### Правило 13 — тест проверяет поведение, а не объявление

По каждому из 10 тестов `tests/backend/test_search_local.py`:

| Тест | Что проверяет | Что уронит |
|---|---|---|
| `test_a_substring_is_enough` | вхождение подстроки в название | `.contains()` заменённый на `==` (целое совпадение) |
| `test_the_case_does_not_matter_in_russian` | регистронезависимость на кириллице | `folded()`/`fold()` заменённые на сырое сравнение |
| `test_the_original_title_is_searched_too` | второе название тоже участвует | снятая ветка `OR original_title` |
| `test_the_type_of_content_never_mixes` | отбор по `kind` | снятое условие `item_table.c.kind == kind` |
| `test_a_percent_sign_is_a_letter_and_not_a_wildcard` | `%` — буква, не джокер | снятый `autoescape=True` |
| `test_the_found_cards_are_whole` | найденное — полная `CardView` (оценка, теги) | подмена сборки на «голые» номера вместо `in_order`/`views_for` |
| `test_an_empty_query_finds_nothing` | пустой/пробельный запрос — не «показать всё» | снятая ветка `if not needle: return []` |
| `test_the_alphabet_orders_the_found` | устойчивый порядок по алфавиту, включая порядок сборки после `views_for` (id создания не совпадает с алфавитным) | снятый `order_by(title)` в SQL **и** нарушение порядка id при сборке в `in_order` |
| `test_no_more_than_a_portion_comes_back` | предел применяется и равен `SEARCH_SIZE=20` (жёсткая проверка значения константы плюс поведенческая проверка длины) | забытый `.limit()`, забытая передача `limit` в `SearchService.local`, изменённое значение `SEARCH_SIZE` |
| `test_the_search_does_not_touch_the_clock` | поиск не завязан на `synced_at`/время | случайно добавленный фильтр по сроку годности синка |

Все десять проверяют следствие («что видно снаружи»), а не факт объявления —
правилу 13 соответствуют. `test_no_more_than_a_portion_comes_back` — образец
двойной защиты (как и `test_a_portion_is_fifty_and_it_is_applied` в
`test_feed.py`): жёсткое `assert SEARCH_SIZE == 20` ловит смену константы,
поведенческая часть — что она действительно применяется в двух местах
(репозиторий и сервис).

Мутация «пропавшая карточка роняет выдачу» в этом файле не тестируется
напрямую — она ловится `test_a_card_lost_between_the_two_queries_drops_out`
в `test_feed.py`, потому что защита теперь общая (`ViewsRepository.in_order`)
и покрывает оба вызывающих. Команда прогона включает оба файла, поэтому
разрыва в подтверждённом покрытии нет.

## Чего не хватает

**Основной пробел: поиск по разделу игр (`Kind.GAME`) как положительный
сценарий не проверен вовсе.** Единственный тест с `Kind.GAME`
(`test_the_type_of_content_never_mixes`) заводит игровую карточку и ищет её
*отрицательно* — вызовом `search.local(Kind.MOVIE, ...)`, который должен её
не найти. Ни один тест не вызывает `search.local(Kind.GAME, ...)` и не
проверяет, что игра действительно находится. Правдоподобная поломка: параметр
`kind` в `LibraryRepository.search`/`SearchService.local` перестаёт
использоваться и жёстко замещается на `Kind.MOVIE` (например, опечатка при
рефакторинге сигнатуры) — весь набор из 10 тестов останется зелёным, потому
что все они вызывают поиск только с `Kind.MOVIE`. Раздел игр в этот момент
перестанет находить вообще что угодно, и узнают об этом только руками.

Второстепенно: подчёркивание `_` в запросе как обычный символ — проверен
только `%`. Ручной эксперимент (`c.contains('50% off_deal', autoescape=True)`
→ `... ESCAPE '/'` с экранированием обоих знаков) подтверждает, что
`autoescape=True` уже гасит `_` тоже, то есть в текущем коде это не баг — но
ни один тест этого не фиксирует. Если `autoescape=True` когда-нибудь заменят
на ручное `.replace('%', ...)`, забыв про `_`, ни один из 10 тестов не
покраснеет.

Не является пробелом: пустая строка `""` против строки из пробелов (`"   "`)
— оба входа проходят один и тот же путь `query.strip()`, отдельная проверка
не добавила бы уверенности. `original_title IS NULL` при поиске — обходится
той же `folded()`, что и в уже проверенном на NULL `find_by_title`
(`test_a_null_title_does_not_break_the_search_for_duplicates`); прямой тест
на search-е не написан, но риск закрыт по аналогии, а не голословно.

## Вывод

Согласен с обоими намеренными отклонениями:
- со снятием `sources`/`genres` у `SearchService` — правило 8 требует
  сегодняшнего потребителя, а `local()` их не трогает;
- с переносом `in_order` в `ViewsRepository` — перенос сохраняет суть
  решения задачи 5 («словарь не хранит порядок»), устраняет второе появление
  тех же трёх строк и остаётся в рамках ответственности модуля.

Единственная оговорка — тестовый дублёр `Forgetful` теперь наследует
`ViewsRepository` вместо обёртки над ним, что не нарушение, но новая связка,
за которой стоит следить при дальнейшей правке `in_order`.

**Готово к коммиту: с правками.** Рекомендация — один короткий тест на
позитивный поиск в `Kind.GAME` (единственный найденный пробел, где
правдоподобная поломка проходит весь набор незамеченной); тест на `_` можно
добавить тем же слайсом или сознательно отметить как не покрытый, по примеру
задачи 5 плана.
