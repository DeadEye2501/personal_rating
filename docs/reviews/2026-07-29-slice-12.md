## Итог

SQLite и никакого наблюдаемого следствия не имеют. Остальные шесть складываются

## Настоящие дыры

### 1. `delete` может не смотреть на свой аргумент

```
delete(poster).where(poster.c.item_id == item_id)
      →  delete(poster).where(poster.c.item_id == 1)     ← 12 зелёных
```

Все три теста удаления работают с карточкой номер 1: `test_delete` кладёт 1 и
удаляет 1, `test_delete_takes_only_the_asked_picture` кладёт 1 и 2 и удаляет
снова 1, `test_deleting_what_is_not_there_is_quiet` удаляет из пустого. Поэтому
`delete`, всегда сносящий первую карточку, проходит всё насквозь.

Закрывается одной правкой в `test_delete_takes_only_the_asked_picture` —
удалять вторую, а не первую:

```python
    await posters.put(1, PICTURE, now=WHEN)
    await posters.put(2, OTHER, now=WHEN)

    await posters.delete(2)

    assert await posters.has(2) is False
    assert await posters.get(1) == PICTURE
```

Проверено: с этой правкой мутация ловится, и прежняя мутация «`where` потерян»
продолжает ловиться тем же тестом.

### 2. `has` может сравнивать «не меньше» вместо «равно»

```
where(poster.c.item_id == item_id) + one_or_none()
      →  where(poster.c.item_id >= item_id) + first()   ← 12 зелёных
```

В хранилище лежит карточка 1, спрашивают про 999 и про 1. При сравнении «не
меньше» ответ на 999 всё равно «нет» — строк больше 999 нет, — а на 1 всё равно
«да». Дыра тем заметнее, что докстринг `test_missing_poster_is_not_an_error`
обещает сторожить ровно это: «проверка без сравнения с карточкой прошла бы
молча». Исполнитель закрыл случай «`where` вовсе нет», а случай «`where` не
тот» остался.

Закрывается одной правкой того же теста — спрашивать про карточку **меньше**
лежащей:

```python
    await posters.put(5, PICTURE, now=WHEN)

    assert await posters.get(1) is None
    assert await posters.has(1) is False
    assert await posters.has(999) is False
```

Проверено: с этой правкой мутация ловится.

### 3. `close` не проверяется ничем, а следствие у него есть

Три мутации молчат:

| мутация | результат |
|---|---|
| `close` целиком заменён на `return` | 12 зелёных |
| `close` без проверки `if self._engine is not None` | 12 зелёных |
| фикстура не зовёт `close` вовсе | 12 зелёных |

Если это и есть часть «мутаций без наблюдаемого следствия», то утверждение
неверно — следствие прямое и на Windows видно сразу. Замер:

```
close вызван:    файл удалён
close не вызван: PermissionError [WinError 32] файл занят другим процессом
```

Неотпущенный SQLite держит файл открытым: базу нельзя ни удалить, ни перенести,
ни заменить восстановленной копией. Это ровно то поведение, ради которого
`close` и написан, и наблюдается оно в одну строку:

```python
async def test_close_lets_go_of_the_file(tmp_path):
    """Закрытие отпускает файл: неотпущенный SQLite держит его открытым, и
    базу нельзя ни удалить, ни перенести."""
    path = tmp_path / "posters.db"
    store = PosterStore(path)
    await store.open()
    await store.put(1, PICTURE, now=WHEN)
    await store.close()

    path.unlink()
    assert not path.exists()
```

Проверено: тест зелёный на чистом коде и краснеет на «`close` — `return`».

### 4. Повторный `open` теряет первый движок

```python
self._engine = create_engine(self._path)
self._engine = create_engine(self._path)   ← 12 зелёных
```

Замер того же вида: после `open(); open(); close()` файл по-прежнему занят, а
после `open(); close()` — свободен. Первый движок не отпускается никогда, и его
соединение живёт до конца процесса. Сегодня повторно `open` никто не зовёт, но
класс от этого не защищён и это не проверено.

Решить надо явно, одно из двух: либо `open` сперва отпускает прежний движок,
либо принимается, что звать его дважды нельзя, и решение записывается в план.
Молчаливого третьего варианта быть не должно, потому что `close` от неоткрытого
состояния как раз защищён — защита есть с одной стороны и отсутствует с другой.

## Молчат по устройству, и это правда

Шесть мутаций проверены и признаны не имеющими наблюдаемого следствия — здесь
утверждение исполнителя подтверждается:

| мутация | почему молчит |
|---|---|
| `data` BLOB → Text | SQLite типизируется динамически и байты в TEXT-колонке не перекодирует |
| `data` `nullable=False` снят | до NULL не дотянуться: `put` всегда подставляет оба значения |
| `fetched_at` `nullable=False` снят | то же |
| `item_id` Integer → Text | снова динамическая типизация: значение ходит туда и обратно неизменным |
| ключ переехал на суррогат, `item_id` остался `unique` | семантика сохранена; вариант **без** `unique` ловится одиннадцатью тестами |
| таблица переименована | переименование согласованное, `posters.db` снаружи модуля не читает никто |

Важно, что объявление типа не сторожится, а **поведение сторожится**: подмена
байтов строкой прямо в `get` (`value.decode()`) ловится шестью тестами. То есть
дыры здесь нет, но докстринг `test_bytes_come_back_exactly_as_written`
(«пройди она через кодировку, PNG перестал бы открываться») обещает больше, чем
тест может: смену типа колонки он не увидит.

## Что ловится — полный список пойманных мутаций

Разрешение конфликта: конфликт не разрешается вовсе; `do_nothing` вместо
`do_update`; обновляется только `data`; обновляется только `fetched_at`;
`index_elements` указывает не на ту колонку.
Чтение: `where` потерян в `get`; сравнение перевёрнуто; отдаётся не та колонка;
отдаётся строка целиком; `get` всегда пусто.
`has`: `where` потерян; ответ перевёрнут; всегда «нет»; всегда «да».
`delete`: `where` потерян; сравнение перевёрнуто; не делает ничего.
Транзакции: `begin` → `connect` в `put`; то же в `delete`.
Схема и файл: таблица не создаётся; создаётся пустая схема; `fetched_at` не
временного типа; время режется до даты; ключ не ключ вовсе; база берётся из
другого файла; база в памяти вместо файла; картинка режется; `item_id` в
`put` игнорируется; фикстура не открывает хранилище; фикстура берёт другой файл.

## Мёртвых тестов нет

Каждый из двенадцати падает хотя бы на одной мутации. Отдельно проверено
`test_a_stored_poster_is_there`, добавленный исполнителем сверх плана: он —
единственный, кто ловит «`has` всегда отвечает нет». Место своё оправдывает.

`test_bytes_come_back_exactly_as_written` в одиночку не ловит ничего: всё, что
ловит он, ловит и `test_put_and_get` сравнением с эталоном. Удалять не
предлагаю — он называет отдельное свойство, — но докстринг надо привести в
соответствие с тем, что он на самом деле сторожит (см. выше).

## Соответствие плану и спекам

Совпадает: ключ `item_id`, а не хеш адреса; отдельный файл рядом с основной
базой; шесть методов ровно с теми сигнатурами, что в разделе «Интерфейсы»;
обрезка 2:3 не тащится сюда; внешних ключей к основной базе нет.

Отклонения от плана — три, все в лучшую сторону:

1. **`PosterStore` в `conftest.py` импортируется наверху, а не внутри функции.**
   Причина, по которой план предлагал импорт внутри («модуля ещё нет»), к
   моменту написания фикстуры истекла. Наверху — правильно: правило 2 и `E402`
   против импорта под кодом.
2. **`WHEN` берётся из `conftest.MOMENT`, а не заводится своей константой.** Так
   уже сделано в `test_wishlist.py` — единый момент времени на сюиту вместо
   четвёртой копии даты.
3. **Тестов двенадцать вместо шести.** Все шесть плановых на месте, добавленные
   шесть проверяют байтовость, разделение карточек, обратную половину `has`,
   сдвиг времени, точечность удаления и переживание перезапуска.

Расхождения со спекой — два, оба мелкие, но назвать надо:

- **`data` объявлена `nullable=False`, а в спеке `NOT NULL` стоит только у
  `fetched_at`.** Ужесточение разумное; либо принять и поправить спеку, либо
  снять.
- **Докстринг `test_second_put_moves_the_fetch_time` противоречит спеке.** Он
  говорит: «по нему решают, не пора ли перезабрать постер». Спека говорит
  обратное: «Пока карточка есть, обложка не подменяется: перезапрос по сроку её
  не касается». Колонка спекой предусмотрена и остаётся, но обоснование в
  докстринге надо переписать. Заодно стоит отметить: читателя у `fetched_at`
  сегодня нет нигде — колонка пишется и не читается.

Отдельно про этот же тест: он сам открывает движок по пути
`tmp_path / "posters.db"`, повторяя выбор имени, сделанный фикстурой. Мутация
«фикстура берёт другой файл» это подтвердила — тест краснеет. Не дефект, но
связь неявная: другого способа прочитать `fetched_at` у хранилища нет, и стоит
либо сказать это комментарием, либо отдать путь из фикстуры.

## Манифест против всего проекта

Читал `docs/module-map.md` целиком.

**Правило 7, `PosterStore` не наследует `Repository` — оправдано.** `Repository`
объявлен как «работа с **основной** базой через фабрику сессий» и принимает
готовый `async_sessionmaker`; три его помощника — сессионные. `PosterStore`
владеет собственным движком, имеет жизненный цикл `open`/`close`, ходит ядром
SQLAlchemy и ORM-отображения не имеет вовсе. Наследование потребовало бы завести
сессии поверх своего движка ради таблицы, у которой нет модели, и не
переиспользовало бы ни строки. Это не пропущенный дубль.

**Правило 6 — замечание, не нарушение.** `posters.py` держит и объявление
таблицы, и класс доступа, тогда как у основной базы это разведено по
`storage/tables/` и `storage/repository/`. При 82 строках и одной таблице
разделение дало бы два файла по сорок строк; докстринг модуля описывает его
одной фразой без «и». Асимметрию стоит помнить, если файл начнёт расти.

**Правило 8 — проверка `if self._engine is not None` в `close`.** Потребителя
сегодня нет, и мутация «снять проверку» молчит. Держать её стоит: она делает
`close` идемпотентным, а тесты зовут его в разборке фикстуры. Но тогда её надо
и проверить, и согласовать с `open` — см. дыру 4.

**Правило 3, повторы.** Четыре метода делятся общим двухстрочным узором
`async with self._engine.…() as connection: await connection.execute(…)`.
Выносить не предлагаю: три из четырёх различаются и способом соединения, и
разбором результата, а обёртка на два вызова читаемости не добавит.

**Прочее.** Комментарии осмысленные, оба объясняют неочевидный выбор (ключ по
карточке, кириллица в байтовом литерале) — правило 11 соблюдено. Широких
`except` нет, подавлений проверок нет, файл 82 строки, самая длинная функция 11
строк. Карта модулей в основном дереве пересобрана и `PosterStore` содержит.

## Жизненный цикл движка — замеры

| действие | что происходит |
|---|---|
| `get`/`has` до `open` | `AttributeError: 'NoneType' object has no attribute 'connect'` |
| `put`/`delete` до `open` | `AttributeError: 'NoneType' object has no attribute 'begin'` |
| `close` до `open` | проходит молча |
| `get` после `close` | `AttributeError: 'NoneType' object has no attribute 'connect'` |
| `open` дважды, потом `close` | файл остаётся занятым |

Обращение к неоткрытому хранилищу даёт сообщение про `NoneType`, по которому
причину не понять. Требования на это ни в плане, ни в спеке нет, и заводить
проверку в каждом методе ради несуществующего потребителя — против правила 8.
Но состояние «не открыт» класс уже различает в `close`, и различает
непоследовательно: там оно предусмотрено, здесь падает. Это надо либо
выровнять, либо записать как принятое решение.
