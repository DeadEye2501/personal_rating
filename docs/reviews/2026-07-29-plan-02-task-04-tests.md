# Ревью — задача 4 плана `2026-07-27-sources.md`: тесты слайса

Измерение: тесты этого слайса (поиск в TMDB). Незакоммиченная работа в рабочем
дереве: `backend/model/search.py`, `backend/sources/tmdb/{client,parse}.py`,
`tests/backend/sources/{conftest,test_tmdb_search}.py`.

## Сильные стороны

- Тела ответов честно берутся из записанных фикстур `tests/fixtures/tmdb/search_movie.json`
  и `search_tv.json` (проверено: реально живые данные TMDB — «Интерстеллар»,
  «Andor», кириллица на месте, просто консоль Windows её транслитерирует при
  печати). Исключение — четыре теста с телом прямо в тесте
  (`test_a_movie_read_by_the_series_rules_loses_its_title`,
  `test_the_year_comes_from_the_date_of_the_right_type`,
  `test_a_date_that_is_not_a_date_leaves_the_year_empty`,
  `test_a_candidate_without_a_poster_gets_no_url`,
  `test_a_body_that_is_not_a_search_result_becomes_a_refusal`) — все проверяют
  граничные случаи (пустая дата, `poster_path: null`, чужой тип содержимого,
  битое тело), которые в двух имеющихся фикстурах живьём не встречаются или
  встретились бы случайно; это оправданное исключение, а не лень записать.
- Набор шире восьми тестов из плана (шестнадцать) — добавлены год, постер без
  URL, состав перехватываемых исключений, проброс готового отказа сквозь
  клиента. Значимая часть находок из списка «уже проверено исполнителем»
  (12 мутаций) подтверждена чтением — они действительно ловятся.
- `test_a_refusal_from_the_wire_passes_through_untouched` и
  `test_a_body_that_is_not_a_search_result_becomes_a_refusal` — редкий случай,
  когда тест называет причину отказа (`Reason.NETWORK` vs `Reason.BROKEN`) и
  это реально разные пути кода, а не просто «результат — Refusal».
- `bad_key.json` / `not_found.json` в фикстурах не используются в тестах
  задачи 4 — это правильно: классификация HTTP-кодов явно отложена в самом
  плане до задачи 6 (строка 1202: «Классификация кодов появится в задаче 6 —
  здесь ответ разбирается только на успешном пути»). Отсутствие теста на них
  здесь — не дыра, а точное соответствие границе слайса.

## Находки

### Важно (Should Fix)

1. **`backend/sources/tmdb/parse.py:22`, дыра: список обрезается — ни один
   тест не заметит.** Мутация `for row in payload.get("results", [])[:1]:`
   (использован только первый элемент выдачи) прогнана и возвращена — весь
   пакет `tests/backend/sources` остаётся зелёным (45/45). Ни один тест не
   проверяет **количество** элементов в `hits` — только `hits[0]` или
   отфильтрованные подмножества. Значит порванный цикл, ошибка `break` вместо
   `continue`, случайный слайс — ничего этого набор не поймает, а в
   `search_movie.json` и `search_tv.json` больше одного результата специально
   для такой проверки. Почини: добавь
   `assert len(hits) == len(fixture("tmdb/search_movie.json")["results"])`
   (или простое `assert len(hits) == 2`) в один из существующих тестов на
   `search_movie.json`.

2. **`backend/sources/tmdb/parse.py:28`, дыра: `source_id` может стать не
   строкой.** Мутация `source_id=row["id"]` (без `str()`) прогнана и
   возвращена — набор зелёный. `first.source_id` в
   `test_search_gives_candidates_not_cards` проверяется только на истинность
   (`assert first.source_id`), а `int` истинен так же, как строка. Контракт
   `SearchHit.source_id: str` не проверяется в рантайме (`dataclass` без
   валидации), поэтому это единственная линия защиты. Почини:
   `assert isinstance(hits[0].source_id, str)` в том же тесте, либо
   `assert hits[0].source_id == "157336"` (id из фикстуры) — второе строже и
   заодно перестаёт быть «проверкой объявления», а проверяет фактическое
   поведение разбора.

3. **`backend/sources/tmdb/client.py:24`, дыра: `api_key` можно не отправлять
   вовсе.** Мутация `return {"language": LANGUAGE, **extra}` (без
   `"api_key": self._key`) прогнана и возвращена — весь пакет остаётся
   зелёным. `test_client_asks_the_right_endpoint_and_language` проверяет
   `"language=ru-RU" in seen["url"]` и `"query=" in seen["url"]`, но не
   `"api_key=" in seen["url"]`. В реальности TMDB без ключа ответит 401, и
   ровно этот путь ничем не защищён на уровне «ключ доехал до запроса».
   Почини: добавить `assert "api_key=k" in seen["url"]` в тот же тест.

4. **`backend/sources/tmdb/parse.py:18`, дыра: `original_title` фильма может
   тихо взять значение `title`.** Мутация
   `original_key = "original_name" if is_series else "title"` прогнана и
   возвращена — весь пакет зелёный. Ни один тест на `search_movie.json` не
   проверяет `original_title` вообще — есть проверка `original_title` только
   для сериалов
   (`test_series_are_parsed_from_their_own_fields`, и там лишь истинность).
   В фикстуре `title` = «Интерстеллар», `original_title` = `Interstellar` —
   разные строки, разница легко проверяется. Почини: добавь
   `assert hits[0].original_title == "Interstellar"` (или хотя бы
   `!= hits[0].title`) в тест на `search_movie.json`.

### Мелочь (Nice to Have)

5. **`backend/sources/tmdb/parse.py:32`, `synopsis` не проверяется вовсе.**
   Ни один тест не читает `hit.synopsis`. Мутация вроде `row.get("overviews")`
   (опечатка в ключе) прошла бы молча. Не критично — поле декоративное для
   первого круга загрузки, но раз остальные поля разбора покрыты по одному,
   стоило бы и это для симметрии.
6. **`backend/model/search.py`** — чистый датакласс без логики, дополнительно
   мутировать нечего сверх того, что уже покрыто через `parse_search`;
   отдельного файла тестов на сам тип нет, и это нормально — поведения в нём
   нет, только форма.
