#### 2. Девять строк в двух экранах совпадают дословно

`client/app/LibraryScreen.svelte:113-137` против

#### 3. Правило отбора написано по обе стороны границы и не сторожится ничем

`client/state/filters.js:107-125` против
`backend/storage/repository/sections.py:60-103`.

Одно правило четырьмя частями, и обе записи должны совпадать во всех четырёх:
внутри тега и жанра — «и» (`every` против `_carrying_all` с
`count(distinct) == len(set(ids))`); внутри оценки — «или» (`some` против
`IN`); исключённое — «ни одного из этих» (`some(...) → false` против
`not_in`); неоценённое исключением по оценке не задевается (`has = []` против
явного `_COLUMN.is_(None) |`).

Сегодня они совпадают — проверено по обоим телам. Что связь настоящая, видно по
истории: коммит `4f3e90a` («фильтры сужают, а не расширяют») правил обе стороны
одним диффом, потому что иначе поиск и лента показали бы на тех же двух метках
разные наборы. Сам `filters.js:98-101` это и обещает: «Правило при этом одно на
обе стороны, и разъехаться им нельзя».

Обещание не подкреплено ничем. `tests/bridge/test_page_contract.py` сторожит
шестнадцать пар границы, и все они про **имена**; правило отбора туда не входит.
Записи в `docs/not-duplicates.md` тоже нет: там есть `_included ≠ _excluded`
(строка 59), но пары «фронт против SQL» нет ни одной.

**Что оставить:** обе реализации — одну убрать нельзя, SQL на странице не
исполнить, а тащить каждый кандидат поиска через базу значит писать в неё то, что
в неё попадать не должно. Чинится не выносом, а сторожем: либо пара в
`docs/not-duplicates.md` с доводом «слить нечем» (тогда отпечаток вернёт её в
разбор при правке любой стороны), либо, что лучше, — проверка в
`test_page_contract.py`, сверяющая по набору примеров, что `passes` и `_narrow`
отбирают одно и то же. Первое дёшево и делается сейчас; второе — заявка, не
вердикт.

#### 4. Среднее по непустым посчитано дважды — на странице и в модели

`client/state/scores.js:52-56` против `backend/model/rating.py:6-12`.

```js
export function average(values) {
  const given = values.filter((value) => value !== null && value !== undefined)
  if (!given.length) return null
  return given.reduce((sum, value) => sum + value, 0) / given.length
}
```

```python
def average_score(*aspects: int | None) -> float | None:
    filled = [aspect for aspect in aspects if aspect is not None]
    if not filled:
        return None
    return sum(filled) / len(filled)
```

Одно правило, два языка, оба докстринга объясняют его одними словами («деление на
три занизило бы втрое»). Довод у страницы есть и он верен (`scores.js:58-61`):
пока человек проставляет три шкалы игры, ответа базы ещё нет, а число под
звёздами меняться обязано.

Цена, которую довод не покрывает: у игры **показанное** число всегда считает
страница (`Film.svelte:22` зовёт `meanOf`, а не читает `rating.score`), тогда как
сортировка, фильтр по оценке и гистограмма считают по тому, что записал
`average_score`. Разойдись формулы — карточка покажет одно, а столбец и порядок в
ленте будут про другое, и оба набора тестов останутся зелёными: питон проверяет
свою, Vitest — свою.

**Что оставить:** обе, по тому же доводу, что и у пары №3, — и с той же починкой:
запись в `docs/not-duplicates.md` как минимум, проверка «на одном наборе шкал обе
стороны дают одно число» как максимум. Отпечаток тут особенно уместен: тело
`average_score` короткое, и правка в нём выглядит безобидной.
