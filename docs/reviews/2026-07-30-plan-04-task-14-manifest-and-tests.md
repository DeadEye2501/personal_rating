Прогон: `pytest tests/backend/test_by_credit.py tests/backend/test_credits.py

Мутации исполнителя (список из задания) сверены построчно с кодом и с тем, что
каждая из них должна ронять — все соответствуют актуальному коду `items_of`

(«отбор по человеку снят», «предел не применяется») действительно требовали
второго человека и пятой карточки — оба условия в финальном тесте выполнены

## Правило 2 — место для кода

`items_of` лежит в `CreditRepository` (`backend/storage/repository/credits.py`,
L194–218). По `docs/module-map.md` ответственность модуля — «всё, что
приложение делает в базе с человеком или студией как с сущностью: их строки, их
роли на карточках и подсказка при вводе имени». Метод — прямое продолжение этого
списка («что ещё связано с этой сущностью»), использует уже заведённые в модуле
`self._entity`, `self._link`, `Repository._rows`. Второго кандидата на место
нет: `ViewsRepository` собирает уже готовые карточки по списку id, а не ищет
id по человеку. **Место верное.**

## Правило 6 — одна ответственность на модуль

Докстринг модуля не изменился и не потребовал изменения — `items_of` не
добавляет модулю новой обязанности, только новый запрос к уже описанным
таблицам. Нарушения нет.

## Правило 7 — абстракция со второй реализацией

Новых абстракций не заведено. `items_of` пользуется уже существующей
generic-схемой `Entity`/`self._entity`, обкатанной на `people`/`companies` с
плана 3. Нарушения нет.

## Правило 8 — ничего на всякий случай

- **`distinct` нужен.** `PrimaryKeyConstraint("item_id", "person_id", "role")`
  у `person_credit` (`backend/storage/tables/catalog.py:86`) допускает две
  строки на одну карточку для одного человека (режиссёр + актёр) — без
  `distinct` `item.c.id` продублируется. Проверено чтением схемы и тестом
  `test_both_roles_of_one_person_give_one_card`. **Обоснован.**
- **`limit`/`offset` — сегодня их передают только тесты.** Grep по всему
  проекту: `items_of` не зовёт ни `backend/app.py`, ни `LibraryService`, ни
  клиент — `LibraryService.views_of` сознательно не заведён (задокументировано
  заданием и подтверждено: в `backend/service/library.py` такого метода нет, а
  `in_order` уже раньше переехал в `ViewsRepository.in_order`, которым
  пользуются `page` и `local`). Формально это «параметр без сегодняшнего
  потребителя». Но: (а) сигнатура — часть контракта, зафиксированного планом
  (`CreditRepository.items_of(entity_id, limit, offset) -> list[int]`,
  `docs/plans/2026-07-27-reading.md:5779`); (б) весь бэкенд на этой стадии
  проекта не имеет клиента вовсе — тем же критерием пришлось бы браковать
  `LibraryService.page`, `SectionsRepository.ids` и любой другой метод плана
  1–4, что абсурдно для бэкенд-сначала разработки; (в) оба параметра реально
  проверены тестом `test_a_portion_is_taken_from_the_offset` (не просто
  объявлены). **Не считаю нарушением** — с оговоркой отметить в отчёте, не в
  коде.

## Правило 11 — комментарий объясняет неочевидное решение

Докстринг `items_of` (L196–203) даёт три утверждения, проверены все три:

1. **«`distinct` обязателен...это две строки связи и одна карточка»** — верно,
   см. правило 8 выше (PK допускает 2 строки на человека+item).
2. **«Порядок — по своей оценке, высокие сверху; неоценённые следом»** — верно
   по коду (`order_by(rating.c.score.desc(), item.c.id)`) и подтверждено тестом
   `test_the_unrated_follow_the_rated`.
3. **«SQLite при `DESC` кладёт `NULL` вниз сам»** — верно по документации
   SQLite (`ORDER BY`: NULL считается меньше любого значения → при `ASC` идёт
   первым, при `DESC` — последним). Это специфика SQLite, не SQL-стандарт
   (PostgreSQL, например, по умолчанию делает наоборот — `NULLS LAST` для
   `ASC`), поэтому комментарий объясняет по-настоящему неочевидное решение, а
   не пересказывает код.

Ни одно утверждение не пересказывает код построчно — все объясняют «почему»,
не «что». **Правило 11 соблюдено.**

## Правило 13 — тест проверяет поведение, по каждому из 9

| Тест | Следствие | Ронящая строка |
|---|---|---|
| `test_everything_of_one_person_comes_back` | отбор идёт по конкретному человеку, а не по всем, у кого есть хоть одна связь (второй человек в данных не даёт мутации пройти молча) | L213 `.where(self._link == entity_id)` |
| `test_the_highest_rated_comes_first` | сортировка — по убыванию оценки | L214 `rating.c.score.desc()` (замена на `.asc()`) |
| `test_the_unrated_follow_the_rated` | неоценённые не выпадают из выдачи, а идут последними | L211 `.outerjoin(rating, ...)` (замена на `.join`) |
| `test_both_roles_of_one_person_give_one_card` | одна карточка не дублируется, если у роли два вхождения | L206 `.distinct()` |
| `test_a_portion_is_taken_from_the_offset` | `limit` и `offset` реально режут выдачу (5 карточек, не 4 — иначе порция от смещения случайно совпала бы с остатком) | L215–216 `.limit(limit).offset(offset)` |
| `test_studios_work_the_same_way` | обобщённая реализация верна и для `companies()`, не только для `people()` | любая часть L204–218, если бы она была захардкожена под `person_credit`/`PEOPLE` |
| `test_a_studio_does_not_see_the_films_of_a_person` | связь берётся из таблицы связей своей сущности, а не по совпавшему номеру | L209 `self._entity.credit` / L213 `self._link` (перепутанные местами дали бы утечку) |
| `test_a_person_with_nothing_gives_nothing` | пустая связь не роняет запрос и не выдаёт мусор | L207–213, любой join, ломающий пустой случай (напр. `join` вместо `outerjoin` дал бы то же самое пустое — тест слабый, см. ниже) |
| `test_the_cards_come_back_whole` | список id из `items_of` пригоден как вход `ViewsRepository.in_order` — порядок и содержимое переживают сборку карточек | L204–218 целиком (интеграционная, дублирует часть L214 с тестом 2) |

**Про `test_a_studio_does_not_see_the_films_of_a_person`: `assert nolan ==
studio` — честная проверка предпосылки, не хрупкая зависимость.** Она открыто
утверждает то, от чего зависит весь смысл теста (совпадение номеров), а не
полагается на это молча. Если бы нумерация людей и студий когда-нибудь стала
общей (например, обе сущности переехали в одну таблицу с общим автоинкрементом)
— или наоборот, тестовая база стала бы создавать записи в другом порядке — тест
упал бы **на этом ассерте**, с понятным сообщением, а не давал бы ложное
зелёное на следующей строке. Ровно та форма, которую манифест требует от
неочевидной зависимости: не спрятана, а объявлена и проверена.

Слабое место — `test_a_person_with_nothing_gives_nothing`: он не отличит
`outerjoin` от `join`, не отличит правильный отбор по сущности от отбора,
всегда возвращающего пусто. Он один не самодостаточен, но избыточен по
отношению к остальным восьми — не проблема сам по себе.

## Чего не хватает — непокрытая поломка

**Снятие вторичного ключа сортировки `item.c.id` в `order_by(rating.c.score.desc(),
item.c.id)` не поймает ни один из 9 тестов.** Ни в одном тесте нет двух карточек
с одинаковой оценкой: в тесте 2 — 6.0 и 9.0, в тесте 5 — 10.0/9.0/8.0/7.0/6.0
(`10.0 - number`), везде значения разные. SQLite без второго ключа сортировки не
гарантирует стабильный порядок среди строк с равным `rating.score` — на
маленькой таблице он часто возвращает физический порядок вставки и мутация
пройдёт молча, а на реальных данных (после `VACUUM`, после update) порядок
внутри одной оценки может неожиданно поменяться между двумя запросами одной
страницы. Это ровно тот же класс, что уже поймал ревью на других страницах
ленты (задача 6) — здесь его закрыла бы всего одна карточка с оценкой, равной
уже существующей.

Проверены и остальные предложенные кандидаты — не являются поломками:
- **человек, связанный с карточкой другого типа контента (игра/фильм)** —
  `items_of` не различает `kind`, и это соответствует духу метода («всё, с чем
  связан»); не баг, а не описанное явно, но не противоречащее поведение;
- **`limit=0`** — `.limit(0)` на SQLAlchemy/SQLite даёт `LIMIT 0`, то есть
  пустой список; поведение корректно и предсказуемо, просто не покрыто тестом;
- **человек, у которого карточка удалена** — не воспроизводится: `item_fk`
  везде `ondelete="CASCADE"` (`backend/storage/tables/base.py:20-25`), а
  `PRAGMA foreign_keys=ON` включена на каждом соединении
  (`backend/storage/session.py:33`), так что строка связи удаляется вместе с
  карточкой — осиротевшего `item_id` в выдаче `items_of` появиться не может.

## Minor

- Сигнатура `items_of` разбита на две строки нестандартно для файла: соседние
  многострочные сигнатуры в этом же классе (`create`, L105–107) кладут все
  параметры с новой строки под закрывающую скобку на уровень глубже; здесь же
  первая строка держит часть параметров, а `offset` продолжает не под уровнем
  отступа, принятым в файле. Не входит в проверяемые машиной правила и не
  ломает работу — чисто согласованность стиля внутри модуля.

## Итог

Критичных находок нет. Единственная содержательная находка — непокрытая
поломка вторичного ключа сортировки (раздел выше); она не блокирует коммит
(следствие метода при равных оценках не специфицировано планом и не ломает ни
одну существующую функцию), но стоит держать в уме при следующей задаче,
которая тронет эту сортировку.

**Готово к коммиту: Да.**
