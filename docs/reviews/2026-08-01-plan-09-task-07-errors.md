# Ревью задачи 7 плана 9 — ошибки поведения

Измерение одно: поломки поведения. База — `4816348`, голова — рабочее дерево.
Читался только дифф (`bridge/search.py`, `client/app/App.svelte`,
`client/app/SearchScreen.svelte`, `client/app/Topbar.svelte`,
`client/components/SearchField.svelte`) плюс то, во что он упирается:
`bridge/answer.py`, `bridge/kept.py`, `bridge/wire.py`, `bridge/thread.py`,
`client/api/bridge.js`, `client/api/owned.svelte.js`, `client/app/trouble.js`,
`client/state/session.js`, `backend/service/people.py`, `backend/model/view.py`.

## Strengths

Проверено по коду, а не по описанию — всё названное держится:

- **Через границу потоков исключений не летит.** `Kind(kind)` стоит внутри
  лямбды, а лямбда зовётся в `BackendThread._begin`, то есть в потоке бэкенда и
  внутри `try` — кривой тип уезжает `{"fail": "broken"}` с `logger.exception`.
  Кривой `domain` (`KeyError` в `PeopleSearch._entities[domain]`) идёт тем же
  путём: отказ громкий, не молчаливый.
- **Правило 9 не нарушено ни в одном новом вызове.** `about(...).catch(lost)`
  идёт через `complaining('поиск', ontrouble)`, и молчит там ровно молчаливое
  (`cancelled`, `stale`). Отказ источника приезжает полем `refusals`, а не
  исключением, и получает свою плашку.
- **Канал выбран верно.** `about()` идёт по `'search'`, поэтому вытеснение
  работает в обе стороны: строка после клика и клик после строки одинаково
  отбрасывают чужой ответ по `latest` (`bridge.js:67`). Показанная лента при
  любом чередовании двух жестов соответствует последнему из них — проверено
  разбором четырёх порядков доставки.
- **`views` не «остаётся от прошлого жеста» после ответа:** `about()` пишет весь
  список целиком, а не доливает.
- **Отмена заведена.** Номер кладётся в `ops`, `owned()` гасит его при уходе с
  раздела; `_person` пишет в память после `await`, поэтому отменённый запрос
  полупустой памяти не оставляет.
- **`_asked` не пишется намеренно, и это верно:** второго шага у жеста нет,
  `external` за ним не зовётся.
- **`to_wire` словарь из `_person` переваривает** (ветки `dict` и `tuple` есть),
  так что `ExternalSearch`-подобная форма доезжает разобранной.
- **`withSection(session, 'search')` при уже открытом поиске отдаёт тот же
  объект** (`session.js:27`), поэтому клик по имени внутри поиска не пересоздаёт
  `{#key session.section}` и не роняет разметку. Клик из библиотеки, наоборот,
  пересоздаёт раздел с пустым `views` — то есть старой выдачи там не видно.
- **Сторож «мост → бэкенд» новый вызов покрывает сам:** `back.finder.by_entity`
  собирается разбором и сверяется с `PeopleSearch.by_entity` по числу доводов
  (три). Сторож «страница → мост» (`called <= surface`) на `search.by_person`
  тоже зелёный.
- **Кандидат из внешней выдачи кнопок с именами не даёт вовсе** —
  `view_from_hit` не заполняет ни `people`, ни `companies`, — поэтому
  `entity_id: None` до `by_entity` не доходит.

## Issues

### Critical (Must Fix)

**1. `bridge/search.py:79-82` — `_person` захватывает память моста, не спросив,
его ли ещё очередь. После этого «звезда» на карточке молча перестаёт работать.**

```python
async def _person(self, back, op, domain, entity_id, kind):
    answer = await back.finder.by_entity(domain, entity_id, kind)
    self._kept.put(op, list(answer.views))
```

`Kept` держит **ровно одно** значение (`bridge/kept.py:12-24`), и `_outer` из-за
этого проверяется прямо (`search.py:71-75`): «пока летел ответ, страница могла
захватить ячейку под свою выдачу». У `_person` такой проверки нет, а он —
**первый писатель в эту ячейку, который ходит в сеть**: `by_entity` делает
`/search/person` и `gather` по фильмографиям, то есть от сотен миллисекунд до
20 секунд. `_own` рядом тоже пишет без проверки, но он локальный SQLite и
разъехаться успевает разве что теоретически.

Достижимый ход, самый обычный из двух:

1. клик по режиссёру — `by_person(op=N)`, TMDB думает;
2. человек не дождался и щёлкнул по актёру — `by_person(op=N+1)`, ответ пришёл
   первым, лента показывает его (страница сверяет `latest`, всё правильно);
3. доехал ответ N и делает `self._kept.put(N, …)` — **память моста теперь
   держит выдачу по первому человеку**;
4. человек жмёт звезду на карточке из показанной (второй) выдачи →
   `search.ensure(op=N+1)` → `_kept.taken(N+1)` → `None` → `stale()`.

`Failed('stale').silent === true` (`bridge.js:12`), а `onscore` ловит через
`lost` → `reported` выходит на первой строке. **Ни карточки, ни плашки, ни
записи в журнал: кнопка просто мертва**, и остаётся мертва при каждом повторном
нажатии.

Тот же итог даёт пара «клик по имени, потом строка»: строковый поиск успевает
положить свой номер, а доехавший позже `_person` его вытесняет — и звезда
умирает уже в выдаче по строке.

Почему важно: заведение карточки из выдачи — это половина смысла жеста («из неё
добавляют карточку тем же `ensure`», сказано в докстринге самого метода), и
ломается оно беззвучно. Выхода из состояния человек не найдёт: поле поиска
`byPerson` очистил, а Enter по пустому полю выдачу просто гасит.

Как чинить. Номера операций у страницы строго растут (`bridge.js:58`,
`counter += 1`), и порядок доставки на это не влияет, — значит вытеснение можно
решать в самой памяти: `Kept.put` принимает запись, только если её номер не
меньше уже удерживаемого (равенство нужно `_outer`, который приходит тем же
номером). Тогда опоздавший `_person` тихо ничего не делает, а ячейка остаётся у
того жеста, чья выдача на экране. Альтернатива — своё поле «последний
спрошенный номер», проставляемое синхронно в `local`/`by_person`, и проверка
перед `put`; она шумнее и повторяет то, что `Kept` уже знает.

### Important (Should Fix)

**2. `client/app/SearchScreen.svelte:38-43` и `45-55` — выдача прошлого жеста
остаётся на экране весь поход в сеть, а при отказе остаётся навсегда.**

```js
$effect(() => {
  const clicked = person
  if (clicked) { about(clicked, kind).catch(lost); return }
  …
})

async function about({ domain, entity_id }, forKind) {
  const answer = await numbered('search.by_person', …)
  views = answer.views
```

У строкового пути первая половина локальная и приезжает за миллисекунды —
`look()` подменяет `views` практически сразу. У клика по имени первой половины
нет: `by_person` отвечает целиком, после сети, до 20 секунд (а `DEADLINE` моста
— 60).

Всё это время лента показывает выдачу **предыдущего** жеста, и одновременно
`byPerson` уже очистил поле поиска (`App.svelte:161`). То есть экран
утверждает: «поиска нет, вот эти карточки — ответ». Если клик сделан по имени на
карточке из этой же выдачи, разницу заметить нечем вовсе.

Хуже при отказе: `broken`/`timeout`/`closed` уходят в `lost`, `views` не
трогается — плашка говорит «не удалось», а под ней продолжает лежать чужой
список, и человек читает его как результат.

Как чинить: гасить список перед походом — `views = []` первой строкой `about()`
(эффект `views` не читает, круга не будет), либо в ветке эффекта. Заодно это
уравнивает поведение с приходом из библиотеки, где `{#key}` пересоздаёт раздел и
список и так пуст.

### Minor (Nice to Have)

**3. `client/app/App.svelte:159-164` — `person` не снимается никем, кроме
`onsearch`.** Уход в «Оценённые» и возврат в «Поиск» пересоздаёт `SearchScreen`
(`{#key session.section}`), эффект видит непустой `person` и **заново идёт в
сеть** за тем же человеком. Смена типа содержимого делает то же самое, только с
другим `kind`. Поведение симметрично `query` (строка тоже переспрашивается), и
для `kind` оно даже верное — вкладка первичный фильтр, — поэтому это не поломка,
а цена, которую стоит назвать вслух: у строки повтор стоит одного локального
запроса плюс внешний, у клика — только внешнего, и он длиннее.

**4. `bridge/search.py:40-49` — `_asked` остаётся от прошлой строки.** Сегодня
недостижимо: `external` зовёт только `look()`, и номер он берёт синхронно
(`lastOp('search')` вычисляется в том же микротаске, что и возврат
`search.local`), так что чужой номер туда не попадает. Отмечаю потому, что
находка 1 меняет расклад: после починки памяти по номеру ячейка может законно
держать номер клика, и `external(этот номер)` прошёл бы проверку
`taken(op) is None` и ушёл в сеть **со старой строкой**, положив её выдачу в
память клика. Достаточно на шаге починки убедиться, что этот путь по-прежнему
никем не зовётся, или снимать `_asked` в `by_person`.

**5. `client/components/SearchField.svelte:22` — `onsearch(value.trim())` при
`typed`, хранящем необрезанное.** Расхождение косметическое: `query.text`
обрезан, `typed` — нет, и на следующем Enter та же строка уедет обрезанной
снова. Ни на выдачу, ни на снятие человека не влияет.

Проверено и находкой **не** является:

- гонка `_outer` против `_person` за память по номеру `op1`: у `_outer` проверка
  на месте, чужой номер он не перезаписывает;
- `external` после клика по имени: страница его не зовёт (ветка эффекта), а
  позванный с чужим номером он честно отвечает `stale`;
- `Kind(kind)` и кривой `domain`: оба отказывают громко, наружу исключений нет;
- эффект не подписан на `session` целиком — читает `person` и производный
  `kind`, поэтому клик по жанру поиск в сеть не гонит;
- голый `return` в обеих ветках эффекта уборщиком не становится;
- `person`/`query` не могут оказаться выставленными одновременно: оба писателя
  снимают чужое, и Svelte сводит обе записи в один прогон эффекта;
- лишний проп `person`, доезжающий до `LibraryScreen` и `StatsScreen`, они
  просто не разбирают.

## Recommendations

1. Чинить в порядке 1 → 2: первая находка — беззвучная потеря главного действия
   выдачи, вторая видна глазами и лечится строкой.
2. Починку памяти делать в `Kept`, а не в `_person`: писателей в ячейку уже трое
   (`_own`, `_outer`, `_person`), и правило «опоздавший не захватывает» одно на
   всех — разложенное по трём местам, оно разъедется молча, как уже разъехалось
   между `_outer` и `_person`.
3. При проверке живьём воспроизвести именно чередование: клик по имени → пока
   крутится, клик по второму имени → нажать звезду на показанной карточке.
   Одиночный жест обе находки прячет.

## Assessment

**Ready to merge?** No

**Reasoning:** `_person` вытесняет память моста без проверки очереди, и после
любого чередования двух жестов кнопка заведения карточки перестаёт работать
беззвучно — ни плашки, ни записи, ни выхода из состояния. Остальное правится
одной-двумя строками, но это чинится до коммита.
