## Находки

### 1. Наружу открыто то, у чего нет потребителя снаружи

**Правило 8, отчасти 6. Серьёзность: средняя.**

`FIELDS`, `values_of`, `to_item` в `library.py` объявлены публично. Ни один
другой модуль и ни один тест их не импортирует — проверено поиском по проекту:

```
grep -rn "values_of\|to_item\|FIELDS" --include=*.py .   # только library.py
```

План писал их приватными — `_FIELDS`, `_values`, `_to_item`
(`2026-07-27-storage.md:2862–2892`); при реализации префикс снят без причины,
видимой из кода.

Конвенция проекта здесь однозначная: в листовых модулях публично ровно то, что
кто-то импортирует. `backend/storage/session.py` открывает `fold`,
`prepare_connection`, `create_engine`, `session_factory` — у всех четырёх есть
потребитель в другом файле. `backend/storage/tables/base.py` открывает `item_fk`
и `genre_fk` — их зовут `catalog.py` и `mine.py`. `__all__` в проекте пишут
только пакеты-поверхности (`backend/model/__init__.py`,
`backend/storage/tables/__init__.py`), и отсутствие `__all__` в `library.py`
конвенции не противоречит — противоречит именно голое имя без `_`.

Цена не косметическая. Впереди пять репозиториев; поверхность
`backend.storage.repository.library` должна читаться как «`LibraryRepository` и
`ItemExists`», а сейчас читается как пять имён, из которых три — внутренняя
кухня превращения строки в тип.

**Что сделать:** вернуть `_FIELDS`, `_values_of`, `_to_item`.

### 2. Одна и та же четвёрка строк написана дважды

**Правило 3. Серьёзность: средняя.**

`get` и `find_by_source` совпадают целиком, кроме условия:

```python
async with self._sessions() as session:
    result = await session.execute(select(item_table).where(...))
    row = result.one_or_none()
    return to_item(row) if row else None
```

`list_by_kind` и `find_by_title` — та же история со списком:

```python
async with self._sessions() as session:
    result = await session.execute(select(item_table)...)
    return [to_item(row) for row in result.all()]
```

Это второе появление, а не третье, — правило 3 срабатывает уже здесь. Машина
такое не поймает и не поймает никогда: хук сравнивает тела функций целиком, а
здесь повтор сидит внутри тел, которые различаются условием выборки (об этом
прямо сказано в описании скилла — «повтор внутри тела функции не виден»).

Заодно это единственное место, где видно общее для всех шести будущих
репозиториев: `async with self._sessions() as session` написано пять раз в одном
классе и будет написано ещё столько же в каждом следующем.

**Что сделать сейчас — и не больше:** два приватных метода на самом
`LibraryRepository`, принимающих готовый `select`:

```python
async def _one(self, statement) -> Item | None: ...
async def _many(self, statement) -> list[Item]: ...
```

Четыре метода чтения ужимаются до «собрать запрос — позвать». Общего базового
класса репозиториев заводить **нельзя**: правило 7, второй реализации ещё нет.
Когда появится вторая (задача 10 и дальше) — тогда и смотреть, повторились ли
`_one`/`_many` дословно; сегодня это домысел.

### 3. Тест про пустые тексты не может упасть

**Правила 13 и 14. Серьёзность: средняя.**

`test_empty_texts_come_back_empty_and_not_missing` (строка 79) обещает сторожить
три `or ""` в `to_item`. Он их не сторожит: сними все три — тест останется
зелёным.

Причина в том, что NULL до `to_item` в этом тесте не доезжает. У `Item` поля
`original_title`, `synopsis`, `poster_url` имеют значение по умолчанию `""`,
`values_of` кладёт в базу именно `""`, и обратно приезжает `""`. Проверено на
живой базе, не рассуждением:

```
NULL? original_title/synopsis/poster_url: (0, 0, 0)
что лежит: ("''", "''", "''")
```

То есть тест записывает пустую строку и читает пустую строку — `or ""` в этой
цепочке не участвует. При этом сама защита нужна: колонки объявлены nullable
(`catalog.py:26,29,30`), и строки с NULL в таблице бывают — их пишет, например,
фикстура `stored` из `conftest.py`, у которой `MINIMAL["item"]` этих трёх полей
не содержит вовсе.

**Что сделать:** завести строку с NULL и прочитать её репозиторием. Готовое уже
лежит в `conftest.py` — фикстура `stored` пишет ровно минимальную строку:

```python
async def test_empty_texts_come_back_empty_and_not_missing(sessions, stored):
    item_id = await stored("item")           # в базе NULL, а не ""
    got = await LibraryRepository(sessions).get(item_id)
    assert (got.original_title, got.synopsis, got.poster_url) == ("", "", "")
```

Такой тест краснеет от снятия любого из трёх `or ""`.

Замечание в сторону: если решить, что NULL в этих колонках не бывает никогда, то
под правило 8 попадают уже сами `or ""` — защита без сегодняшнего источника
NULL. Но фикстура `stored` такой источник и есть, а задача 17 (ручные карточки)
добавит второй, так что правильный ход — чинить тест, а не убирать защиту.

### 4. `runtime` можно выкинуть из `FIELDS`, и никто не заметит

**Правило 13. Серьёзность: средняя.**

Тринадцать имён в `FIELDS` — единственное, что связывает поля `Item` с
колонками при вставке. Двенадцать из них сторожатся: убери `title`, `year`,
`kind`, `source`, `source_id`, `original_title`, `released_at`, `synopsis`,
`poster_url`, `seasons_count`, `episodes_count` — какой-нибудь тест покраснеет;
убери `synced_at` — покраснеют почти все, колонка `NOT NULL`.

`runtime` — исключение. Ни один тест не заводит карточку с непустой
длительностью: единственное упоминание — `assert stored.runtime is None` в
`test_optional_fields_survive_the_round_trip` (строка 76). Выпади `"runtime"` из
`FIELDS`, в базу уедет NULL, обратно приедет `None`, и утверждение сойдётся.
Забыть имя в этом кортеже — ровно та поломка, которую легко внести случайно при
задаче 16.

**Что сделать:** одной правкой — задать `runtime` в круговом тесте и проверить
его значение. Поле фильма, так что просить его надо у фильма, а не у сериала:
либо добавить `runtime=169` в отдельную круговую проверку для `Kind.MOVIE`,
либо развернуть `test_optional_fields_survive_the_round_trip` в два случая.

### 5. Ответственность модуля описана через «и»

**Правило 6. Серьёзность: низкая.**

Докстринг `library.py` — «Карточки: заведение новой и чтение.» Это перечисление
операций через «и», то есть ровно то, на что правило 6 и указывает как на
признак двух модулей. Здесь двух модулей нет — запись и чтение одной сущности
это одна ответственность репозитория, — но формулировка от этого не становится
верной, и она поедет в карту модулей как есть.

Хуже то, что будет дальше: задачи 15, 16 и 17 добавляют сюда удаление,
обновление и привязку, и докстринг превратится в «заведение, чтение, удаление,
правку и привязку». Описывать надо предмет, а не список операций: «Хранение
карточек библиотеки» — одна фраза без «и», которая переживёт все четыре задачи.

### 6. Докстринг `values_of` ссылается в никуда

**Правило 11. Серьёзность: низкая.**

```python
"""Карточка в вид для вставки. `id` не берётся: его выдаёт база.

Перечисления не переводятся в строку по пути: они `StrEnum`, то есть уже
строки, и в базу ложатся своим значением. Проверено тем, что читает
колонку сырой."""
```

Первые две фразы — по делу: решение неочевидное (план писал
`values["kind"] = str(item.kind)`, реализация это убрала), и объяснение
заслуженное.

Последняя фраза — «Проверено тем, что читает колонку сырой» — не называет, чем
именно проверено. Тест такой действительно есть, я его нашёл и убедился, что он
читает сырую колонку: `test_enumerations_are_stored_as_their_plain_values`
(`tests/backend/test_library.py:88`), `SELECT kind, source FROM item`, сверка с
`("series", "manual")`. То есть утверждение правдиво, но читателю оно ничего не
даёт: чтобы им воспользоваться, надо найти тест самому.

**Что сделать:** назвать тест по имени либо снять фразу — первые две её вполне
заменяют.

## Что проверено и оказалось в порядке

**Правило 1 — искали ли готовое.** Да, и это видно по коду: приведение регистра
не написано заново, а взято из `backend/storage/session.py` (`fold`) — та же
функция, что зарегистрирована в SQLite под именем `py_lower`, поэтому обе
стороны сравнения приводятся одними правилами. Это ровно то, ради чего правило 1
и существует. Похожего превращения строки базы в тип границы в проекте до сих
пор не было — искал по `to_item`, `row`, `Item(`.

**Правило 2 — место.** Новый пакет `backend/storage/repository/` отличается от
обоих соседей внятно: `tables/` объявляет схему, `session.py` открывает
соединение и фабрику сессий, `repository/` пишет и читает запросы. Ни в один из
существующих модулей это не ложится.

**Правило 7 — не рано ли абстракция.** `LibraryRepository` — не абстракция: ни
интерфейса, ни базового класса, ни фабрики, ни реестра. Это конкретный класс с
внедрённой зависимостью, а внедрение зависимостей в слое данных — принятое
решение проекта (`CLAUDE.md`, «внедряемые зависимости в слое данных»).

Класс здесь оправдан против пяти функций с первым параметром `sessions`: пять
методов пользуются одной и той же зависимостью, и вариант с функциями тащил бы
`sessions` в каждый вызов на стороне сервисного слоя. Правило 7 при этом
соблюдено буквально — общий предок репозиториев не заведён, хотя соблазн был.

Отдельно: раздел карты «Абстракции с одной реализацией» показывает
«`Exception` — наследник один: `ItemExists`». Это ложная тревога самого
`scripts/module_map.py` — он считает базовым классом что угодно, включая
стандартную библиотеку. С каждым новым исключением раздел будет шуметь сильнее;
имеет смысл научить сборщик карты не считать наследование от `Exception`
абстракцией. К слайсу это не относится, но записываю, раз увидел.

**Правило 4 и 5 — размеры.** `library.py` 124 строки, самый большой метод
`create` — 16, самая большая функция `to_item` — 20, глубина вложенности 2,
параметров не больше трёх. `test_library.py` 206 строк — до сигнала на 300
далеко.

**Правило 9 — `except`.** Единственный обработчик ловит узкий `IntegrityError` и
пробрасывает `ItemExists ... from error`. Немых обработчиков нет.

**Правило 12 — подавления.** Ни одного `# noqa`, `# type: ignore` во всём
слайсе.

**Границы слайса — чужого не захвачено.** Ни удаления (задача 15), ни
обновления (16), ни привязки (17) в `library.py` нет: только `create` и четыре
чтения, ровно как в интерфейсе задачи 9. Упоминание привязки в докстринге
`test_creating_the_same_identity_twice_is_refused` — обоснование, зачем
проверяется отказ, а не реализация задачи 17.

**Граница слоёв.** `tests/backend/test_layers.py` уже сторожит то, что новый
пакет в клиент не просочится: `ALLOWED_FROM_BACKEND` — только `backend.model` и
`backend.config`, а `test_client_takes_only_the_boundary_types_from_the_backend`
проверяет полные имена модулей, а не корневые, и в комментарии там назван именно
`backend.storage.repository`. Отдельного теста слайсу не нужно.

**Мутационная проверка остальных тестов.** Прогнал четырнадцать поломок по
`library.py` (снятая сортировка, `py_lower` → встроенный `lower`, потерянный
`strip`, выпавшее условие по источнику, по типу содержимого, равенство названия
заменено вхождением, `Kind(row.kind)` → `row.kind`, имя перечисления вместо
значения). Все, кроме разобранных в находках 3 и 4, дают красное. Тесты в целом
живые.

## Замечание к процессу, а не к коду

Прогон мутаций пришлось прервать: во время моей проверки в том же рабочем дереве
работал другой рецензент этого же слайса, и `library.py` оказался пойман в
изменённом состоянии (`kind=row.kind` вместо `kind=Kind(row.kind)`) — мутация,
которую вносил не я. Пересечение дало и ложное красное, и ложное зелёное в моём
первом прогоне, и часть результатов пришлось перепроверять чтением кода и
запросом к живой базе вместо мутаций.

Правки за собой я не оставил: `git status` в конце ревью показывает те же четыре
записи, что и в начале (`docs/module-map.md`, `tests/conftest.py`,
`backend/storage/repository/`, `tests/backend/test_library.py`) плюс отчёты
рецензентов; `pipenv run pytest -q` — 112 passed. Ни `data/`, ни `*.db` в корне
не появилось.

На будущее: рецензенты, которым нужны мутации, должны работать на своей копии
дерева (отдельный worktree), а не в общем. Иначе параллельные проверки портят
результаты друг другу, и портят молча.
