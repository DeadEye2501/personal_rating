## Critical

### 1. Ряд ответных кнопок скопирован разметкой в трёх окнах

- `client/app/ReviewModal.svelte:69-76`
- `client/app/CardModal.svelte:297-304`
- `client/components/Confirm.svelte:13-20`

**Что общего.** Первые два блока совпадают **побайтово**, включая отступы:

```svelte
    <div class="modalfoot">
      <Button variant="btn--cancel" onclick={onclose}>
        {#snippet children()}Отмена{/snippet}
      </Button>
      <Button variant="btn--go" disabled={saving} onclick={keep}>
        {#snippet children()}Сохранить{/snippet}
      </Button>
    </div>
```

У `Confirm.svelte` первая половина (обёртка и кнопка «Отмена») совпадает
дословно тоже, а вторая отличается двумя выражениями — `variant={danger ? …}`
и `{ok}` вместо литерала «Сохранить».

**Почему это повтор, а не совпадение формы.** Ряд один и тот же по решению
проекта — это записано в самом `styles/modalfoot.css:3`: «Ряд один на все окна».
Оформление у него уже общее, разметка — нет. Три места объявляют одно и то же
расположение, один и тот же порядок кнопок и одно и то же слово «Отмена».
Разъехаться они могут молча: переименуй `btn--cancel`, поменяй порядок кнопок
или слово — и два окна из трёх останутся прежними при зелёном наборе.
Компоненты по решению проекта не проверяются вовсе, так что сторожа тут нет
никакого.

**Почему это не поймала машина.** Логику на JavaScript и разметку Svelte хук не
разбирает вовсе — сравниваются только Python и CSS. `.modalfoot` как блок CSS
объявлен один раз и потому чист.

**Что должно остаться.** Один компонент `client/components/ModalFoot.svelte` —
дом тот же, где уже лежит его третий потребитель `Confirm.svelte`, и
направление слоёв (`app → components → styles`) не нарушается. Поверхность
выводится из трёх мест вызова: `ok = 'Сохранить'`, `variant = 'btn--go'`,
`disabled = false`, `oncancel`, `onok`. Выбор `danger ? 'btn--danger' :
'btn--go'` остаётся на месте вызова у `Confirm` — это его правило про
необратимое, а не правило ряда.

Прецедент выноса разметки в проекте есть и он свежий: ревью плана 8 вынесло
`.icon-btn` с общим сбросом кнопки и строку ввода по тому же поводу.

## Important

### 2. Геометрия широкого окна объявлена дважды

- `client/styles/cardform.css:6-29` — `.modal--card`
- `client/styles/review.css:6-16` — `.modal--review`

**Что общего.** Из семи обычных объявлений (не считая четырёх custom-свойств у
карточки) совпадают четыре дословно и одно по значению:

| объявление | `.modal--card` | `.modal--review` |
|---|---|---|
| `width` | `min(1080px, 100%)` | `min(1080px, 100%)` — **то же** |
| `display` | `grid` | `grid` — **то же** |
| `padding` | `34px 40px 28px` | `34px 40px 28px` — **то же** |
| `overflow` | `hidden` | `hidden` — **то же** |
| `gap` | `var(--row-gap)` (= 14px) | `14px` — **то же значение** |
| высота | `max-height: calc(100dvh - 48px)` | `height: 70dvh` |
| строки | `auto minmax(0,1fr) auto` | `minmax(0,1fr) auto` |

Совпал и комментарий, почти слово в слово: «Ничто не выходит за скруглённый
край: длинный **состав/текст** прокручивается внутри своей области, а не поверх
ряда кнопок». Один и тот же довод, написанный дважды, — верный признак того,
что и правило одно.

**Почему это повтор.** Оба окна — это одно и то же изделие: широкое окно с
прокручиваемым телом и рядом кнопок внизу. Ширина 1080 и отступы `34px 40px
28px` выбраны один раз и для одного вида; сегодня они написаны в двух файлах, и
правка одного молча оставит второй прежним. Ровно тот случай, ради которого
палитра и заведена — «цвет не пишем по месту», только тут не цвет, а размер.

**Почему это не поймала машина.** Проверка сравнивает блоки CSS по набору
объявлений; у `.modal--card` их одиннадцать против семи, и отпечатки не
сошлись. Совпадение большинства она не ловит по построению.

**Что должно остаться.** Общее уезжает в `client/styles/modal.css` — там уже
живут `.modal--narrow`, `.modal--ask` и `.modal--danger`, то есть дом для
разновидностей окна назначен раньше и не мной. В `cardform.css` и `review.css`
остаётся только разное: высота, раскладка строк и custom-свойства карточки.

Имя общего правила — решение пользователя, а не рецензента: годится и
`.modal--card, .modal--review { … }` одной строкой селекторов, и отдельный
`.modal--wide`. Значения при этом не меняются ни на пиксель — переносится
написанное, а не подбирается новое.

### 3. `patch` живёт двумя копиями, при готовом доме для него

- `client/app/LibraryScreen.svelte:113-116`
- `client/app/SearchScreen.svelte:194-196`

```js
// LibraryScreen
function patch(view, fields) {
  views = views.map((each) =>
    each.item_id === view.item_id ? { ...each, ...fields } : each)
}

// SearchScreen
function patch(view, fields) {
  views = views.map((each) => same(each, view) ? { ...each, ...fields } : each)
}
```

**Что общего.** Имя, сигнатура, дело и тело — всё, кроме предиката совпадения:
у ленты строка ищется по номеру, у выдачи поиска по паре «источник плюс
идентификатор», потому что у кандидата номера может не быть вовсе.

**Почему это повтор, а не законная пара «разные предикаты».** Проект уже
разобрал этот самый выбор и вынес его — в том же модуле, соседней функцией:

```js
// client/app/reread.js:17
export const without = (views, gone) =>
  views.filter((each) => gone.item_id != null
    ? each.item_id !== gone.item_id
    : !same(each, gone))
```

`without` и `patch` — две половины одного дела («что раздел делает со своим
списком, когда карточку записали или удалили», докстринг `reread.js:1`), и
одна из них общая, а вторая скопирована. Довод «предикат и есть вся разница»,
которым проект законно разводит `merge_fields` с `overwrite_fields` и
`_included` с `_excluded`, здесь не работает: разницы нет — `without` доказал,
что оба предиката укладываются в одно правило, и в ленте, где номер есть у
каждой строки, это правило вырождается ровно в сегодняшнее сравнение по номеру.

Оба потребителя, кстати, дописаны этим же слайсом: эффект записанной рецензии
зовёт `patch` и в `LibraryScreen.svelte:132-135`, и в
`SearchScreen.svelte:216-219`, тремя одинаковыми строками.

**Что должно остаться.** `client/app/reread.js:patched(views, view, fields)` —
рядом с `without`, тем же правилом выбора ключа. Обе локальные `patch`
исчезают; разделы зовут общее.

## Minor

### 4. `user-select: none` в `review.css` не делает ничего

- `client/styles/review.css:39-42` — `.review__text { cursor: text; user-select: none }`
- `client/styles/base.css:15-26` — `body { … user-select: none }`

Во всём фронте `user-select` объявлен трижды, и это все три: `none` на `body`,
`text` у `.field__input` (с комментарием «body запрещает выделение, полю оно
нужно») и `none` у `.review__text`. `.review__text` — это `<div>`
(`ReviewModal.svelte:66`), не `.field__input`, и ничто между `body` и им
выделение не возвращает: свойство наследуется, и правило повторяет
унаследованное.

Хуже самого повтора то, что рядом стоит комментарий, объясняющий несделанное:
«Текст читают, а не выделяют: правка начинается кликом, и выделение мешало бы
ему тем сильнее, чем длиннее рецензия». Читающий поверит, что запрет держит это
правило, а держит его `base.css`, — и снявший его отсюда ничего не заметит.

**Что должно остаться.** `body { user-select: none }` в `base.css`. Строка 41
`review.css` снимается; `cursor: text` остаётся — он свой и настоящий.

### 5. Замок записи `keep()` совпал у двух окон — и вынести его нечем

- `client/app/ReviewModal.svelte:41-52`
- `client/app/CardModal.svelte:137-147`

```js
if (saving) return
saving = true
try   { …своё… }
catch (error) { lost(error, '…не сохранилась') }
finally { saving = false }
```

Идиома «второго нажатия не бывает, отказ — плашкой» стоит дважды, различаясь
телом `try` и текстом. Общее уже вынесено настолько, насколько выносится:
`lost` — это `complaining(...)` из `app/trouble.js`, единый способ поступить с
отказом.

Оставшееся не выносится: `saving` — это `$state` компонента, и передать руну в
общую функцию можно только объектом-держателем, то есть завести обёртку
длиннее обеих копий ради четырёх строк. Прецедент в проекте записан —
`merge_fields ≠ overwrite_fields`, «функция высшего порядка вышла бы длиннее
обеих».

**Что должно остаться.** Обе копии на месте; пара пишется вердиктом в
`docs/other/not-duplicates.md`, чтобы следующий проход не разбирал её заново.
Дописывает туда исполнитель.

## Рассмотрено и отведено

Кандидаты, подтверждения не получившие. В `not-duplicates.md` из них имеет
смысл записать только те, что рецензент найдёт снова, — они помечены ★.

**Бэкенд, снос опустевшей строки:**

- ★ `backend/storage/repository/ratings.py:38-44` (`emptied`) ≠
  `ratings.py:85-87` (`RatingsRepository.clear`) — оба сносят строку `rating`, и
  общее у них **уже вынесено**: обе строят оператор общим
  `storage/statements.py:clearing`. Дальше они расходятся по существу: `clear`
  сносит строку безусловно, вместе с рецензией, а `emptied` — только ту, в
  которой не осталось ни балла, ни трёх шкал, ни текста, и делает это вторым
  оператором той же транзакции. Слить нельзя: условие и есть содержание
  второго, а его отсутствие — содержание первого.
