## Разбор молчаливых

### Настоящие дыры

#### 1. M08 — `StrEnum` подменён на `Enum`. Главная находка

Одна строка импорта, `from enum import Enum as StrEnum`, и все восемь тестов
зелёные. А наблюдаемое поведение `Reason` меняется целиком — замерено:

| | `StrEnum` | `Enum` |
|---|---|---|
| `str(Reason.QUOTA)` | `'quota'` | `'Reason.QUOTA'` |
| `f"{Reason.QUOTA}"` | `'quota'` | `'Reason.QUOTA'` |
| `Reason.QUOTA == "quota"` | `True` | `False` |
| `isinstance(Reason.QUOTA, str)` | `True` | `False` |
| `json.dumps({"r": Reason.QUOTA})` | `{"r": "quota"}` | `TypeError` |

Это ровно то, ради чего `StrEnum` и выбран, и ровно то, о чём говорит докстринг
теста: «значения уходят в лог». В лог уходит `str()`, а `str()` тестом не
наблюдается ни разу. Дальше по плану 2 причина отказа попадёт в записи логов
шести клиентов; если бы `StrEnum` был выбран по ошибке, узнали бы об этом по
строчке `Reason.QUOTA` в логе, а не по красному тесту.

Тест `test_reasons_cover_every_way_a_source_can_refuse` читает `r.value` —
атрибут, который у обоих перечислений одинаков. Он смотрит мимо разницы.

**Чинится одной строкой поведения вместо чтения `.value`:**

```python
def test_a_reason_renders_as_its_wire_string():
    """Причина уходит в лог строкой: f"{reason}" должно дать "quota",
    а не "Reason.QUOTA"."""
    assert f"{Reason.QUOTA}" == "quota"
```

#### 2. M05, M06, M35 — поле `detail` не сторожит никто

Три разные порчи проходят молча: сменить значение по умолчанию, переименовать в
`message`, выбросить поле целиком. Ни один тест не называет `detail`, не
передаёт его и не читает.

При этом соседнее необязательное поле, `retry_after`, покрыто двумя тестами —
и на переданное значение, и на умолчание. Пара полей объявлена рядом, а
проверено одно: случай, когда тест написан по одному примеру, а не по
интерфейсу. План обещает `Refusal(source, reason, retry_after, detail)` —
половина хвоста этого обещания не проверяется.

Формально краснеет только M31 (снятое умолчание), но краснеет не тест, а
интерпретатор: `detail: str` после `retry_after: ... = None` — синтаксически
невозможный датакласс, модуль не импортируется. Это не заслуга тестов.

**Чинится симметрично тестам про `retry_after`:**

```python
def test_refusal_may_carry_a_human_readable_detail():
    refusal = Refusal(source="omdb", reason=Reason.BROKEN, detail="нет поля Response")
    assert refusal.detail == "нет поля Response"


def test_refusal_without_a_detail_carries_an_empty_one():
    """Отсутствие подробностей — пустая строка, а не None: detail уходит в лог
    склейкой, и None превратился бы в слово «None»."""
    assert Refusal(source="omdb", reason=Reason.QUOTA).detail == ""
```

#### 3. M04, M07, M32 — позиционный вызов не проверяется

Все восемь тестов строят `Refusal` только именованными аргументами. Поэтому
молчат сразу три порчи: переставить `source` и `reason`, переставить
`retry_after` и `detail`, объявить датакласс `kw_only=True`.

Последствие переставленной пары замерено:

```
правильный порядок: source='omdb'            reason=<Reason.QUOTA: 'quota'>
переставленный:     source=<Reason.QUOTA: …> reason='omdb'
```

В поле имени источника ляжет причина, а в причину — строка `"omdb"`, и
`Refusal` при этом построится без единой жалобы. `kw_only` не объявлен, значит
позиционный вызов разрешён и шесть клиентов плана 2 вправе им пользоваться.

Дыра неглубокая, но и затыкается одним тестом:

```python
def test_refusal_reads_the_same_built_positionally():
    """Клиенты строят отказ и позиционно тоже: порядок полей — часть
    интерфейса, а не деталь объявления."""
    assert Refusal("omdb", Reason.QUOTA) == Refusal(source="omdb", reason=Reason.QUOTA)
```

Он закрывает M04, M07 и M32 разом — и заодно M15 (см. ниже).

#### 4. M13, M14 — обязательное поле тихо становится необязательным

`reason: Reason = Reason.NETWORK` и `value: T = None` проходят молча. После
первой `Refusal(source="omdb")` строится и получает причину `NETWORK`: забытый
аргумент превращается не в ошибку, а в неверный диагноз отказа. После второй
`Found()` — находка без находки.

Дыра мелкая: такую правку трудно внести случайно, обычно она появляется как
побочный эффект перестановки полей — чтобы датакласс скомпилировался. Поскольку
перестановка полей уже дыра №3, эти две ходят с ней парой.

Отдельных тестов «поле обязательно» не прошу: это ближе к чтению объявления, чем
к наблюдению следствия. Достаточно того, что позиционный тест из пункта 3 ловит
перестановку в корне.

#### 5. M15 — `Refusal` перестал сравниваться по значению

`eq=False` проходит молча: сегодня ни один тест не сравнивает два исхода между
собой. Замерено: `Refusal(...) == Refusal(...)` становится `False`.

Сегодняшнего потребителя нет — по букве это «поломка без последствий». Но
равенство по значению — ровно тот способ, которым будут написаны тесты задач
4–12 этого же плана: «клиент вернул
`Refusal(source="omdb", reason=Reason.QUOTA)`». Если `eq` отвалится, те тесты
станут зелёными на чём угодно, и искать причину будут в клиентах, а не здесь.

Отдельного теста снова не прошу: позиционный тест из пункта 3 сравнивает два
`Refusal` между собой и закрывает это заодно.

### Молчание без последствий — тест не нужен

**M02, M33 — `frozen` (и `slots`) сняты с `Missing`.** У `Missing` нет ни одного
поля, менять в нём нечего. Замерено: единственная наблюдаемая разница —
хешируемость, `hash(Missing())` перестаёт работать без `frozen`. Хеширует
`Missing` сегодня никто, потребителя не видно. Тест на хеш был бы тестом «на
всякий случай» — правило 8.

**M03, M18 — снят `slots`.** `frozen` остаётся, значит присвоить атрибут
по-прежнему нельзя. Разница только в памяти: у объекта появляется `__dict__`,
40 байт против 48 плюс словарь. Поведения это не меняет.

**M12, M19 — эквивалентные мутанты.** `not isinstance(outcome, Refusal)` вместо
`is_answer(outcome)`, и `type(outcome) in (Found, Missing)` вместо `isinstance`:
на замкнутом множестве из трёх исходов обе формы дают тот же результат на всех
входах. Тестом их не различить в принципе — и не надо.

M12 стоит отметить отдельно: `writable` сегодня буквально
`return is_answer(outcome)`, то есть два публичных предиката с одинаковым
поведением. Поэтому шесть утверждений из восьми ходят парами — `is_answer(x) is
True` и рядом `writable(x) is True` — и проверяют одно и то же дважды. Это
замечание к коду, не к тестам, и не по моему измерению, но оно объясняет, почему
покрытие выглядит плотнее, чем оно есть.

**M16, M17, M20, M36 — только аннотации.** `Outcome` — псевдоним типа, он не
вычисляется в рантайме вовсе; `Found[T]` против `Found`; `retry_after: int`
вместо `timedelta`; `writable(outcome: object)`. Замерено: датакласс спокойно
принимает `timedelta` в поле, объявленное как `int`. Проверять аннотации через
`pytest` — значит читать объявление, что правило 13 прямо запрещает. Это работа
проверяльщика типов, и если она нужна, заводить надо его, а не тест.

**M25 — порядок членов `Reason`.** Ничто не перебирает причины по порядку и не
берёт первую. Последствий нет.

### `test_reasons_cover_every_way_a_source_can_refuse` — разбор

```python
assert {r.name: r.value for r in Reason} == {
    "QUOTA": "quota",
    "RATE": "rate",
    ...
}
```

Это буквально то, что описано в правиле 13: объявление прочитано и сравнено с
переписанным в тест ожиданием. Пять пар в тесте — посимвольная копия пяти строк
`errors.py`. Тест повторяет код.

Докстринг защищается тем, что сверяется пара «имя-значение», а не множество
значений, — и защита верная **против одной конкретной порчи**, перестановки двух
значений местами, мутации автора №7. Но она отвечает не на то возражение,
которое ставит правило 13.

Что тест всё-таки сторожит, проверено: M09, лишняя причина, и M10, потерянная,
краснеют. Полнота набора — реальная и полезная гарантия, терять её не надо.

Чего он **не** сторожит — M08, того единственного свойства `Reason`, которое
видно снаружи. Пять значений выписаны в тест, а поведение, ради которого они
существуют, — рендериться строкой в лог, — не наблюдается ни разу.

**Предложение:** не выбрасывать тест, а разделить его на то, что он делает
хорошо, и то, чего в нём нет.

```python
def test_reasons_cover_every_way_a_source_can_refuse():
    """Полнота набора: причину код выбирает по имени, и лишняя или потерянная
    строка означает, что клиент не сможет назвать свой отказ."""
    assert set(Reason.__members__) == {"QUOTA", "RATE", "KEY", "NETWORK", "BROKEN"}


def test_a_reason_renders_as_its_wire_string():
    """Причина уходит в лог строкой, а не именем члена."""
    assert f"{Reason.QUOTA}" == "quota"
    assert Reason.NETWORK == "network"
```

Первый остаётся сверкой имён — это по-прежнему чтение объявления, но имя здесь и
есть интерфейс: по нему причину выбирает код, и ничего наблюдаемого за именем не
стоит. Второй наблюдает следствие и краснеет на M08.

## Дисциплина стенда

со снятой до начала копией, временные файлы стенда лежали вне репозитория,
