## Проверка довода 1 (снятие `item.c.id` из `order_by`)

**Не согласен: довод неверен, и это подтверждено эмпирически, а не только
рассуждением.**

Довод ссылается на то, что `rating.item_id` — целочисленный первичный ключ, то
есть rowid таблицы `rating`. Но управляющая таблица запроса — `item`
(`item.outerjoin(rating)...`), и порядок `LEFT OUTER JOIN` определяется планом
обхода **`item`**, а не `rating`. У `item.id` тоже `Integer, primary_key=True`
— тоже rowid, но это не спасает довод, потому что у `item` есть составной
индекс `ix_item_kind_year (kind, year)`, а WHERE в каждом запросе раздела
всегда фильтрует по `item.c.kind`.

Прямая проверка (`EXPLAIN QUERY PLAN` на реальных таблицах, временная
in-memory база, 29 строк с разными `year`, все оценки равны):

```
SEARCH item USING COVERING INDEX ix_item_kind_year (kind=?)
SEARCH rating USING INTEGER PRIMARY KEY (rowid=?) LEFT-JOIN
```

Без второго ключа сортировки при равных `score` порядок оказался
`[5, 10, 15, 20, 25, 1, 6, 11, ...]` — сгруппирован по `year`, никак не по
`id`. С `item.c.id` вторым ключом — строго `[1, 2, 3, ..., 29]`.

Вывод: **потеря второго ключа наблюдаема**, как только в данных есть больше
одного значения `year` при равных значениях первичного ключа сортировки — а
это обычное состояние реальной библиотеки (у фильмов разные годы). Тест 11
(`test_equal_scores_are_ordered_by_identifier`) не ловит эту мутацию только
потому, что все шесть его карточек созданы с одним и тем же `year=2000` —
тогда SQLite укладывает совпадающие ключи индекса `(kind, year)` по rowid
внутри, и порядок случайно совпадает с id. Это тот же класс совпадения,
который уже один раз молча пропустил мутацию в тесте про алфавит (до
исправления набора имён) — здесь он не исправлен.

**Рекомендация**: заменить данные теста 11 (или добавить новый) — те же
равные оценки, но разные `year` у карточек. Тогда потеря `item.c.id`
действительно покраснеет.

## Проверка довода 2 (перестановка `_excluded`/`_included`)

**Согласен.** Обе функции добавляют условия в одну конъюнкцию `WHERE` через
последовательные `.where()`, а конъюнкция коммутативна и ассоциативна: SQL не
различает, в каком порядке к запросу приклеены условия `AND`. Сила исключения
действительно держится на виде условия (`NOT IN` против `IN`), а не на
позиции вызова. Порядок вызовов `_included`/`_excluded` действительно
ненаблюдаем при любых данных — в отличие от довода 1, здесь нет скрытого
физического слоя (индекса), который мог бы сделать порядок вызовов значимым.

## Недостаточные данные (порядок)

Тесты 6, 7, 8, 9, 17 — во всех ровно две карточки, и в каждом вторая созданная
карточка (больший `id`) — победитель по проверяемому критерию при `descending
=True`, а первая — при `descending=False` (тест 17). То есть ожидаемый порядок
в каждом из этих пяти тестов совпадает с порядком по `id` (по убыванию либо по
возрастанию). Конкретно это значит: мутация «`_KEYS[Sort.SCORE]` (или
`RATED_AT`, `YEAR`, `ADDED_AT`) указывает на `item.c.id` вместо настоящего
столбца» **пройдёт молча** — ни один из этих пяти тестов её не поймает,
потому что ожидание неотличимо от сортировки по id. Единственный тест, чьи
данные не совпадают с id-порядком, — 18 (алфавит, три карточки, ожидаемый
порядок — перестановка id, а не монотонная последовательность).

## Чего в наборе не хватает (непокрытые поломки)

1. **Подмена `_KEYS[Sort.SCORE]`/`RATED_AT`/`YEAR`/`ADDED_AT` на `item.c.id`.**
   Разобрано выше — пройдёт молча на пяти тестах порядка, кроме `TITLE`.
2. **Потеря второго ключа `item.c.id` в `order_by` при неравном `year`.**
   Разобрано в проверке довода 1 — при текущих данных теста 11 не ловится, но
   реально наблюдаемая поломка на обычных данных.
3. **`CAST` пропущенный в ветке `excluded_scores`** (`_COLUMN.not_in` заменён
   на `rating.c.score.not_in` без `cast`). Тест 21 использует только целые
   оценки (7.0, 9.0), поэтому численное сравнение совпадает что с `CAST`, что
   без него. Дробная оценка (например, 7.33 при исключённом столбце 7) не
   проверена вовсе для ветки исключения — только для включения (тест 16).
4. **Исключение по метке/жанру в разделе `WISHLIST`.** Все тесты на
   `excluded_tag_ids`/`excluded_genre_ids` (19, 20) собраны на `RATED`. Ни
   один тест не подтверждает, что то же исключение работает в `WISHLIST` —
   гипотетическая мутация вроде `if feed.section is Section.RATED: query =
   _excluded(query, filters)` (исключение навешано только на «Оценённые») не
   поймается ничем, кроме теста 22, а тот проверяет только `excluded_scores`,
   не теги/жанры.
5. **Фильтр по нескольким жанрам одновременно (`OR` внутри `genre_ids`).**
   Аналог теста 13 для тегов не сделан для жанров: во всех тестах на жанры
   (14, 15, 19, 20) используется ровно один `genre_id`. Мутация, специфичная
   для ветки `genre_ids` в `_included`/`_carrying` (например, использование
   `==` первого элемента вместо `.in_()` только в жанровой ветке), пройдёт
   молча — по всем данным её невозможно отличить от корректной реализации,
   раз тестируется только один жанр.
6. **`Kind.SERIES` вообще не встречается** ни в одном тесте — есть только
   `MOVIE` и `GAME` (тест 5). Риск невысокий структурно (код фильтрует общим
   равенством `item.c.kind == feed.kind` без спецкейсов), но если появится
   код, специфичный для типа контента (например, отдельная обработка
   сериалов при подсчёте `episodes_count` в разделах), для него сейчас нет
   ни одной проверочной карточки.
7. **Порция вместе с фильтром.** Тест 10 проверяет `offset`/`limit` без
   активных фильтров, тесты на фильтры (12–20) все берут `limit=50, offset=0`
   без реальной порции. Комбинация «фильтр сузил набор, и внутри него берётся
   вторая порция» не проверена ни разу — при текущей однозапросной реализации
   риск невысок (LIMIT/OFFSET применяются к уже отфильтрованному запросу), но
   специального теста, ловящего регресс именно на стыке, нет.

## Вердикт

Тесты в целом добротные и метко названные — 16 из 23 тестов действительно
дискриминируют то, что заявляют. Но раздел сортировки (пять из шести
Sort-критериев) построен на данных, которые не отличают настоящую сортировку
от сортировки по id, и заявленная «ненаблюдаемость» второго ключа порядка на
самом деле неверна — подтверждено прямым запуском `EXPLAIN QUERY PLAN`.
