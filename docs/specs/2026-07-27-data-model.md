# Модель данных

Схема локальной базы: что храним, как связано, почему именно так. Реализация —
SQLite, SQLAlchemy в асинхронном режиме, миграции Alembic с первого коммита.

## Два принципа

**Каталог отдельно от моих данных.** `item`, `genre`, `person`, `company` и связи
между ними наполняются из TMDB, Steam и GOG либо заводятся руками. `rating`,
`tag`, `item_tag`, `wishlist` — мои, они не зависят от источника.

Отсюда правило внешних ключей: **со стороны каталога удаление каскадное.**
Обновление каталога трогает только то, что реально меняется у источника, — и
никогда не переписывает карточку целиком: название, синопсис, постер и состав с
момента первой записи принадлежат человеку. Подробнее ниже, в разделе про
перезапрос.

Удаление карточки при этом уносит и мои данные — так решено, см.
`docs/specs/2026-07-27-manual-cards.md`. Оно всегда идёт через подтверждение, в
котором перечислено, что именно пропадёт: оценка, теги, закладка. Запрещающих
ключей в схеме нет — иначе программа знала бы, чего человек хочет, и всё равно
заставляла бы доказывать серьёзность намерений.

**Один `item` с полем типа, а не три таблицы.** Оценки, теги, отложенное, лента,
поиск и фильтры пишутся один раз на все три типа контента. Различий на поверку
мало: длительность у фильма, число сезонов и серий у сериала — необязательные
поля вместо трёх параллельных ветвей во всей схеме.

## Каталог

### item

Карточка любого типа контента.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | INTEGER PK | |
| `kind` | TEXT NOT NULL | `movie` \| `series` \| `game` |
| `source` | TEXT NOT NULL | откуда карточка: `manual` \| `tmdb` \| `steam` \| `gog` |
| `source_id` | TEXT NOT NULL | идентификатор в этом источнике |
| `title` | TEXT NOT NULL | локализованное название, если источник его дал |
| `original_title` | TEXT | |
| `year` | INTEGER | год выхода |
| `released_at` | DATE | полная дата, если известна |
| `synopsis` | TEXT | |
| `poster_url` | TEXT | откуда скачана обложка; у ручной карточки пусто |
| `runtime` | INTEGER | минуты; только у фильма |
| `seasons_count` | INTEGER | только у сериала |
| `episodes_count` | INTEGER | всего серий; только у сериала |
| `synced_at` | DATETIME NOT NULL | когда карточку последний раз обновляли |

`UNIQUE (source, source_id)` — идентичность карточки. Источник назван в
отдельной колонке специально: в предшественнике поле называлось `kinopoisk_id`,
а хранило TMDB ID, потому что проект сменил источник и не переименовал колонку.

**У ручной карточки `source = 'manual'`**, а идентификатор выдаётся при
создании. Поля остаются обязательными, и `UNIQUE` продолжает работать: привязка
к внешней базе — это правка двух полей, а не смена идентичности, потому что
оценка, теги и закладка держатся за `item.id`. Подробности —
`docs/specs/2026-07-27-manual-cards.md`.

**`title` — локализованное название, `original_title` — как в оригинале.** У
TMDB пара приезжает в одном ответе. У игры зависит от магазина: Steam отдаёт
русские название и описание, если издатель их завёл, у GOG локализованы только
жанры.

В карточке сериала показывается «2 сезона, 24 серии». Оба числа приходят в том
же ответе `/tv/{id}`, что и вся остальная карточка.

Разбивку по сезонам и длину серии не храним: они стоили бы отдельного запроса
на каждый сезон, а «по 12 серий» вместо «24 серии» ничего не добавляет.

**Перезапрашивается только то, что реально меняется: число сезонов и серий у
сериала и оценки.** Всё остальное из источника приезжает один раз при создании
карточки и больше не трогается — название, синопсис, постер, длительность, жанры
и состав с этого момента принадлежат тебе и правятся руками.

Срок прежний, месяц от `synced_at`, и делается это **только для видимых
карточек**. Обновление сериала стоит дёшево: `number_of_seasons` и
`number_of_episodes` приходят в `/tv/{id}` без единого довеска, то есть без
`aggregate_credits`, который тянет 167 КБ.

Ручных карточек это не касается: перезапрашивать нечего.

**Частичной карточки в базе не бывает.** Строка из внешнего источника пишется
только из детального ответа и сразу целиком, поэтому признака полноты в схеме
нет, а `synced_at` означает «на этот момент карточка была полной». Ручная
карточка пишется из формы, и её полнота — дело твоё: обязательно там только
название. Подробности — `docs/specs/2026-07-27-search-and-loading.md`.

### genre, genre_map, item_genre

```
genre       id         INTEGER PK
            name       TEXT NOT NULL            каноническое имя
            kind       TEXT NOT NULL            film | game
            UNIQUE (name, kind)

genre_map   source     TEXT NOT NULL            tmdb | steam | gog
            ext_id     TEXT NOT NULL
            genre_id   INTEGER NOT NULL → genre
            PK (source, ext_id, genre_id)

item_genre  item_id    INTEGER → item
            genre_id   INTEGER → genre
            PK (item_id, genre_id)
```

**Справочник жанров и соответствия к нему зашиты в миграцию.** Он маленький,
меняется раз в годы и нужен целиком с первого запуска: в выдаче поиска приходят
голые `genre_ids`, и без готового справочника жанр кандидата показать нечем.

Это та граница, по которой жанры отличаются от тегов: жанр приходит снаружи,
тег заводит только человек. Но приходит он идентификатором, а как этот
идентификатор называется — решено заранее и лежит в миграции.

**Наборов жанров два: кино и игры.** Фильмы и сериалы делят один — «драма» у
фильма и у сериала это одна строка, иначе фильтр по драме превратился бы в два
разных фильтра. Игры держатся отдельно: там своя лексика, и в фильтре у кино ей
не место.

Сериальные жанры живут в том же наборе кино. То, что «мыльную оперу» ни один
фильм не получит, ничему не мешает — жанр просто не будет никому присвоен.

Уникальность составная: «приключения» есть и у кино, и у игр, и это разные
строки.

**Сборные жанры разворачиваются в обычные.** У TMDB в сериалах они есть, и
хранить их как есть нельзя: «НФ и Фэнтези» — это не жанр, а два жанра, сшитых
чужим справочником.

| Приходит от TMDB | Ложится в |
|---|---|
| Боевик и приключения (`10759`) | боевик + приключения |
| НФ и фэнтези (`10765`) | фантастика + фэнтези |
| Война и политика (`10768`) | военный + политика |

Все части, кроме «политики», уже есть в киношном справочнике TMDB — то есть
разворачивание почти не плодит новых жанров, а сводит сериальные обозначения к
тем же строкам, что и у фильмов. «Политику» заводим своей: это законная половина
существующего жанра, и терять её при разборе незачем.

## Что зашивается в миграцию

Собрано с живого TMDB 27.07.2026: `/genre/movie/list` — 19 жанров,
`/genre/tv/list` — 16, общих у них восемь.

**Набор «кино» — 25 жанров.** Объединение обоих списков после разложения
сборных:

```
боевик, вестерн, военный, детектив, детский, документальный, драма, история,
комедия, криминал, мелодрама, музыка, мультфильм, мыльная опера, новости,
политика, приключения, реалити-шоу, семейный, телевизионный фильм, ток-шоу,
триллер, ужасы, фантастика, фэнтези
```

**Соответствий `genre_map` для TMDB — 30 строк** на 27 уникальных
идентификаторов: 24 обычных дают по строке, три сборных — по две. Восемь
идентификаторов встречаются в обоих списках TMDB и означают одно и то же, так
что строка у них одна.

**Имена пишем свои.** Раз справочник наш, регистр и формулировки тоже наши: TMDB
отдаёт киношные жанры строчными, а сериальные — с заглавной, «Ток-шоу» и
«Мыльная опера» **[живьём]**. Тащить эту разноголосицу в базу незачем.

**Игровую половину придётся собирать выборкой.** Ни Steam, ни GOG списка своих
жанров не публикуют — эндпоинта вроде `/genre/list` у них нет, жанры приходят
только внутри карточки конкретной игры. Значит набор собирается прогоном по
представительной выборке игр, и он по определению неполный: неизвестный жанр
будет попадаться и после. На этот случай есть правило ниже — запись в лог.

Соответствия внешним справочникам живут в `genre_map` и нигде больше:
в предшественнике та же задача была размазана по четырём несинхронизированным
словарям в коде при живой таблице жанров. У игр источников два, и словари у них
разные: Steam отдаёт жанры с числовыми идентификаторами, GOG — со слагами. Оба
ложатся в один набор `game` через `genre_map`.

Ключ `genre_map` включает `genre_id`, потому что соответствие не взаимно
однозначно: у TMDB в сериалах есть сборные жанры — «Sci-Fi & Fantasy»,
«Action & Adventure», «War & Politics», — и один внешний идентификатор должен
разворачиваться в два наших. Это же снимает нужду в таблице алиасов:
сопоставляем по идентификаторам, а не по строкам, и ни один из источников не
отдаёт жанр без идентификатора.

**`kind` из ключа `genre_map` убран.** В спеке было записано, что у TMDB
идентификаторы жанров различаются между фильмами и сериалами, — это неверно:
пространство идентификаторов у него одно, и из восьми id, встречающихся в обоих
списках, ни один не значит разного. «Драма» — это `18` и у фильма, и у сериала
**[живьём]**. Расходятся не идентификаторы, а наборы, так что различать `movie` и
`series` в ключе было незачем.

**Неизвестный идентификатор жанра — это запись в лог, а не новая строка.**
Источник добавил жанр, которого в миграции нет: карточка показывается без него,
случай попадает в лог. Молча пропускать нельзя, но и заводить жанр на лету тоже:
имена в справочнике наши, а сборный жанр автоматически не разложить.

### person, person_credit

```
person         id         INTEGER PK
               name       TEXT NOT NULL
               source     TEXT              manual | tmdb, может пустовать
               source_id  TEXT              может пустовать
               UNIQUE (source, source_id)

person_credit  item_id    INTEGER → item
               person_id  INTEGER → person
               role       TEXT NOT NULL     director | actor | showrunner
               position   INTEGER           порядок в титрах
               PK (item_id, person_id, role)
```

`position` нужен для «топ-5 актёров» в карточке: без него порядок теряется и
главные роли не отличить от эпизодических.

Роль входит в первичный ключ: один человек бывает на одной карточке и
режиссёром, и актёром.

**Заведённый руками человек — `source = 'manual'`** со своим идентификатором.
Внешнего у него нет, поэтому одного и того же человека от двух разных отличает
интерфейс: при вводе подсказываются уже заведённые, и выбор из списка — это
отдельный жест от заведения нового. Уникальность по имени в базе не навязываем —
полные тёзки существуют. Подробности — `docs/specs/2026-07-27-people.md`.

**Источник у `person` и `company` необязателен.** Steam и GOG людей не отдают
вовсе, а студии приходят голыми строками без идентификаторов: класть туда
нечего, и выдумывать суррогат ради непустоты незачем. У таких строк
`source` и `source_id` пустуют, склейка идёт по имени. Уникальный ключ этому не
мешает: в SQLite два `NULL` в нём друг другу не противоречат.

Состав игр приходить неоткуда: ни Steam, ни GOG людей не отдают, только компании.
У игры `person_credit` заполняется только вручную.

### company, company_credit

```
company         id, name, source, source_id     как у person, включая то,
                                                что источник необязателен
                                                manual | tmdb | steam | gog
                UNIQUE (source, source_id)

company_credit  item_id     INTEGER → item
                company_id  INTEGER → company
                role        TEXT NOT NULL     developer | publisher
                PK (item_id, company_id, role)
```

Студии отделены от людей: у игры разработчик и издатель — это роли компании, а
не человека.

### external_id

```
item_id  INTEGER → item
source   TEXT NOT NULL     imdb | kinopoisk | steam | gog
value    TEXT NOT NULL
PK (item_id, source)
UNIQUE (source, value)
```

Всё, что не основной источник карточки. У кино это IMDb ID и идентификатор
Кинопоиска. У игры — идентификатор второго магазина, если ты сам его вписал:
общего ключа между Steam и GOG не существует, автоматически он взяться не может.

На них же собираются ссылки «открыть на IMDb» из карточки.

### external_rating

```
item_id     INTEGER → item
source      TEXT NOT NULL       imdb | kinopoisk | tmdb | rotten |
                                metacritic | steam | gog
value       REAL                пусто — источник такой оценки не знает
fetched_at  DATETIME NOT NULL   когда спрашивали
PK (item_id, source)
```

Отдельная таблица, а не пять колонок в `item`, как было у предшественника:
набор источников у кино и у игр разный. Значение лежит в том виде, в каком его
отдал источник — IMDb десятибалльный, Rotten Tomatoes стобалльный. Шкала не
хранится: она выводится из имени источника в коде и применяется только при
показе.

**Имя источника — это владелец оценки, а не тот, кто её привёз.** Steam отдаёт
две разные величины: Metascore принадлежит Metacritic и ложится в строку
`metacritic`, доля положительных отзывов игроков — в строку `steam`. Числа обоих
лежат в 0–100, но это разные величины, и складывать их нельзя. У GOG своя оценка
игроков, она ложится в строку `gog`.

**У Кинопоиска одна строка независимо от зеркала.** Оба зеркала отдают один и
тот же идентификатор Кинопоиска и одну и ту же оценку — источник называется
`kinopoisk`, а какое зеркало ответило, в данных не отражается. То же и в
`external_id`.

**Три различимых состояния.** Пустое значение — это ответ, а не отсутствие
ответа:

| Строки нет | Строка есть, `value` пуст | Строка есть со значением |
|---|---|---|
| не спрашивали | спрашивали, у источника нет | есть оценка |

Без этого различия фильм, которого MDBList не знает, перезапрашивался бы при
каждом показе — так и было у предшественника.

**Срок годности считается от `fetched_at`**, а не хранится отдельным полем:
политику тогда можно менять, не трогая базу. Значение живёт месяц — за это
время оценка IMDb сдвигается на сотые доли. Отрицательный ответ живёт неделю:
у свежего релиза оценка ещё может появиться, но ходить за ней ежедневно незачем.

Пока оценки не приехали, в карточке на их месте крутится индикатор: они
догружаются фоном и показ не задерживают.

## Мои данные

### rating

Одна строка на элемент.

| Поле | Тип | Смысл |
|---|---|---|
| `item_id` | INTEGER PK → item | |
| `score` | REAL | значение, по которому работает всё приложение |
| `visual` | INTEGER | ─┐ |
| `narrative` | INTEGER | ├ только у игр, 1–10, каждая может пустовать |
| `gameplay` | INTEGER | ─┘ |
| `review` | TEXT | |
| `created_at` | DATETIME NOT NULL | |
| `updated_at` | DATETIME NOT NULL | |

У фильма и сериала `score` — это и есть выставленная оценка. У игры — среднее
выставленных шкал, пересчитывается при записи. Смысл в том, что лента,
сортировка, фильтр по оценке и гистограмма работают с одним числом и не знают,
что у игр шкал три.

Инвариант поддерживается приложением, а не базой: он зависит от `item.kind`,
которого в этой таблице нет.

История оценок не ведётся — хранится только текущее значение.

### tag, item_tag, wishlist

```
tag       id        INTEGER PK
          name      TEXT NOT NULL
          kind      TEXT NOT NULL        movie | series | game
          position  INTEGER NOT NULL     ручной порядок внутри своего набора
          UNIQUE (name, kind)

item_tag  item_id   INTEGER → item
          tag_id    INTEGER → tag
          PK (item_id, tag_id)

wishlist  item_id   INTEGER PK → item
          added_at  DATETIME NOT NULL
```

**Наборов тегов три, по одному на тип контента, и они независимы.** Фильмы,
сериалы и игры размечаются своими словами, поэтому уникальность составная, а
модалка тегов показывает набор текущего типа.

Здесь три набора, а не два, как у жанров. Жанр приходит снаружи и означает одно и
то же у фильма и сериала, поэтому «драма» там одна; тег придумывает человек под
конкретный тип.

Прямое следствие: тег, нужный везде, заводится трижды.

`position` — потому что в интерфейсе строки тегов переставляются
перетаскиванием, то есть порядок задаётся вручную и должен пережить перезапуск.
Порядок свой в каждом наборе.

**`item_tag` не даёт повесить чужой тег** — то есть тег одного типа на карточку
другого. Инвариант держит приложение, а не база: он зависит от `item.kind`,
которого в этой таблице нет. То же и с пересчётом `score` у игр.

**Тег заводит и назначает только человек.** Из источников в эту таблицу не
попадает ничего: чужие метки — это жанры, и они лежат отдельно. Поэтому теги
Steam мы не берём, хотя он их отдаёт с весами.

## Хранилище постеров

Отдельный файл SQLite рядом с основной базой.

```
posters.db

poster  item_id     INTEGER PK   карточка, которой принадлежит обложка
        data        BLOB         картинка, обрезанная под 2:3
        fetched_at  DATETIME NOT NULL
```

**Отдельный файл, а не колонка в основной базе.** Основная база маленькая и
часто пишется, картинки большие и пишутся один раз. В общем файле они утяжелили
бы каждый бэкап и каждый `VACUUM`, а миграции пошли бы поверх гигабайтов.

**SQLite, а не папка с файлами.** Одна сущность вместо тысяч мелких файлов: нет
висячих сирот, запись атомарна, всё переносится копированием одного файла.

**Ключ — `item_id`.** Ранее здесь был хеш адреса, чтобы хранилище ничего не
знало о предметной области. Это перестало иметь смысл: файл всё равно лежит
локально, а у залитой с диска картинки адреса нет. С ключом по карточке скачанный
и залитый постер неразличимы, и особой ветки для ручных не нужно.

**Постер живёт ровно столько, сколько карточка.** Пока карточка есть, обложка не
подменяется: перезапрос по сроку её не касается. Удалили карточку — обложка
удаляется вместе с ней, но **кодом, а не каскадом**: внешних ключей между двумя
файлами SQLite не бывает. Это единственное место, где «удалить всё разом» не
обеспечено самой базой, и его надо покрыть тестом.

Цена — файл растёт вместе с библиотекой: при ~80 КБ на постер тысяча карточек это
80 МБ.

**Хранится один размер, 2:3, с запасом под высокую плотность экрана.** У TMDB это
`w500` — 500×750. У Steam вертикальная обложка лежит по предсказуемому адресу
`library_600x900_2x.jpg` — настоящие 600×900, в ответе API её нет **[живьём]**.
Вариант без `_2x` отдаёт 300×450, вдвое меньше собственного имени. У GOG —
`coverVertical` из ответа поиска. Залитая руками картинка обрезается по центру до
тех же пропорций.

Отдельные превью не делаем — масштабирование под карточку живёт в памяти.

## Индексы

Помимо тех, что приходят из первичных и уникальных ключей:

- `item (kind)` — лента всегда отфильтрована по типу контента;
- `item (kind, year)` — сортировка по дате выхода;
- `rating (score)` — сортировка по оценке и гистограмма;
- `rating (updated_at)` — сортировка по времени оценки;
- `wishlist (added_at)` — порядок по умолчанию в разделе «Хочу посмотреть»;
- `item_genre (genre_id)` — фильтр по жанру;
- `item_tag (tag_id)` — фильтр по тегу;
- `person_credit (person_id)` — «показать всё с этим человеком»;
- `company_credit (company_id)` — то же для студии.

## Что сознательно отложено

Не «забыли», а решено не делать сейчас:

| Что | Когда понадобится |
|---|---|
| Профиль вкуса: средние оценки по жанрам, людям, студиям | когда дойдём до рекомендаций |
| Кеш рекомендаций | тогда же |
| `item_fts` — полнотекстовый поиск | когда каталог вырастет настолько, что `LIKE` начнёт тормозить; на нескольких тысячах строк разницы нет |
| `app_state` — курсор импорта | когда будет решена стратегия загрузки каталога |
| Платформы у игр | в макете их нет |
