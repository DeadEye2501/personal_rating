# Отказы источников

Чем источник отвечает в разных случаях и как приложение их различает.

Зачем это нужно: в `external_rating` пустое значение означает «спрашивали,
у источника такой оценки нет», и оно не перезапрашивается неделю. Спутать это с
отказом в обслуживании нельзя — иначе приложение решит, что у IMDb нет
«Интерстеллара».

Проверено 27.07.2026. Пометки: **[живьём]** — проверено запросом без ключа,
**[док]** — из официальной документации или OpenAPI, **[?]** — неофициальный
источник, требует подтверждения на живом ключе. Перепроверенное позже несёт свою
дату — **[живьём 29.07.2026]**: источник меняется, и знать, когда замерено,
важнее, чем считать все замеры одновременными.

## Общее правило

**Отказ в обслуживании никогда не приходит с HTTP 200.** Исключение одно, и его
надо помнить поимённо: **OMDB**.

У Steam под `200` тоже приходит не то, чего ждёшь, — но это не отказ, а ответ
«игры нет»: `{"success": false}`. Разница существенная, потому что ответ в базу
пишется, а отказ не пишется никогда.

## Что писать в базу

| Ситуация | Что делаем |
|---|---|
| Источник ответил, что объекта у него нет | строка с пустым значением, не трогаем неделю |
| Источник ответил оценкой | строка со значением, не трогаем месяц |
| Отказ: квота, частота, ключ, сеть, сбой | **не пишем ничего**, спросим при следующем показе |

Отметок о неудаче в данных нет. От долбёжки защищает предохранитель на клиенте:
исчерпалась квота — клиент целиком помечает себя выключенным на срок и в сеть
не ходит. Это одна переменная в памяти вместо записи в сотни строк.

## По источникам

### TMDB

| | |
|---|---|
| Объекта нет | `404`, `status_code` 34; битый идентификатор — 6 **[док]** |
| Частота | `429`, `status_code` 25 **[док]** |
| Квота | суточной нет **[док]** |
| Ключ | `401`, `status_code` 7; отозванный — 10 **[живьём]** |
| Сбой | 500, 502, 503, 504 с кодами 11, 43, 9, 46, 24 **[док]** |

Различается однозначно. Ключ проверяется раньше существования объекта, поэтому
при протухшем ключе даже несуществующий идентификатор даёт `401` — ошибка в
безопасную сторону. `Retry-After` не отдаётся, откат свой.

### Steam

Два эндпоинта: поиск `steamcommunity.com/actions/SearchApps/{строка}` и карточка
`store.steampowered.com/api/appdetails?appids={id}`. Оба проверены живьём
27.07.2026, битый `appids` перепроверен 29.07.2026.

| | |
|---|---|
| Игры нет | `200` + `{"999999999":{"success":false}}` **[живьём]** |
| Поиск ничего не нашёл | `200` + пустой массив `[]` **[живьём]** |
| Битый или отсутствующий `appids` | `400` + `null` — валидный JSON **[живьём 29.07.2026]** |
| Частота | 220 запросов подряд прошли без троттлинга **[живьём]** |
| Ключ | не нужен **[живьём]** |
| Квота | документации нет вовсе |
| Сбой | не проверен |

Различается однозначно и дёшево: `success` — булев флаг рядом с данными, а не
код в списке. Отрицательный факт пишем при `200` **и** `success == false`.

Пустое, отсутствующее и ошибочное различаются по коду и форме тела, а не по
тому, упал ли разбор:

- `200` и объект, где `success: true`, — игра есть;
- `200` и объект, где `success: false`, — игры нет, и это ответ;
- `200` и пустой массив у поиска — не нашлось, и это тоже ответ;
- `400` — спросили неправильно; тело `null` разбирается без ошибки и не
  означает ничего, различает только код;
- `200`, но тело `null`, пустое или не объект — считаем поломкой источника, а
  не «игры нет»: у «игры нет» есть своя положительная форма, и подменять её
  отсутствием данных значит записать пустое значение на неделю вместо того,
  чтобы спросить снова.

Узнавать битый запрос по падению разбора нельзя: `null` — валидный JSON, и
клиент, ждущий исключения, не дождётся его никогда.

`success: false` не различает «appid не существует» и «существует, но скрыт из
витрины» — для нас это одно состояние.

### GOG

| | |
|---|---|
| Поиск | **никогда не говорит «не найдено»** — см. ниже **[живьём]** |
| Продукта нет | `404` `{"error":"Product not found"}` у `api.gog.com/products/{id}` **[живьём]** |
| Ключ | не нужен **[живьём]** |
| Частота, квота | документации нет вовсе, не проверены |
| Сбой | не проверен |

**Главная ловушка: поиск в каталоге всегда что-то возвращает.** На заведомую
бессмыслицу `catalog.gog.com/v1/catalog?query=like:zzqqxxnotagame123` приходит
`200` и **полсотни несвязанных игр** (50 ровно, 29.07.2026; 27.07.2026 их было
22 — число не постоянно), на пустой запрос — весь каталог, 6317 наименований
**[живьём]**.

Отсюда два следствия. Первое: **отрицательный факт по поиску GOG записать
нельзя** — «игры нет» и «поиск не справился» выглядят одинаково. Второе: то, что
«Planescape» и «Fallout 2» у него не находятся, не означает их отсутствия в
каталоге; это значит, что поиск отранжировал их мимо.

Второй эндпоинт, `embed.gog.com/games/ajax/filtered`, отдаёт пустой результат на
всё **[живьём]** — не использовать.

### MDBList

| | |
|---|---|
| Объекта нет | `404` `{"error":"Item not found"}` **[?]** |
| Квота | `429` `{"error":"Daily API limit exceeded!"}` + `Retry-After`, `X-RateLimit-*` **[док]** |
| Ключ | `401` `{"error":"Invalid API key"}`; на `/user` тот же текст под `403` **[живьём]** |
| Без ключа | `401` `{"error":"Authentication required…"}` **[живьём]** |
| Сбой | `500` `{"error":"An error occurred"}`; Cloudflare отдаёт HTML **[док/живьём]** |

**Без заголовка `User-Agent` запрос до MDBList не доходит.** Cloudflare отвечает
`403` с телом `error code: 1010` — не JSON, и код тот же, каким у `poiskkino.dev`
обозначена исчерпанная квота. С любым `User-Agent` тот же запрос отдаёт `200`
**[живьём]**. Заголовок обязателен, иначе источник выглядит вечно отказавшим.

Различается однозначно. Срок отката — из `Retry-After`, запасной путь `/user` →
`rate_limit_reset`. Там же видна квота: `api_requests: 1000` и
`api_requests_count` — 1000 в сутки подтверждено **[живьём]**.

Две оговорки. `200` ещё не значит «оценка есть»: у найденного объекта
конкретный рейтинг может прийти как `null`. Ответ `401` кешируется Cloudflare на
15 минут **[живьём]**.

Отдельно: у каталожных эндпоинтов бывает `202` + `Retry-After: 5` — это не
отказ и не отсутствие, а «кеш строится, повтори» **[док]**.

**Ловушка при переносе кода.** Легаси-эндпоинт `mdblist.com/api/?apikey=…`
отдаёт `503` с телом `{"response":"False","error":"Invalid API key or Rate
Limiter Reached!"}` — **битый ключ и лимит слиты в один ответ под кодом сбоя**
**[живьём]**. Актуальный адрес — `api.mdblist.com/{provider}/{type}/{id}`.
Предшественник ходил в старый.

### OMDB

| | |
|---|---|
| Объекта нет | `200` + `{"Response":"False"}`, текст разный **[живьём]** |
| Квота | `401` + `Error: "Request limit reached!"` **[?]** |
| Ключ | `401` + `Error: "Invalid API key!"` **[живьём]** |
| Без ключа | `401` + `Error: "No API key provided."` **[живьём]** |
| Частота | отдельного лимита нет **[док]** |

Одно из двух исключений из общего правила. Различаем **сначала по коду**:
`200` с `Response: "False"` — объекта нет, пишем пустое значение; `401` — отказ,
строку не создаём.

Текст `Error` под этим `200` бывает как минимум трёх видов **[живьём]**:
`Movie not found!` при поиске по названию, `Error getting data.` по
несуществующему `i=`, `Incorrect IMDb ID.` на битом формате идентификатора. Все
три означают одно и то же, и правило «сначала код» это подтверждает: разбирать
текст здесь не нужно.

Внутри `401` квоту от битого ключа различает только текст. Искать подстроку
`limit` нестрого, а неизвестный `401` считать временным отказом. Полного
официального списка значений `Error` не существует.

Срок отката: заголовков нет, квота суточная — константа до следующих суток.

### Кинопоиск, `kinopoiskapiunofficial.tech`

| | |
|---|---|
| Объекта нет | у `/api/v2.2/films` — `200` + `total: 0`, `items: []`; `404` для него не документирован **[док]** |
| Частота | `429`; 5 запросов в секунду на этом эндпоинте **[док]** |
| Квота | **`402`** «Превышен лимит запросов» — отдельный код **[док]** |
| Ключ | `401` `{"message":"You don't have permissions…"}`, одинаково для пустого и мусорного **[живьём]** |
| Сбой | в спецификации нет ни одного 5xx **[док]** |

Использовать именно `/api/v2.2/films`, а не `search-by-keyword`: у второго
`404` означает и «фильм не найден», и «поиск ничего не дал» — два разных смысла
в одном коде.

Ловушка: `429` может прийти от nginx с телом `text/html` **[живьём]** —
разбор JSON на нём падает.

Отрицательный ответ подтверждён живьём: несуществующий `imdbId` даёт `200` и
`{"total":0,"totalPages":0,"items":[]}`.

Остаток квоты — `/api/v1/api_keys/{apiKey}`, и **ключ нужен одновременно в пути
и в заголовке `X-API-KEY`**: только в пути — `401` **[живьём]**. Ответ:
`{"totalQuota":{...},"dailyQuota":{"value":500,"used":2},"accountType":"FREE"}` —
то есть 500 в сутки подтверждено живьём, раньше цифра стояла как неофициальная.

### Кинопоиск, `poiskkino.dev`

| | |
|---|---|
| Объекта нет | `404` `{"statusCode":404,…}` у точечных `/{id}`; поиск — `200` + `docs: []` **[док]** |
| Частота | `429` нигде не документирован; заголовки `x-ratelimit-*` есть только на `/v1.5/token` **[док/живьём]** |
| Квота | `403` `{"statusCode":403,"message":"Превышен дневной лимит!"}` **[док]** |
| Ключ | `401`, три разных текста, в том числе «Пользователь не найден!» для отозванного **[живьём]** |
| Сбой | не документирован; периметр Envoy, при падении апстрима тело plain text **[живьём]** |

Коды не пересекаются — из зеркал это самое чистое. **Сопоставлять строго по
`statusCode`, а не по тексту:** в самой спецификации есть баг — у нескольких
точечных эндпоинтов ответ `404` ссылается на тип ошибки `403`, поэтому
официальный пример под заголовком «Фильм с таким id не найден» показывает тело
«Превышен дневной лимит!» **[док]**.

Тот же `403` приходит и на нарушение пагинации в демо-режиме — эти два случая
не различить.

Срок отката — `GET /v1.5/token` → `requestsRemaining`, `ttl`, `resetAt`.
Эндпоинт лимит не тратит. Это лучший источник срока среди всех агрегаторов.

Также: поле `message` может прийти массивом, хотя типизировано строкой **[док]**.

| Источник | Откуда |
|---|---|
| MDBList | заголовок `Retry-After` |
| poiskkino.dev | отдельный запрос `/v1.5/token`, лимит не тратит |
| Кинопоиск unofficial | отдельный запрос `/api/v1/api_keys/{apiKey}` |
| OMDB | своя константа до следующих суток |
| TMDB | свой откат, заголовков нет |
| Steam | своя константа |
| GOG | своя константа |

## Что не проверено

Ключи есть у TMDB, OMDB, MDBList и `kinopoiskapiunofficial.tech` — взяты из
предшественника. Steam и GOG ключей не требуют. Нет ключа только у
`poiskkino.dev`.

- **Квота и частота не проверены нигде.** Ни одного источника не доводили до
  `429`, `402` или `403`: для этого надо выбрать суточный лимит.
- **MDBList: как выглядит «объекта нет».** Проверить не удалось — взятый как
  заведомо несуществующий `tt9999999` оказался настоящим фильмом, и ответ пришёл
  нормальным. Строка про `404` остаётся неподтверждённой.
- **Steam и GOG: сбои и лимиты.** Документации у обоих нет вовсе, 5xx вызвать не
  удалось, частота проверена только у Steam и только сверху.
- **`poiskkino.dev` — целиком.**
- OMDB: точный текст `"Request limit reached!"` — из issue-трекера, не из
  документации.
- Кинопоиск unofficial: точное тело `402`.
- 5xx ни у одного источника вызвать не удалось.

## Откат при исчерпанной квоте

**Берём срок из ответа, где источник его называет; где не называет — ждём до
конца суток.** Пробовать раньше бессмысленно: придёт тот же отказ, только
потраченный на него запрос уже не вернуть.

| Источник | Сколько ждём |
|---|---|
| MDBList | из `Retry-After` |
| poiskkino.dev, Кинопоиск unofficial | из запроса остатка квоты |
| OMDB | до следующих суток |
| TMDB | суточной квоты нет, откат только по частоте |
| Steam, GOG | квоты не документированы; откат свой, по частоте |
